Template Method Pattern

Master invariant algorithm skeletons, Inversion of Control (IoC), and the Hollywood Principle ("Don't call us, we'll call you"). Directly synthesized from Course Faculty's lecture notes and authentic exam sheets.

⚡ Executive Summary Template Method: The Invariant Workflow Skeleton
Collapse Expand

“The Hollywood Principle: 'Don't call us, we'll call you.' The parent class calls subclass operations, never the reverse.”

🎯 Invariant Algorithm Skeleton

An abstract base class defines the invariant execution steps in a final template method. Subclasses implement the abstract primitives or hook steps, but cannot alter the execution sequence.

→ Guarantees mandatory lifecycle ordering.
🕵️‍♂️ Hooks vs. Abstract Primitives

Abstract primitives must be overridden by subclasses. Hook methods provide sensible default or empty implementations that subclasses may optionally override to fine-tune behavior.

→ Prevents boilerplate in subclasses that need default behavior.
Template Method Architecture Matrix
Concept / Pattern Architectural Mechanism Why It Matters in Practice & Exams
Template Method Final Skeleton Method Enforces invariant step execution order across all subclasses.
Primitive Operation Abstract Method Mandatory step that each concrete subclass must implement.
Hook Method Default / Empty Body Optional interception point for subclasses without forcing override.

Pattern Profile & Canonical UML Architecture

Core GoF Specification
Name: Template (also known as Template Method)
Type: Behavioral pattern because it focuses on how objects interact and communicate with each other.
Important Note: You are extending the base class, not implementing an interface.
Problem: Two different components have significant implementation (and behavior) similarities, but demonstrate no reuse of a common interface or implementation. Any change requires a duplication of efforts.
Solution: Abstract our commonality into a common superclass and use the Hollywood Principle (“Don't call us, we call you!”) as the parent class calls the subclass (and not the other way around).
Use it to:
  • Implement the invariant parts of an algorithm once and leave it to the subclasses to implement behavior that can vary.
  • Localize common behavior among subclasses and place it in a common class (superclass) to avoid code duplication — classic example of code refactoring.
  • Control how subclasses extend superclass operations. Define a template method calling hook operations at specific points, thereby permitting extensions at precisely that point — Open Closed Principle (OCP).
⚠️ Note from Course Faculty: Beware the template method can appear in different states apart from the textbook implementation.

📖 Head First: Preparing Beverages (Template Method) Head First Chapter 8
Collapse Expand

In “Head First Design Patterns,” Chapter 8 delves into the Template Method Pattern through the example of preparing beverages like tea and coffee. This pattern defines the skeleton of an algorithm in a method, allowing subclasses to override specific steps without changing the algorithm's overall structure.

Example: Preparing Beverages

The process of making tea and coffee shares a common sequence of steps:

  1. Boil water.
  2. Brew or steep the beverage.
  3. Pour into a cup.
  4. Add condiments.

While the overall process is similar, the specifics of brewing and adding condiments differ between tea and coffee. The Template Method Pattern captures this shared structure and allows subclasses to define the differing steps.

💻 Java Code Implementation (Annotated from Exam Notes) CaffeineBeverage.java 
// 1. Abstract Template Superclass defining the invariant skeleton of the algorithm
public abstract class CaffeineBeverage {

    // The Template Method: Marked 'final' so subclasses CANNOT override the execution sequence!
    // This enforces the invariant algorithm skeleton (Hollywood Principle: superclass calls subclass).
    final void prepareRecipe() {
        boilWater();
        brew();
        pourInCup();
        addCondiments();
    }

    // Primitive operations: abstract methods deferred to subclasses for specific beverage variations
    abstract void brew();
    abstract void addCondiments();

    // Invariant operations: concrete steps shared identically across all caffeine beverages
    void boilWater() {
        System.out.println("Boiling water");
    }

    void pourInCup() {
        System.out.println("Pouring into cup");
    }
}

// 2. Concrete Subclass: Implements the primitive operations specific to Tea
public class Tea extends CaffeineBeverage {
    public void brew() {
        System.out.println("Steeping the tea");
    }

    public void addCondiments() {
        System.out.println("Adding Lemon");
    }
}

// 3. Concrete Subclass: Implements the primitive operations specific to Coffee
public class Coffee extends CaffeineBeverage {
    public void brew() {
        System.out.println("Dripping Coffee through filter");
    }

    public void addCondiments() {
        System.out.println("Adding Sugar and Milk");
    }
}

// 4. Test Drive Client: Demonstrates polymorphism & Inversion of Control
public class BeverageTestDrive {
    public static void main(String[] args) {
        Tea tea = new Tea();
        Coffee coffee = new Coffee();

        System.out.println("\nMaking tea...");
        tea.prepareRecipe(); // prepareRecipe() in superclass calls Tea's brew() & addCondiments()

        System.out.println("\nMaking coffee...");
        coffee.prepareRecipe(); // prepareRecipe() in superclass calls Coffee's brew() & addCondiments()
    }
}

// 5. Hook Variation: Hooks provide optional extension points without altering the skeleton
public abstract class CaffeineBeverageWithHook {

    // Template method calling a conditional hook
    final void prepareRecipe() {
        boilWater();
        brew();
        pourInCup();
        // The hook method customerWantsCondiments() controls whether condiments are added
        if (customerWantsCondiments()) {
            addCondiments();
        }
    }

    abstract void brew();
    abstract void addCondiments();

    void boilWater() {
        System.out.println("Boiling water");
    }

    void pourInCup() {
        System.out.println("Pouring into cup");
    }

    // Hook operation: provides a default implementation (returns true).
    // Subclasses can optionally override this hook (e.g. prompt customer) without breaking OCP.
    boolean customerWantsCondiments() {
        return true;
    }
}

3 Core Architectural Rules Tested in Exams

Exam Essentials
Rule 1 Mark the Template Method final in Java

If prepareRecipe() is not final, rogue subclasses can override the entire skeleton, tampering with execution ordering or removing security/validation checks. Marking it final protects the invariant sequence.

Rule 2 The Hollywood Principle ("Don't call us, we'll call you!")

High-level components (the superclass) treat low-level components (the subclasses) as passive modules. The superclass decides when and how to call subclass methods—subclasses never call the superclass template method directly. This is the foundation of Inversion of Control (IoC) frameworks.

Rule 3 Hooks vs. Abstract Methods (OCP Conformance)

Abstract Methods enforce mandatory steps: subclasses must implement them or fail compilation. Hook Methods provide a default empty or boolean behavior, offering optional extension points without breaking existing subclasses, directly fulfilling the Open-Closed Principle (OCP).

The Big Exam Trade-off: Inheritance vs. Composition

Duck / Comparator Exam Case Study

Exam Question from Course Faculty's Notes: “The Template Method relies on inheritance. Would it be possible to get the same functionality of a Template Method, using object composition? What would some of the tradeoffs be?”

Yes: Instead of relying on subclassing, we inject a strategy object (such as a Comparator<Duck>) directly into the class via Constructor Dependency Injection. 

import java.util.Comparator;

public class Duck {
    private String name;
    private int weight;
    private Comparator<Duck> comparator;

    // The comparator is injected (composition) instead of using inheritance.
    public Duck(String name, int weight, Comparator<Duck> comparator) {
        this.name = name;
        this.weight = weight;
        this.comparator = comparator;
    }

    // Delegate comparison to the composed comparator.
    public int compare(Duck other) {
        return comparator.compare(this, other);
    }

    public int getWeight() {
        return weight;
    }

    @Override
    public String toString() {
        return name + " weighs " + weight;
    }

    public static void main(String[] args) {
        // Define a Comparator to compare ducks by weight.
        Comparator<Duck> weightComparator = (d1, d2) -> Integer.compare(d1.getWeight(), d2.getWeight());
        Duck duck1 = new Duck("Daffy", 8, weightComparator);
        Duck duck2 = new Duck("Donald", 10, weightComparator);

        System.out.println(duck1);
        System.out.println(duck2);
        System.out.println("Comparison result: " + duck1.compare(duck2)); // Negative if duck1 is lighter.
    }
}
✅ Pros of Composition Approach
  • Runtime Flexibility: Behaviors can be swapped or modified at runtime by injecting different delegate objects, offering dynamic customization.
  • Loose Coupling: Composition decouples the algorithm's structure from its individual steps, making the system more modular and easier to test.
  • Enhanced Reusability: Individual strategy objects can be reused across different contexts without being tied to a rigid inheritance hierarchy.
⚠️ Cons of Composition Approach
  • Boilerplate & Object Graph: It may result in more boilerplate code and a more complex object graph.
  • Increased Complexity: Managing multiple objects and their interactions can lead to a more complex design compared to a single inheritance-based template.
  • Distributed Algorithm Logic: The overall flow of the algorithm might be less transparent since the steps are spread across several objects, potentially making the system harder to understand.
Architecture Dimension Template Method (Inheritance) Strategy / Composition Alternative
Runtime Flexibility Rigid: Behavior is statically bound at compile time; cannot swap beverage recipe dynamically. Dynamic: Can swap algorithms dynamically at runtime via setter/constructor dependency injection.
Algorithm Transparency High: The entire algorithm flow is visible in one single method (prepareRecipe()). Distributed: Flow is fragmented across multiple delegate objects and interfaces.
Object Graph & Memory Minimal: Single object instance allocated on the heap. Higher Overhead: Proliferation of small strategy objects, allocations, and references.

Authentic Exam Sheet · Question 8 [5 Pts] How does the Strategy Pattern differ from the Template Method Pattern?

Official Model Answer & Grading Rubric (Exam Standard):

The difference centers around coupling mechanism, runtime mutability, and algorithm granularity:

  1. Coupling Mechanism:
    • Strategy: Utilizes object composition and delegation. Context holds an interface reference to a Strategy object.
    • Template Method: Utilizes class inheritance. Subclasses extend an abstract base class.
  2. Runtime Mutability:
    • Strategy: Entire algorithms can be swapped dynamically at runtime via setter injection (e.g. duck.setFlyBehavior(new FlyRocketPowered())).
    • Template Method: Algorithm variants are bound statically at compile-time via inheritance; changing behavior requires re-instantiation.
  3. Algorithm Granularity:
    • Strategy: Encapsulates and swaps the entire algorithm as an atomic unit.
    • Template Method: Freezes the invariant algorithm skeleton in the superclass and allows subclasses to vary only individual steps.
