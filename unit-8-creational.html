Abstract Factory & The Singleton Pattern

“Each pattern is a rule which describes what you have to do, to bring that configuration of relationships about.” — Christopher Alexander

Managing object instantiation responsibly: ensuring cohesive product families and controlling global instance lifecycles safely in multi-threaded environments.

1

8.3 The Abstract Factory Pattern

Producing families of related products without binding to concrete classes.

GoF Intent: Provide an interface for creating families of related or dependent objects without specifying their concrete classes.

The Pizza Franchise Problem: NY Pizza requires thin crust, marinara sauce, and Reggiano cheese. Chicago Pizza requires thick deep-dish dough, plum tomato sauce, and Mozzarella. If a Chicago kitchen accidentally uses NY dough with plum sauce, quality control fails.

The Solution: Create an PizzaIngredientFactory interface. Each regional factory (NYPizzaIngredientFactory, ChicagoPizzaIngredientFactory) produces a guaranteed cohesive family of ingredients.

2

Factory Method vs. Abstract Factory

Factory Method (Inheritance)

Relies on inheritance: an abstract class declares an abstract method createPizza(String type), and subclasses decide which concrete product class to instantiate. Creates one product.

Abstract Factory (Composition)

Relies on composition: an independent factory object is passed to client code, exposing multiple factory methods to create an entire family of related products.

8.5 The Singleton Pattern & Thread-Safety

Guaranteeing a single shared instance across a multi-threaded application.

Intent: Ensure a class only has one instance, and provide a global point of access to it.

DoubleCheckedLocking.javaThread-Safe Lazy Initialization
public class DatabaseConnectionPool {
    // 1. volatile prevents CPU instruction reordering!
    private static volatile DatabaseConnectionPool uniqueInstance;

    // 2. Private constructor prevents direct 'new' instantiations
    private DatabaseConnectionPool() {}

    // 3. Double-checked locking avoids synchronizing on every call
    public static DatabaseConnectionPool getInstance() {
        if (uniqueInstance == null) {
            synchronized (DatabaseConnectionPool.class) {
                if (uniqueInstance == null) {
                    uniqueInstance = new DatabaseConnectionPool();
                }
            }
        }
        return uniqueInstance;
    }
}
⚠️ Why is Singleton Often Considered an Anti-Pattern?
  • Hidden Dependencies: Classes access Singleton.getInstance() internally instead of declaring dependencies in their constructors.
  • Unit Testing Nightmare: Global state persists across test cases, making tests interdependent and impossible to run reliably in parallel.
  • Violates SRP: The class controls both its domain responsibility AND its own lifecycle management.

8.7 Questions for Self-Study

Exam Drill Why is the volatile keyword mandatory in Java's Double-Checked Locking Singleton implementation?

Without volatile, the JVM/compiler can reorder bytecode instructions during object creation.

Specifically, new Object() involves three steps: (1) allocate memory, (2) initialize the object, (3) assign reference to uniqueInstance. If instructions reorder step 3 before step 2, another thread checking uniqueInstance == null outside the synchronized block might see a non-null reference to a partially initialized object, leading to silent memory corruption or crashes.
