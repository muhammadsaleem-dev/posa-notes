Creational Patterns: Singleton & Factories

Master object instantiation encapsulation, thread-safe Singleton idioms (Double-Checked Locking, Bill Pugh Holder, Enum), the Reflection Guard, and the fundamental differences between Factory Method and Abstract Factory.

⚡ Executive Summary Creational Patterns: Decoupling Instantiation from Usage
Collapse Expand

“Abstract the instantiation process. Make software independent of how objects are created, composed, and represented.”

🎯 Factory Method vs. Abstract Factory

Factory Method uses inheritance: subclasses decide which single product to create. Abstract Factory uses composition: an object creates families of related or dependent products without binding to concrete classes.

→ Single product variance vs. multi-product family variance.
🕵️‍♂️ Singleton Hazards & Reflection Guards

Singletons introduce global mutable state and tight coupling. If a true Singleton is required, protect against reflection and serialization attacks using single-element Enums or explicit constructor guards.

→ Prefer dependency injection over pervasive Singleton usage.

Creational Patterns Overview

Core GoF Specifications
1. Singleton Pattern: "Ensure a class only has one instance, and provide a global point of access to it." Private constructor, static instance holder, and public static accessor (getInstance()).
2. Factory Method Pattern: "Define an interface for creating an object, but let subclasses decide which class to instantiate. Factory Method lets a class defer instantiation to subclasses." (Relies on inheritance).
3. Abstract Factory Pattern: "Provide an interface for creating families of related or dependent objects without specifying their concrete classes." (Relies on object composition).

Thread-Safe Singletons & The Reflection Guard

Concurrency & Reflection Defense
CRITICAL CONCURRENCY 4 Ways to Implement Singleton in Java
1. Double-Checked Locking (DCL)

Lazy initialization avoiding continuous synchronized overhead: 

public class DclSingleton {
    // volatile is mandatory to prevent instruction reordering!
    private static volatile DclSingleton instance;
    private DclSingleton() {}

    public static DclSingleton getInstance() {
        if (instance == null) {
            synchronized (DclSingleton.class) {
                if (instance == null) {
                    instance = new DclSingleton();
                }
            }
        }
        return instance;
    }
}
2. Bill Pugh Holder Idiom

Lazy-loaded by JVM class loader without any synchronization: 

public class HolderSingleton {
    private HolderSingleton() {}

    private static class Holder {
        static final HolderSingleton INSTANCE = new HolderSingleton();
    }

    public static HolderSingleton getInstance() {
        return Holder.INSTANCE; // Loaded on first call!
    }
}

Exam Focus: The Reflection Guard Exception

Even with a private constructor, an attacker can use constructor.setAccessible(true) via Java Reflection to instantiate a second instance.
The Defense: Check if an instance already exists inside the constructor and immediately throw an IllegalStateException (or RuntimeException): 

private Singleton() {
    if (instance != null) {
        throw new IllegalStateException("Singleton already initialized! Use getInstance()");
    }
}

Factory Method vs. Abstract Factory

Architectural Disambiguation
DECISION MATRIX Which Creational Pattern to Use?
Dimension Factory Method Abstract Factory
Primary Mechanism Inheritance: Subclasses override creator method. Object Composition: Factory object injected into client.
Product Scope Creates a single product (e.g. Pizza). Creates an entire product family (e.g. Dough, Sauce, Cheese).
Client Coupling Client subclasses the Creator class. Client depends only on the AbstractFactory interface.
Extensibility Easy to add new products (create new creator subclass). Hard to add new product types (requires changing factory interface).

Direct Question → Answer Format
Question 1: Singleton Reflection Attack & Defense 6 Points

How can an attacker create multiple instances of a classic Java Singleton despite private constructors, and what exact defensive code must be added to the constructor to neutralize this vulnerability?

Model Answer:
  1. The Attack: Using Java Reflection, an attacker retrieves the declared constructor via Constructor<?> c = Singleton.class.getDeclaredConstructor(), bypasses visibility via c.setAccessible(true), and invokes c.newInstance() to instantiate a second distinct object.
  2. The Defense: Add an instantiation guard inside the constructor: 
    private Singleton() {
    if (instance != null) {
        throw new IllegalStateException("Instance already created! Use getInstance().");
    }
}
  3. Alternative: Use an enum Singleton { INSTANCE; }, which the JVM natively protects against reflection instantiation and deserialization attacks.
Question 2: Why is the volatile Keyword Mandatory in Double-Checked Locking? 4 Points

Why does Double-Checked Locking without volatile fail in multithreaded environments?

Model Answer:

Without volatile, the JVM and CPU can reorder instructions during object creation (instance = new Singleton()). The creation steps:

  1. Allocate memory space for Singleton object.
  2. Initialize the object (execute constructor).
  3. Assign reference of allocated memory to variable instance.

Due to compiler optimization, step 3 can execute before step 2. Another thread checking the outer if (instance == null) observes a non-null reference and returns a partially initialized, corrupt object! The volatile keyword introduces a memory barrier preventing instruction reordering.
