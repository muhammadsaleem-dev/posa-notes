PILLAR 1 OF 8 · INTENT & MOTIVATION

Decoupling Instantiation from Utilization

Using the new operator ties code to a concrete implementation, violating the Dependency Inversion Principle. Creational patterns encapsulate object construction so client code remains completely agnostic of concrete product types.

Abstract Factory Intent

Provide an interface for creating families of related or dependent objects without specifying their concrete classes.

Singleton Intent

Ensure a class has only one instance, and provide a global point of access to it.

PILLAR 4 OF 8 · DESIGN PRINCIPLES

Dependency Inversion Principle (DIP) in Creation

DIP Formulation

Depend upon abstractions. Do not depend upon concrete classes. Never hold direct references to concrete product classes.

Family Consistency Guarantee

Abstract Factory enforces that products created by a factory are guaranteed to be compatible (no Chicago thick dough with NY marinara sauce).

Singleton vs Global State

Singletons provide global access, but should strictly be used when exactly ONE instance is required (e.g. hardware registry or thread pool).

PILLAR 5 OF 8 · IMPLEMENTATION MECHANICS

Double-Checked Locking & The volatile Barrier

DoubleCheckedLocking.java · Thread-Safe Singleton
public class DatabaseConnectionPool {
    // 1. volatile keyword establishes happens-before memory barrier
    private static volatile DatabaseConnectionPool uniqueInstance;

    private DatabaseConnectionPool() {}

    public static DatabaseConnectionPool getInstance() {
        if (uniqueInstance == null) { // Check 1 (no lock overhead)
            synchronized (DatabaseConnectionPool.class) {
                if (uniqueInstance == null) { // Check 2 (under lock)
                    uniqueInstance = new DatabaseConnectionPool();
                }
            }
        }
        return uniqueInstance;
    }
}
PILLAR 6 OF 8 · COSTS & TRADE-OFFS

Architectural Liabilities & Anti-Pattern Risks

✅ Creational Benefits
  • 100% decoupling from concrete class constructors.
  • Guaranteed compatibility across product families.
  • Lazy instantiation conserves memory and resources.
⚠️ Architectural Liabilities
  • Adding new product types to Abstract Factory requires editing all concrete factories.
  • Singleton creates hidden dependencies and state pollution during unit testing.
  • Violates Single Responsibility Principle (manages state AND lifecycle).

Prof. Schäfer Exam Traps: The volatile Memory Barrier

🚨 Frankfurt UAS Exam Trap #1: Why is volatile strictly required?

Question: "In Java Double-Checked Locking, why can omission of volatile cause crashes even with synchronized?"
Model Answer: The JVM or CPU can reorder bytecode instructions during object allocation. Creating an object involves: (1) allocate memory, (2) run constructor, (3) assign reference. If instructions are reordered so (3) happens before (2), another thread outside the lock may read a non-null reference to a partially initialized object, causing immediate NullPointerExceptions or data corruption.

JDK Benchmark: java.sql.DriverManager.getConnection(), Runtime.getRuntime().

● Stage 01 · Object Instantiation Woes

The Franchise Quality Control Crisis

Consider a expanding Pizza franchise. NY stores need thin crust, marinara sauce, and fresh Reggiano cheese. Chicago stores require thick deep-dish dough, plum tomato sauce, and heavy Mozzarella. If a Chicago kitchen mistakenly uses thin NY dough with plum sauce, quality control fails and customers complain.

FragilePizzaStore.java · The Anti-Pattern
// ANTI-PATTERN: Client code directly instantiating concrete ingredients!
Pizza orderPizza(String style, String type) {
    Pizza pizza;
    if (style.equals("NY")) {
        pizza = new NYStyleCheesePizza(new ThinCrustDough(), new MarinaraSauce(), new ReggianoCheese());
    } else if (style.equals("Chicago")) {
        // Human error risk: Developer mixes up thick crust with NY marinara sauce!
        pizza = new ChicagoStyleCheesePizza(new ThickCrustDough(), new MarinaraSauce(), new MozzarellaCheese());
    }
    // Client is tightly coupled to every single concrete ingredient class!
    pizza.prepare();
    pizza.bake();
    return pizza;
}
🧠 Key Takeaways: The Creational Axioms
Encapsulate 'new'

Object creation is a volatile responsibility. Confining new inside factories shields clients from changes in class hierarchies.

Product Families

Abstract Factory ensures related products that belong together (dough, sauce, cheese) are always instantiated as a cohesive unit.

Thread-Safe Concurrency

Lazy-loaded Singletons require strict memory barriers (volatile) to prevent multi-threaded race conditions.

● Stage 04 · Enterprise Production Code

Production Code: Thread-Safe Singleton Idioms

There are two production-grade ways to implement Singleton in modern Java: Double-Checked Locking (with volatile) and the Bill Pugh Static Initialization Holder.

BillPughSingleton.java · Lazy & Lock-Free
package de.frankfurt.posa.creational;

public class ConfigurationManager {
    // Private constructor blocks direct instantiation
    private ConfigurationManager() {
        // Guard against reflection attacks
        if (InstanceHolder.INSTANCE != null) {
            throw new IllegalStateException("Already initialized");
        }
    }

    // Static nested class is only loaded when getInstance() is called!
    private static class InstanceHolder {
        private static final ConfigurationManager INSTANCE = new ConfigurationManager();
    }

    // Thread-safe, lazy, and completely synchronization-free!
    public static ConfigurationManager getInstance() {
        return InstanceHolder.INSTANCE;
    }
}

Exam Drill 1 Why is the volatile keyword mandatory in Java's Double-Checked Locking Singleton? (10 Exam Points)

Model Answer (Prof. Schäfer 1.0 Standard):

Without volatile, the Java Memory Model allows CPU instruction reordering during object instantiation.

The expression uniqueInstance = new Singleton() is compiled into three bytecode steps:

  1. Allocate memory on the heap.
  2. Invoke constructor to initialize fields.
  3. Assign reference of allocated memory to uniqueInstance.

If instructions are reordered so that step 3 executes before step 2, another thread executing the first unsynchronized check (if (uniqueInstance == null)) will observe a non-null reference to an uninitialized object. When that thread accesses the instance, it will crash or read corrupt state. The volatile keyword creates a memory barrier that prevents this reordering.

Exam Drill 2 Compare Factory Method and Abstract Factory across Scope, Mechanism, and Coupling. (6 Exam Points)

Comparison Table:

  • Mechanism: Factory Method relies on inheritance (subclasses override an abstract method). Abstract Factory relies on object composition (an external factory object is injected into the client).
  • Scope: Factory Method produces a single product. Abstract Factory produces an entire family of related products.
  • Coupling: Factory Method couples the creator hierarchy to product hierarchies. Abstract Factory decouples the client completely, depending solely on abstract product interfaces.
Exam Drill 3 Why is the Singleton Pattern frequently categorized as an Architectural Anti-Pattern? (4 Exam Points)

Three Architectural Criticisms:

  1. Hidden Dependencies: Classes access Singleton.getInstance() internally instead of declaring dependencies explicitly in their constructors.
  2. Unit Testing Impediment: Global mutable state persists across test executions, causing tests to fail when run in parallel or out of order.
  3. Violates SRP: The class manages its own lifecycle alongside its business domain responsibilities. Modern systems replace Singleton classes with Dependency Injection framework scoping (e.g. Spring `@Scope("singleton")`).
