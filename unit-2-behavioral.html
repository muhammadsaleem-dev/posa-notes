2.2 The Hollywood Principle: Inversion of Control

“Don’t call us, we’ll call you!” — The Hollywood Principle

In traditional top-down procedural programming, low-level modules call high-level utility functions. Under the Hollywood Principle, control flow is completely inverted (IoC):

  • The high-level abstract class dictates when the workflow proceeds.
  • Subclasses provide specific implementations, but never decide when they are called.
  • This prevents dependency rot (the "dependency spaghetti" where components call back and forth indiscriminately).

2.5 Macro Commands & Thread Pool Scheduling

Executing composite command sequences and decoupling work items in concurrent thread pools.

MacroCommand.java Composite Pattern + Command Pattern 
public class MacroCommand implements Command {
    private final List<Command> commands;

    public MacroCommand(List<Command> commands) {
        this.commands = List.copyOf(commands);
    }

    @Override
    public void execute() {
        for (Command cmd : commands) {
            cmd.execute();
        }
    }

    @Override
    public void undo() {
        // Crucial architectural detail: Undo MUST run in reverse order!
        ListIterator<Command> it = commands.listIterator(commands.size());
        while (it.hasPrevious()) {
            it.previous().undo();
        }
    }
}

🎯 Self-Study Q1: Template Method vs. Composition

"The Template Method relies on inheritance. Would it be possible to get the same functionality of a Template Method using object composition? What would some of the trade-offs be?"

Yes, by combining the Strategy Pattern with callbacks: Instead of subclassing, the workflow class holds references to functional interfaces for each variant step (e.g. brewStep and condimentStep).

Trade-offs:

  • Composition Advantages: You can swap individual steps dynamically at runtime and avoid fragile base-class hierarchy lock-in.
  • Composition Disadvantages: Requires managing multiple delegate objects, increases parameter plumbing, and sacrifices the simplicity of a single abstract class skeleton.
🎯 Self-Study Q2: Command Coupling & Dumb vs. Smart Commands

"How tightly coupled is a concrete Command to its Receiver? Can a Command execute logic itself without any Receiver?"

Two Architectural Styles exist:

  1. Dumb Commands (Standard GoF): The command holds only a reference to Receiver and delegates execution (receiver.action()). Coupling between Command and Receiver is tight, but the Invoker remains 100% decoupled from Receiver.
  2. Smart / Self-Contained Commands: The command implements the full business logic directly without delegating to any Receiver. Useful when tasks are standalone calculations, or in distributed RPC queues.
