Universal Architectural Standard Pillar 01

Intent & Failure Mode Elimination

Behavioral patterns coordinate workflows and control flow across decoupled collaborators:

  • ✓ Template Method Intent: Define an invariant algorithm skeleton in an operation, deferring custom steps to subclasses without altering overall workflow structure.
  • ✓ Command Intent: Encapsulate a request as an object, parameterizing callers with different requests, queueing/logging tasks, and enabling reversible multi-level Undo.
  • ✕ Failure Mode Eliminated: Duplicated copy-paste procedural workflows (Template) and tight coupling between caller UI buttons and receiver domain services (Command).

Recipe Skeleton vs. Remote Control

TemplateMethodSkeleton.java · Invariant Workflow 
public abstract class CaffeineBeverage {
    // Invariant algorithm skeleton: declared FINAL so subclasses cannot alter order!
    public final void prepareRecipe() {
        boilWater();
        brew(); // Primitive abstract step
        pourInCup();
        if (customerWantsCondiments()) { // Concrete Hook with default implementation
            addCondiments();
        }
    }
    abstract void brew();
    abstract void addCondiments();
    void boilWater() { System.out.println("Boiling water"); }
    void pourInCup() { System.out.println("Pouring into cup"); }
    boolean customerWantsCondiments() { return true; } // Hook
}
🎯 Prof. Schäfer Exam Criteria: You will be asked: "Why must the template method be declared final?" Answer: To enforce algorithm integrity so subclasses cannot override the sequence of operations.
Universal Architectural Standard Pillar 02

Structural Participants & Responsibility

Isolate roles strictly between who dictates the skeleton, who requests action, and who executes logic:

  • ✓ AbstractClass (Template): Declares invariant template method and primitive step hooks.
  • ✓ ConcreteClass (Template): Implements abstract primitive steps without altering workflow timing.
  • ✓ Invoker (Command): Remote Control or UI Menu. Holds command slot and calls command.execute().
  • ✓ Command Interface: Declares void execute() and void undo().
  • ✓ Receiver: The domain entity (Light, GarageDoor) performing actual work.
Unit 2: Participant Mapping

Remote Control Collaborators

  • ✓ Invoker: RemoteControl (holds an array of Command slots and an undo reference).
  • ✓ Command Contract: Command interface (execute(), undo()).
  • ✓ ConcreteCommand: LightOnCommand, LightOffCommand, CeilingFanHighCommand.
  • ✓ Receiver: Light, CeilingFan (domain hardware entities).
  • ✓ Client: RemoteLoader (wires Receivers into Commands and slots into Invoker).
🎯 Exam Trap: The Invoker must NEVER hold a direct reference to the Receiver! The Invoker only speaks to the Command interface.

Universal Architectural Standard Pillar 04

The Hollywood Principle & Inversion of Control

Low-level components participate in algorithms, but high-level classes control when and how:

  • ✓ The Hollywood Principle: “Don’t call us, we’ll call you.” Prevents dependency rot and circular callback graphs.
  • ✓ Single Responsibility Principle (SRP): The Invoker doesn't know what turning on a light entails; Receiver doesn't know who pushed the button.
  • ✓ Open/Closed Principle (OCP): Adding a new command (e.g. GarageDoorOpenCommand) requires zero edits to RemoteControl.
Unit 2: Behavioral Invariants

IoC in Action: Framework Design

Every major enterprise framework (Spring MVC, JUnit, Android Activity lifecycle) relies on the Hollywood Principle. You register hooks; the framework engine calls them.

🎯 Exam Question: "How does the Hollywood Principle relate to Dependency Inversion (DIP)?" Both favor high-level abstraction, but Hollywood specifically dictates that high-level modules orchestrate the lifecycle of low-level modules, never vice versa.
Universal Architectural Standard Pillar 05

Implementation Mechanics & Null Object Pattern

Enterprise command dispatchers must eliminate null checks and manage state history:

  • ✓ Null Object Pattern (NoCommand): Initializing slots with a do-nothing command eliminates tedious if (slot != null) checks.
  • ✓ Single-Level Undo: Tracking undoCommand = slot; allows immediate one-step rollback.
  • ✓ Multi-Level Undo: Storing executed commands in a Deque<Command> LIFO stack enables browser-like history backtracks.

Remote Slot Assignment & Undo Stack

RemoteControlWithUndo.java · Robust Invoker 
public class RemoteControlWithUndo {
    Command[] onCommands;
    Command[] offCommands;
    Command undoCommand; // Tracks the last executed action

    public RemoteControlWithUndo() {
        onCommands = new Command[7];
        offCommands = new Command[7];
        Command noCommand = () -> {}; // Null Object (Lambda!)
        for (int i = 0; i < 7; i++) {
            onCommands[i] = noCommand;
            offCommands[i] = noCommand;
        }
        undoCommand = noCommand;
    }
    public void onButtonWasPushed(int slot) {
        onCommands[slot].execute();
        undoCommand = onCommands[slot]; // Saved for undo
    }
    public void undoButtonWasPushed() {
        undoCommand.undo();
    }
}
🎯 Exam Trap: Forgetting the Null Object pattern causes NullPointerException on unprogrammed remote buttons.
Universal Architectural Standard Pillar 06

Architectural Costs & Trade-offs

Every pattern balances decoupling flexibility against structural weight:

  • ✓ Template Method Benefits: Maximum code reuse, rigid workflow enforcement, simple compile-time dispatch.
  • ✕ Template Method Costs: Class Bloat ($N$ classes for $N$ variants), compile-time lock (cannot swap steps at runtime).
  • ✓ Command Benefits: Decouples Invoker from Receiver, supports queueing, scheduling, logging, and undo.
  • ✕ Command Costs: Class Explosion (every tiny action needs a Command class). Mitigated in modern Java with lambdas.

Universal Architectural Standard Pillar 07

Rival Pattern Decision Matrix

Discriminating between Strategy, Template Method, and Command is a core POSA exam target:

  • ✓ Template vs. Strategy: Template uses inheritance to vary parts of an algorithm. Strategy uses composition to vary an entire algorithm at runtime.
  • ✓ Command vs. Strategy: Command encapsulates a request / action (with undo & queueing). Strategy encapsulates an algorithm.
  • ✓ Command vs. Observer: Observer broadcasts events to many listeners without return values. Command represents a discrete, targeted action intended for a specific receiver.

Top 3 Exam Traps to Avoid

  • ✕ Trap 1: MacroCommand Undo Forward Loop. Executing undo() in forward order (1 $\to$ 2 $\to$ 3) corrupts dependent state. Must iterate in reverse LIFO order (3 $\to$ 2 $\to$ 1)!
  • ✕ Trap 2: Forgetting final on Template Method. Without final, subclasses can override the skeleton itself, breaking algorithm integrity.
  • ✕ Trap 3: Invoker Knowing the Receiver. Passing the Receiver instance directly to the Invoker breaks encapsulation.

“Don’t call us, we’ll call you!” — The Hollywood Principle (Inversion of Control)

In traditional procedural programming, low-level modules call high-level utility functions. Under the Hollywood Principle, control flow is completely inverted (IoC):

  • The high-level abstract class declares a final template method that dictates when each step executes.
  • Subclasses provide specific step implementations, but never dictate the sequence or timing.
  • This eliminates dependency rot and prevents fragile callback loops.
STAGE 1 KEY TAKEAWAYS · INVERSION OF CONTROL AXIOMS

The 3 Architectural Rules of Template Method

The Template Method pattern establishes strict boundaries between invariant flow control and variant subclass customization:

Rule 1 · Final Skeleton

Freeze the Workflow

Declare the template method as final in the abstract base class to guarantee that no subclass can alter the sequence of execution.

Rule 2 · Hollywood IoC

Don't Call Us

High-level components invoke low-level components, never the reverse. Subclasses fill in blanks without controlling lifecycle timing.

Rule 3 · Optional Hooks

Hooks vs. Abstracts

Use abstract methods for mandatory steps subclasses must supply; use concrete empty hooks for optional behavioral overrides.

Stage 02 · First-Class Request Objects

The Command Pattern: Modeling Verbs as Objects

Decouple the sender of a request (Invoker) from the object that actually executes the business action (Receiver).

Gang of Four Specification

“Encapsulate a request as an object, thereby letting you parameterize clients with different requests, queue or log requests, and support undoable operations.”

Invoker (Caller): Remote control button or UI menu item. Only holds a Command reference and triggers command.execute(). Zero knowledge of Receiver hardware.
Command Interface: Uniform contract declaring void execute() and optional void undo(). Eliminates type variance.
Receiver (Performer): The actual hardware appliance (Light, Stereo, GarageDoor) performing the real domain work.
CommandPatternWiring.java · Complete Contract 
// 1. Command Interface Contract
public interface Command {
    void execute();
    void undo();
}

// 2. ConcreteCommand encapsulating action on Receiver
public class LightOnCommand implements Command {
    private final Light light; // Reference to Receiver

    public LightOnCommand(Light light) {
        this.light = light;
    }
    @Override
    public void execute() {
        light.on(); // Delegated to Receiver
    }
    @Override
    public void undo() {
        light.off(); // Symmetrical reversal
    }
}

Macro Commands, Multi-Level Undo & Thread Pools

CRITICAL EXAM RULE: Reverse Undo Ordering (LIFO)

When executing a MacroCommand (Composite Pattern), commands execute in forward order (1 $\to$ 2 $\to$ 3). However, when calling undo(), the sequence MUST strictly execute in reverse order (3 $\to$ 2 $\to$ 1) using a LIFO Stack or reverse iterator. Otherwise, state dependencies will be corrupted!

MacroCommand.java · Reverse LIFO Loop 
public class MacroCommand implements Command {
    private final Command[] commands;

    public MacroCommand(Command[] commands) {
        this.commands = commands;
    }
    @Override
    public void execute() {
        for (Command cmd : commands) { // Forward chronological order: 1 -> 2 -> 3
            cmd.execute();
        }
    }
    @Override
    public void undo() {
        // FATAL EXAM ERROR: Looping forward!
        // CORRECT: Reverse loop 3 -> 2 -> 1 (LIFO)
        for (int i = commands.length - 1; i >= 0; i--) {
            commands[i].undo();
        }
    }
}

🎯 Official Exam Gotcha: Dumb vs. Smart Commands

"How tightly coupled is a concrete Command to its Receiver? Can a Command execute logic without any Receiver?"

Two Architectural Styles exist:

  1. Dumb Commands (Standard GoF): Command only delegates to Receiver (receiver.action()). Coupling between Command and Receiver is tight, but the Invoker remains 100% decoupled from Receiver.
  2. Smart / Self-Contained Commands: Command implements the complete business logic directly without any Receiver. Used in distributed RPC messaging and standalone calculation jobs.
