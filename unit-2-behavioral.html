2.3 & 2.5 The Template Method Pattern

Brewing Coffee and Tea: How factoring out common steps uncovers an algorithmic template.

☕ Coffee Recipe

  1. Boil water (identical)
  2. Brew coffee in boiling water
  3. Pour in cup (identical)
  4. Add sugar and milk

🍵 Tea Recipe

  1. Boil water (identical)
  2. Steep tea bag in boiling water
  3. Pour in cup (identical)
  4. Add lemon

The Code Smell: Duplication violates the DRY Principle (Don't Repeat Yourself). If the boiling procedure changes (e.g., waiting for optimal temperature), changes must be manually copied to every beverage class.

The Solution: CaffeineBeverage Template

🎣 Hooks in Template Method

A Hook is a method declared in the abstract superclass that provides a default (often empty or boolean) implementation. Subclasses can override it to optionally "hook into" the algorithm at specific points without modifying the template skeleton.

if (customerWantsCondiments()) { addCondiments(); }

2.5.4 The Hollywood Principle

“Don’t call us, we’ll call you!” — The Hollywood Principle

In traditional imperative programming, low-level components call high-level library functions directly. With the Hollywood Principle, the control flow is inverted (Inversion of Control - IoC): The high-level abstract class dictates when and how the algorithm proceeds, and invokes the low-level subclass methods only when their specialized steps are needed.

Template Method vs. Strategy: Which to Choose?
  • Template Method uses Inheritance: Subclasses alter specific algorithmic steps, but the overall skeleton is fixed. Compile-time binding.
  • Strategy uses Composition & Delegation: Entire algorithm is encapsulated in a separate object. Can be swapped dynamically at runtime.

2.7 The Command Pattern: Modeling Verbs

“In the Java Kingdom, the poor verbs (methods) are second-class citizens.” — Steve Yegge (“Execution in the Kingdom of Nouns”)

In pure Object-Oriented programming, everything is expected to be a "noun" (an object). But real systems require handling requests, operations, transactions, and undo queues.

GoF Intent: Encapsulate a request as an object, thereby letting you parameterize clients with different requests, queue or log requests, and support undoable operations.

Command Pattern Architecture

┌─────────────────┐ ┌─────────────────────────┐ ┌─────────────────────────┐ │ Invoker │ │ <<interface>> │ │ Receiver │ │ (RemoteControl) │ invokes │ Command │ delegates │ (Light) │ ├─────────────────┤────────────>├─────────────────────────┤────────────>├─────────────────────────┤ │ - slot: Command │ │ + execute() │ │ + on() │ │ + pressButton() │ │ + undo() │ │ + off() │ └─────────────────┘ └────────────▲────────────┘ └─────────────────────────┘ │ implements ┌────────────┴────────────┐ │ LightOnCommand │ ├─────────────────────────┤ │ - light: Light │ ├─────────────────────────┤ │ + execute() {light.on()}│ │ + undo() {light.off()} │ └─────────────────────────┘
🍽️ The Diner Analogy

Customer (Client) gives order to Waitress (Invoker). Waitress writes order slip (Command) and places it on the rack. The Cook (Receiver) reads and prepares the meal.

↩️ Universal Undo / Redo

Each Command object records the prior state before execution. Invoking undo() restores state without the Invoker needing any internal domain knowledge.

🧵 Thread Pool Queues

In concurrent systems, worker threads pull Command objects (like Runnable or Callable) from a queue and call execute() asynchronously.

2.7.4 Macro Command & Composite Actions

Executing a batch of commands with a single button press.

MacroCommand.java Party Mode Macro 
public class MacroCommand implements Command {
    private final List<Command> commands;

    public MacroCommand(List<Command> commands) {
        this.commands = commands;
    }

    @Override
    public void execute() {
        for (Command c : commands) {
            c.execute();
        }
    }

    @Override
    public void undo() {
        // Undo in reverse order!
        ListIterator<Command> it = commands.listIterator(commands.size());
        while (it.hasPrevious()) {
            it.previous().undo();
        }
    }
}

2.10 Exercise: Questions for Self-Study (Exam Practice)

Prof. Dr. Jörg Schäfer's official self-study questions with verified answers.

Self-Study Q1 The Template Method relies on inheritance. Would it be possible to get the same functionality of a Template Method using object composition? What would some of the tradeoffs be?

Yes, by combining the Strategy Pattern with callbacks or delegate steps:

Instead of having subclasses override protected abstract methods, the main class can hold references to multiple strategy objects (or lambda functions) for each customizable step.

Trade-offs Comparison:

  • Composition Advantage (Flexibility): Individual steps can be swapped dynamically at runtime without instantiating an entirely new subclass. Avoids class explosion.
  • Composition Disadvantage (Object Overhead & Boilerplate): Passing multiple fine-grained strategy delegates increases configuration complexity and object allocations.
  • Inheritance Advantage (Simplicity & State Access): Subclasses directly access protected state in the superclass without exposing getters or passing context references.
Self-Study Q2 How does the Command Object get access to the data it needs to perform its job? How does one guarantee that this does not create a strong coupling?

Access Mechanism:

  1. Constructor Dependency Injection: The specific Receiver and any static parameters are passed into the ConcreteCommand constructor at instantiation time.
  2. Execution Parameters: Alternatively, transient context data can be passed to execute(ExecutionContext ctx).

Preventing Tight Coupling:

  • The Invoker only knows the generic Command interface (execute(), undo()). It has zero coupling to the Receiver or the parameters.
  • The ConcreteCommand binds to a Receiver interface (not necessarily a concrete class).
  • The Receiver remains entirely unaware of the Command pattern; it simply exposes natural domain methods (e.g. turnOn(), deposit()).
