Iterator Pattern (Cursor)

Master sequential traversal encapsulation, the Single Responsibility Principle (SRP) for collections, Fail-Fast modification tracking, and legacy collection adapters.

1

Pattern Profile & Canonical UML Architecture

Core GoF Specification
Name: Iterator Pattern (also known as Cursor)
Type: Behavioral Pattern — focuses on how objects communicate and coordinate responsibilities, specifically sequential data traversal.
Policy: "Provide a way to access the elements of an aggregate object sequentially without exposing its underlying representation."
Problem: Collections store elements in diverse representations: arrays, linked lists, hash tables, or trees. If clients directly loop over internal arrays or nodes, they become tightly coupled to internal data structures. If the aggregate itself implements multiple iteration behaviors, it violates the Single Responsibility Principle.
Solution: Delegate traversal responsibility to an external Iterator object. The aggregate implements an Aggregate interface declaring createIterator(). The iterator encapsulates the current position, step increments, and boundary checks.

Minimal Architecture & Clean Code

Custom Iterator Implementation
📦 Clean Custom Array Iterator
< 25 Lines 
public class ArrayIterator<T> implements Iterator<T> {
    private final T[] items;
    private int position = 0;

    public ArrayIterator(T[] items) {
        this.items = items;
    }

    @Override
    public boolean hasNext() {
        return position < items.length && items[position] != null;
    }

    @Override
    public T next() {
        if (!hasNext()) {
            throw new NoSuchElementException("No more elements");
        }
        return items[position++];
    }

    @Override
    public void remove() {
        throw new UnsupportedOperationException("Remove not supported");
    }
}

Single Responsibility & Fail-Fast Traversal

Core Architectural Axioms
AXIOM 1 · SRP Single Responsibility Principle in Collections

A collection class should have only one reason to change: managing its elements and data storage (insertion, deletion, capacity). The responsibility of iterating through the collection must be delegated to a dedicated iterator class. If the collection managed both data and iteration cursors, concurrent traversals would collide.

AXIOM 2 · CONCURRENCY Fail-Fast Mechanics & ConcurrentModificationException

In the Java Collections Framework (e.g. ArrayList, Vector), iterators are fail-fast:

  • The collection maintains an internal modification counter: protected transient int modCount = 0;
  • When an iterator is created, it takes a snapshot: int expectedModCount = modCount;
  • On every call to next(), it checks: if (modCount != expectedModCount) throw new ConcurrentModificationException();
  • Rule: Structural modifications during iteration are only safe if performed through the iterator's own iterator.remove() method (which updates expectedModCount).
AXIOM 3 · ITERATION CONTROL External vs. Internal Iterators
External Iterator (Passive)

The client controls the loop stepping: while (it.hasNext()) { ... it.next(); }. Gives client fine-grained control to break early, step multiple iterators in parallel, or skip elements.

Internal Iterator (Active)

The iterator/aggregate controls the traversal loop itself: collection.forEach(action). The client passes a function/lambda. More concise and easier to parallelize (e.g. Java Parallel Streams).

Question 1: Legacy Vector to Iterator Adapter 6 Points

A legacy library uses a custom vector LegacyVector with methods int size() and Object elementAt(int index). Provide an implementation of java.util.Iterator that adapts this legacy vector to the standard Java Iterator interface!

Model Answer: 
public class LegacyVectorIteratorAdapter implements Iterator<Object> {
    private final LegacyVector vector;
    private int cursor = 0;

    public LegacyVectorIteratorAdapter(LegacyVector vector) {
        if (vector == null) throw new IllegalArgumentException("Vector cannot be null");
        this.vector = vector;
    }

    @Override
    public boolean hasNext() {
        return cursor < vector.size();
    }

    @Override
    public Object next() {
        if (!hasNext()) {
            throw new NoSuchElementException("Cursor exceeded vector bounds");
        }
        return vector.elementAt(cursor++);
    }

    @Override
    public void remove() {
        throw new UnsupportedOperationException("LegacyVector is read-only");
    }
}

• Combines the Iterator Pattern (providing standard sequential traversal) with the Adapter Pattern (translating size()/elementAt() into hasNext()/next()).

Question 2: Why Does Direct Collection Modification Cause Exceptions? 4 Points

Why does calling list.remove(item) inside a standard Java for (String item : list) loop trigger a ConcurrentModificationException, and how is it resolved?

Model Answer:
  1. Cause: The enhanced for-loop compiles down to an Iterator. Calling list.remove(item) modifies the underlying collection directly, incrementing its internal modCount. On the subsequent iteration, iterator.next() detects that modCount != expectedModCount and immediately throws ConcurrentModificationException to prevent corrupt iteration state.
  2. Resolution: Explicitly use the iterator's own removal method: 
    Iterator<String> it = list.iterator();
while (it.hasNext()) {
    String item = it.next();
    if (condition(item)) {
        it.remove(); // Safely updates both list and expectedModCount!
    }
}
