1

Christopher Alexander’s Epistemology

The Three-Part Rule & System of Forces
Alexander's Canonical Definition: "Each pattern is a three-part rule, which expresses a relation between a certain context, a problem (a system of conflicting forces), and a solution." — Christopher Alexander (The Timeless Way of Building, 1979).
The Three-Part Rule Elements: • Context: The recurring situation or environment in which the engineering problem arises.
• Problem (System of Forces): The conflicting goals, constraints, and requirements acting upon the system (e.g. performance vs flexibility, memory vs speed). A pattern exists to resolve this conflict.
• Solution: A concrete spatial, structural, or behavioral configuration of components that balances the forces into equilibrium.
Pattern Catalog vs. Pattern Language: • Pattern Catalog: A structured collection of isolated, independent solutions indexed by intent (e.g. the 23 Gang of Four patterns).
• Pattern Language: A network of interconnected patterns where applying one pattern resolves certain forces but introduces a new context, prompting the application of subsequent patterns.

The 3 POSA Abstraction Levels

Buschmann et al. Classification
POSA TAXONOMY Architectural Patterns vs. Design Patterns vs. Idioms
1. Architectural Patterns

Fundamental macro-level structure of software systems. Dictates system decomposition, responsibilities of sub-systems, and rules for inter-subsystem coordination.

Examples: Pipes & Filters, Model-View-Controller (MVC), Blackboard, Microkernel.
2. Design Patterns

Medium-scale architectural building blocks. Refines components or their relationships without dictating the overarching system architecture.

Examples: Strategy, Template Method, Composite, Command, Observer, Factory Method.
3. Idioms

Low-level, programming-language-specific patterns. Demonstrates how to implement specific design aspects using language idioms.

Examples: RAII in C++, Double-Checked Locking in Java, Context Managers (with) in Python.

Peter Norvig’s Functional Critique

Are Patterns Missing Language Features?
CRITICAL THEORY 16 of 23 Patterns Disappear in Dynamic Languages

In 1996, Peter Norvig (Director of Research at Google) published an analysis showing that 16 of the 23 Gang of Four patterns are invisible or radically simplified in dynamic or functional programming languages (such as Lisp, Python, and modern JavaScript):

GoF Pattern Heavy OOP Java/C++ Ceremony Modern Functional Equivalent
Strategy Create Strategy interface + 3 concrete classes Pass first-class function / lambda: sorted(data, key=lambda x: x.price)
Command Create Command interface + concrete invoker objects Closure or zero-argument lambda: action = () -> db.save()
Iterator Create Iterator interface with hasNext(), next(), pointer Native Generators and list comprehensions (yield)
Visitor Double dispatch with accept(Visitor) and visit(Node) Pattern matching on algebraic data types (e.g. Kotlin / Scala / Rust match)

Core Exam Practice & Model Solutions

Direct Question → Answer Format
Question 1: Christopher Alexander’s Definition of a Pattern 5 Points

State Christopher Alexander's definition of a software/architectural pattern and explain each component of the Three-Part Rule!

Model Answer:

Christopher Alexander defines a pattern as: "A three-part rule, which expresses a relation between a certain context, a problem (a system of conflicting forces), and a solution."

  1. Context: Describes the recurring situation or state of the system where the problem occurs. It bounds the applicability of the pattern.
  2. Problem (System of Conflicting Forces): Outlines the non-trivial goals and constraints in conflict (e.g., runtime flexibility vs. compile-time safety, memory efficiency vs. code clarity).
  3. Solution: Specifies a configuration of collaborating participants, relationships, and responsibilities that resolves the conflicting forces and balances them into equilibrium.
Question 2: The Three POSA Abstraction Levels 6 Points

Distinguish between Architectural Patterns, Design Patterns, and Idioms according to POSA (Buschmann et al.) and provide one concrete example for each!

Model Answer:
  1. Architectural Pattern (Macro-Level):
    • Scope: Fundamental structural organization schema for the entire software system. Defines high-level subsystems, their interfaces, and global communication policies.
    • Example: Pipes & Filters (or Model-View-Controller).
  2. Design Pattern (Meso-Level):
    • Scope: Medium-scale refinement of subsystems or component collaborations. Does not alter global system architecture. Independent of programming language specifics.
    • Example: Strategy Pattern (or Composite Pattern).
  3. Idiom (Micro-Level):
    • Scope: Low-level pattern specific to a particular programming language or runtime, solving language-specific coding challenges.
    • Example: RAII in C++ or Double-Checked Locking in Java.
Question 3: Peter Norvig’s Critique of Gang of Four Patterns 4 Points

What is the central thesis of Peter Norvig’s critique of Gang of Four design patterns, and why do patterns like Strategy or Command disappear in modern languages?

Model Answer:

Norvig's central thesis is that many design patterns are workarounds for deficiencies in programming language expressiveness. When a language lacks higher-order features, developers must manually build boilerplate class hierarchies to achieve simple abstraction:

  • In classic C++ or Java 1.4, passing an algorithm or behavior required defining an interface and a concrete class (the Strategy or Command pattern).
  • In languages with first-class functions and closures (e.g. Python, JavaScript, Java 8+ lambdas), functions can be passed directly as arguments or assigned to variables. The entire Strategy and Command class hierarchy collapses into a single function parameter or lambda expression.
