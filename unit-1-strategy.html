Unit 1 · Foundation & Behavioral Patterns

Introduction & The Strategy Pattern

“To rely on rustics and not prepare is the greatest of crimes; to be prepared beforehand for any contingency is the greatest of Virtues.” — Sun Tzu

Software architecture begins with anticipating change. Instead of letting changes break existing client code, patterns isolate what varies and decouple behavior from implementation.

1.1 Lecture Motivation: The SimUDuck Evolution

Why naive inheritance fails when requirements inevitably change.

1

The Initial State: SimUDuck Simulator

We start with a clean superclass Duck with quack(), swim(), and an abstract display(). Subclasses like MallardDuck and RedheadDuck inherit cleanly.

2

The New Requirement: Ducks Must Fly!

Naive Solution: Add a fly() method directly to the superclass Duck. All subclasses inherit it automatically.

3

The Catastrophic Bug: Rubber Ducks Flying!

In the simulation, RubberDuck instances suddenly sprout wings and fly across the screen! Inanimate decoy ducks and rubber ducks now possess behaviors they should never have.

4

The Second Naive Fix: Override with No-Ops

Override fly() in RubberDuck to do nothing: fly() { /* do nothing */ }. But as 50 new duck types are added, maintenance collapses and code duplication explodes (violating the DRY Principle).

✓

The Architectural Breakthrough: Delegate, Don't Inherit!

Take what varies and encapsulate it: Separate FlyBehavior and QuackBehavior into interfaces. A Duck has-a behavior rather than is-a behavior. Behavior can now even be swapped dynamically at runtime!

💡 Lesson 1: Program to Interfaces

Clients should depend on abstractions (interfaces or abstract base classes), not concrete implementations.

💡 Lesson 2: Favor Composition Over Inheritance

Composition lets you change behavior dynamically at runtime and prevents rigid class hierarchy lock-in.

1.3 The GoF Strategy Pattern

The formal definition, intent, problem, and solution structure.

Pattern Passport

Also Known As: Policy

GoF Intent: Define a family of algorithms, encapsulate each one, and make them interchangeable. Strategy lets the algorithm vary independently from clients that use it.

Problem: You must cope with anticipated and unanticipated changes to algorithms—even dynamically at runtime—without modifying or breaking existing client classes.

Solution: Encapsulate algorithms into separate strategy classes implementing a common interface. The client context holds a reference to the strategy interface and delegates execution.

1.4 Dependencies, Real-World Examples & Principles

Dependencies Created:

  • Context depends on the abstraction Strategy (Loose Coupling).
  • Context has zero dependency on concrete strategy classes.
  • ConcreteStrategies implement Strategy and do not necessarily know about the Context (unless passed as a parameter).

Real-World Examples in Production:

🔌 Hardware Drivers

OS kernel treats display, storage, and networking through generic driver interfaces, swapping concrete implementations per vendor.

🚗 Route Navigation

Travel app computes directions: walking, public transit, driving, or cycling. The client route remains unchanged while algorithm switches.

⚙️ UNIX qsort / Java Comparator

qsort(..., cmp) accepts a comparator function pointer. In Java, Collections.sort(list, comparator) is the canonical Strategy pattern.

Architectural Links to Future Units:
  • Open-Closed Principle (OCP · Unit 6): Context is closed for modification but open for extension by writing new strategy classes.
  • Liskov Substitution Principle (LSP · Unit 6): Any concrete strategy must seamlessly fulfill the interface contract without unexpected side effects.
  • Template Method (Unit 2): Strategy alters an entire algorithm via delegation, whereas Template Method alters individual steps via inheritance.

1.6 Time to Code! Interactive Sorter Implementation

A clean, production-grade implementation of the Sorter Strategy in modern Java / Python.

SortContext.java Java 17+ 
// 1. The Strategy Abstraction
@FunctionalInterface
public interface SortStrategy<T extends Comparable<T>> {
    void sort(List<T> dataset);
}

// 2. Concrete Strategy: QuickSort
public class QuickSortStrategy<T extends Comparable<T>> implements SortStrategy<T> {
    @Override
    public void sort(List<T> dataset) {
        System.out.println("Executing O(N log N) in-place QuickSort...");
        Collections.sort(dataset);
    }
}

// 3. Concrete Strategy: Custom InsertionSort for small arrays
public class InsertionSortStrategy<T extends Comparable<T>> implements SortStrategy<T> {
    @Override
    public void sort(List<T> dataset) {
        System.out.println("Executing O(N^2) InsertionSort (low overhead for small lists)...");
        // Insertion sort implementation...
    }
}

// 4. The Context
public class DatasetSorter<T extends Comparable<T>> {
    private SortStrategy<T> strategy;

    public DatasetSorter(SortStrategy<T> strategy) {
        this.strategy = strategy;
    }

    // Dynamic runtime strategy switching!
    public void setStrategy(SortStrategy<T> strategy) {
        this.strategy = strategy;
    }

    public void executeSort(List<T> data) {
        strategy.sort(data);
    }
}

1.7 Exercise: Questions for Self-Study (Exam Practice)

Official questions assigned by Prof. Dr. Jörg Schäfer with comprehensive verified answers.

Self-Study Q1 What happens when a system has an explosion of Strategy objects? Is there some way to better manage these strategies?

The Problem (Memory & Object Overhead):

If each Context instance creates its own new Strategy instance, or if there are hundreds of fine-grained strategies, memory consumption and garbage collection pressure increase significantly.

The Solutions:

  1. Stateless Strategies via Flyweight Pattern: If a concrete Strategy has no internal mutable state (it only takes parameters and operates on the passed Context data), it can be made a stateless singleton and shared across thousands of Contexts simultaneously using the Flyweight pattern.
  2. Factory Method / Abstract Factory (Unit 8): Encapsulate Strategy instantiation within a Factory so client code doesn't manage lifecycle manually.
  3. Lambdas & Method References (Modern Languages): In modern Java/Python/TypeScript, functional interfaces allow passing pure functions or method references directly (e.g. data.sort(Integer::compareTo)) without allocating heavy class instances.
Self-Study Q2 In the implementation section of GoF, the authors describe two ways a Strategy gets information: (A) data passed as arguments, or (B) Context reference passed to Strategy. What happens if the data required by Strategy is NOT available on the Context's public interface? How can you remedy this?

The Dilemma:

If the Strategy requires internal data that Context does not expose publicly, naively adding public getters violates Encapsulation / Information Hiding, exposing Context internals to the outside world.

Architectural Remedies:

  1. Pass a Parameter Object / Data Transfer Object (DTO): Have Context bundle exactly the required calculation parameters into a specialized DTO and pass it to algorithm(DataBundle data).
  2. Narrow Interface (Interface Segregation Principle · Unit 6): Define a narrow, specialized interface (e.g. ContextInspectable) with only the getters the Strategy needs. Context implements this interface, and passes this typed to that narrow interface. Outside clients remain blind to these internal methods.
  3. Package-Private or Friend Access (Language-Specific): In Java, place Context and concrete Strategies in the same package using package-private visibility. In C++, designate the Strategy as a friend class.
