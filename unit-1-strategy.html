1.1

Executive Architectural Foundations

The core principles every senior engineer and exam candidate must master before writing a single line of design pattern code.

GOLDEN RULE 1

Encapsulate What Varies

Identify the aspects of your application that are subject to volatility and requirement changes, and separate them from the parts that remain invariant. Never let shifting algorithms pollute stable domain clients.

GOLDEN RULE 2

Favor Composition Over Inheritance

A "HAS-A" relationship provides order-of-magnitude greater flexibility than an "IS-A" relationship. Composition encapsulates algorithm families into interchangeable objects, unlocking runtime hot-swapping.

GOLDEN RULE 3

Program to Interfaces, Not Classes

Clients must depend upon abstract contracts (Java interface or abstract base type), never on concrete implementation classes. This fulfills the Dependency Inversion Principle (DIP · Unit 6).

1.2

The Blackboard Progression (Why Strategy Exists)

Based on the official curriculum script by Prof. Dr. Jörg Schäfer. This section traces the architectural failure of naive inheritance and the rigorous step-by-step deduction of the Strategy pattern.

1

Phase 1: The Initial Clean Inheritance Tree

Clean Baseline Taxonomy

We model a domain simulator with standard object-oriented inheritance: an abstract superclass Duck declaring shared behavior (swim(), quack()) and an abstract display hook. Subclasses inherit shared logic and supply their visual representations.

Figure 1.1: Standard textbook inheritance. Stable only so long as behavioral requirements never mutate.

2

Phase 2: The New Requirement & The Superclass Inheritance Trap

Naive Engineering Trap

Requirement Change: Product management demands that ducks in the simulation must fly to stay competitive.

The Naive Junior Reflex: "We have an object-oriented inheritance tree. Let's add a single fly() method to Duck superclass! All subclasses inherit it instantly with zero boilerplate."

public abstract class Duck { public void quack() { System.out.println("Quack"); } public void swim() { System.out.println("Swimming"); } + public void fly() { System.out.println("Flying high!"); } // INADVERTENT SUPERCLASS MUTATION public abstract void display(); }

⚠️ Hidden Trap: In class inheritance, changing the superclass automatically forces the behavior upon every single descendant class, regardless of whether it makes semantic sense.

3

Phase 3: The Production Outage (The Flying Rubber Duck Bug)

CRITICAL PRODUCTION REGRESSION

During the executive demo, chaos unfolds: RubberDuck instances suddenly sprout wings and fly across the screen! Inanimate wooden DecoyDuck instances also fly!

💥 The Architectural Root Cause:

A localized modification to a superclass silently broke the operational invariant of subclasses that were never intended to fly. In enterprise systems, this manifests as security permissions or financial calculations leaking across unrelated modules.

4

Phase 4: The Flawed Band-Aid (No-op Overrides & LSP Violation)

Antipattern: Empty Overrides

The developers attempt a quick patch: "We will override fly() in non-flying subclasses with an empty body:"

public class RubberDuck extends Duck { - // inherited fly() from Duck superclass + @Override public void fly() { /* Do nothing - cannot fly! */ } // NO-OP BAND-AID }
1. Maintenance Explosion

When 50 new duck variants are created, developers must manually remember to override dozens of irrelevant methods.

2. Silent Regressions

If a new engineer forgets the no-op override in a newly added class, the bug instantly reappears in production.

3. LSP Violation

Subclasses advertise a contract (fly()) they cannot genuinely satisfy, violating formal behavioral subtyping.

5

Phase 5: The Architectural Breakthrough (Delegation over Inheritance)

The Strategy Pattern

The Epiphany: Pull the varying behaviors completely out of the Duck superclass. Encapsulate them inside dedicated Strategy interfaces (FlyBehavior and QuackBehavior). The Duck superclass holds interface references and delegates execution at runtime.

Figure 1.2: The Strategy Pattern architecture. Context holds an interface reference; algorithms vary independently without touching Duck.

⚡ Dynamic at Runtime
The algorithm must change on the fly via setters or configuration without restarting/reallocating.
🔒 Static at Compile-Time
The algorithm variation can be fixed when the subclass is compiled/instantiated.
1.5

Formal Gang of Four (GoF) Pattern Specification

The formal academic blueprint from Gamma, Helm, Johnson, and Vlissides [GHJV95].

Pattern Name: Strategy (also known as Policy)
Classification: Behavioral Pattern (Object Scope)
GoF Intent: “Define a family of algorithms, encapsulate each one, and make them interchangeable. Strategy lets the algorithm vary independently from clients that use it.”
Problem Addressed: You must handle anticipated and unanticipated changes to business algorithms—even dynamically during runtime—without modifying or re-compiling existing client classes.
Solution Architecture: Use object delegation instead of class inheritance. Encapsulate algorithms into separate strategy classes implementing a common interface. The client context holds an interface reference.

Formal Structural Architecture (Vector UML)

Figure 1.3: Strategy Pattern Structural Specification [GHJV95]
GoF Standard

Participants & Responsibilities

  • Context: Maintained with a reference to a Strategy object. Configured with a ConcreteStrategy instance. May define an interface that lets Strategy access its data.
  • Strategy (Interface): Declares an interface common to all supported algorithms. Context uses this interface to call the algorithm defined by a ConcreteStrategy.
  • ConcreteStrategy (A, B, C): Implements the algorithm using the Strategy interface. Encapsulates all data structures, private helpers, and optimizations required.

Real-World Industry Case Studies

Where the Strategy pattern powers production operating systems, payment rails, and standard libraries.

1. Operating System Kernels & Device Drivers

Operating system kernels treat storage, networking, and graphics cards via generic device driver interfaces. Swapping an NVMe SSD for an HDD requires zero changes to the file read/write client kernel logic.

DatasetSorter.java Java 21 Generics & Functional Strategy 
package de.frauas.posa.unit1;

import java.util.Collections;
import java.util.List;
import java.util.Objects;

@FunctionalInterface
public interface SortStrategy<T extends Comparable<T>> {
    void sort(List<T> items);
}

public final class QuickSortStrategy<T extends Comparable<T>> implements SortStrategy<T> {
    @Override
    public void sort(List<T> items) {
        if (items.size() <= 1) return;
        quickSort(items, 0, items.size() - 1);
    }

    private void quickSort(List<T> list, int low, int high) {
        if (low < high) {
            int p = partition(list, low, high);
            quickSort(list, low, p - 1);
            quickSort(list, p + 1, high);
        }
    }

    private int partition(List<T> list, int low, int high) {
        T pivot = list.get(high);
        int i = low - 1;
        for (int j = low; j < high; j++) {
            if (list.get(j).compareTo(pivot) <= 0) {
                i++;
                Collections.swap(list, i, j);
            }
        }
        Collections.swap(list, i + 1, high);
        return i + 1;
    }
}

public class DatasetSorter<T extends Comparable<T>> {
    private SortStrategy<T> strategy;

    public DatasetSorter(SortStrategy<T> strategy) {
        this.strategy = Objects.requireNonNull(strategy, "Strategy must not be null");
    }

    // Dynamic runtime hot-swap without subclassing
    public void setStrategy(SortStrategy<T> strategy) {
        this.strategy = Objects.requireNonNull(strategy, "Strategy must not be null");
    }

    public void executeSort(List<T> dataset) {
        strategy.sort(dataset);
    }
}

package de.frauas.posa.unit1;

import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.DisplayName;
import java.util.ArrayList;
import java.util.List;
import static org.junit.jupiter.api.Assertions.*;

public class DatasetSorterTest {

    @Test
    @DisplayName("Should sort numbers using QuickSort strategy")
    void testQuickSortStrategy() {
        DatasetSorter<Integer> sorter = new DatasetSorter<>(new QuickSortStrategy<>());
        List<Integer> numbers = new ArrayList<>(List.of(9, 3, 7, 1, 5));

        sorter.executeSort(numbers);
        assertEquals(List.of(1, 3, 5, 7, 9), numbers);
    }

    @Test
    @DisplayName("Should hot-swap strategy dynamically at runtime")
    void testRuntimeHotSwap() {
        DatasetSorter<String> sorter = new DatasetSorter<>((list) -> list.sort(null));
        List<String> words = new ArrayList<>(List.of("charlie", "alpha", "bravo"));

        sorter.executeSort(words);
        assertEquals(List.of("alpha", "bravo", "charlie"), words);

        // Hot swap to reverse ordering
        sorter.setStrategy((list) -> list.sort(Collections.reverseOrder()));
        sorter.executeSort(words);
        assertEquals(List.of("charlie", "bravo", "alpha"), words);
    }
}

Exercise: Questions for Self-Study (Official Syllabus)

Verbatim self-study questions assigned by Prof. Dr. Jörg Schäfer with complete exam-grade solutions.

🎯 Self-Study Question 1: Strategy Object Explosion

"What happens when a system has an explosion of Strategy objects? Is there some way to better manage these strategies?"

The Architectural Problem:

If every single Context instance creates and retains its own independent Strategy object, a system managing millions of contexts will allocate millions of small algorithmic objects in heap memory. This causes memory bloat, high cache-miss rates, and severe Garbage Collection latency spikes.

The 3 Exam-Grade Architectural Solutions:

  1. Stateless Strategies via the Flyweight Pattern (Unit 5 & GoF): If a concrete Strategy does not maintain internal mutable state (meaning it only operates on data passed via method parameters), it can be implemented as a stateless singleton. A single Flyweight strategy instance in memory can be shared concurrently across millions of Context objects.
  2. First-Class Functions and Lambdas (Modern Languages): In modern Java (Java 8+) and Python, strategies can be represented as pure function references (e.g. Integer::compareTo or lambdas). Functional interfaces eliminate the need to instantiate heavy class metadata structures.
  3. Strategy Factory (Unit 8): Encapsulate strategy creation inside a centralized Factory. The factory pools or caches pre-created strategy instances, preventing uncontrolled object allocation.
🎯 Self-Study Question 2: Context Data Access Coupling Dilemma

"In the implementation section of the strategy pattern in [GHJV95], the authors describe two ways in which a strategy can get the information it needs: (A) data passed as arguments, or (B) context passed as a reference. But what happens if the data required by the strategy is private in Context?"

The Architectural Dilemma:

If Strategy receives this (a Context reference) to pull private internal data, Context must expose public getter methods. Exposing getters breaks encapsulation and leaks implementation details to all external callers.

The 3 Exam-Grade Solutions:

  1. Segregated Read-Only Interface (Interface Segregation Principle · Unit 6): Define an interface (e.g., ContextDataView) exposing only getters. Have Context implement this interface. Pass ContextDataView rather than the concrete Context to Strategy.
  2. Data Transfer Object (DTO) / Parameter Object: Context extracts the required internal data into an immutable DTO or record and passes it as a parameter: strategy.execute(context.toSnapshot()).
  3. Package-Private Visibility (Language-Level Solution): In Java, declare the sensitive accessor methods with package-private access, placing Context and concrete Strategies in the same internal package.
