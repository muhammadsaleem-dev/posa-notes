Unit 1: The Strategy Pattern (Policy)

How to anticipate software change, isolate volatile algorithms from stable client contexts, and replace brittle inheritance trees with dynamic runtime object composition.

“To rely on rustics and not prepare is the greatest of crimes; to be prepared beforehand for any contingency is the greatest of Virtues.” — Sun Tzu (The Art of War)
1.1

Lecture: Motivation (The Blackboard Progression)

Based on the official curriculum script by Prof. Dr. Jörg Schäfer. This section replicates the 11-step architectural deduction developed on the lecture blackboard.

In object-oriented design, software systems are built to model real-world business domains. However, standard object-oriented textbooks often teach that inheritance is the primary tool for code reuse. In production software engineering, naive inheritance is frequently the single largest source of architectural fragility and regression bugs.

1

Setting the Domain Context: The SimUDuck Simulator

We are tasked with building a water simulation application. We begin with a clean, classic object-oriented inheritance tree: an abstract superclass Duck containing standard shared behaviors like quack(), swim(), and an abstract display() method. Concrete subclasses such as MallardDuck and RedheadDuck inherit these methods and provide their own custom visual representations.

2

3

The Requirement Change & The Naive Engineering Solution

The Change: Marketing demands a new capability to stay ahead of competition: Ducks in the simulation must now fly!

The Naive Junior Engineering Move: "We have an object-oriented inheritance hierarchy. Let's simply add a void fly() method to the superclass Duck! All existing duck subclasses will inherit it automatically with zero extra code."

public abstract class Duck {
    public void quack() { System.out.println("Quack"); }
    public void swim() { System.out.println("Swimming"); }
    public void fly() { System.out.println("Flying high!"); } // Added to base class
    public abstract void display();
}

💥 Step 5: The Catastrophic Production Bug (Rubber Ducks Flying!)

During the executive release demo, disaster strikes: RubberDuck instances suddenly sprout wings and fly across the display screen! Inanimate wooden DecoyDuck instances also fly!

The Architectural Cause: What was thought to be a localized addition to the superclass inadvertently mutated the contracts and behaviors of every single subclass in the system, including those that should never have possessed that capability.

6

The Second Naive "Band-Aid": Overriding with Empty No-Ops

The engineering team attempts a quick fix: "We will override fly() in RubberDuck and DecoyDuck to do nothing:"

public class RubberDuck extends Duck {
    @Override
    public void fly() { /* Do nothing - cannot fly! */ }
}

Why this breaks production architecture: As 40 new duck types are added (Wooden ducks, decoy ducks, drone ducks, decoy callers), developers must manually track, inspect, and override dozens of methods across every single class. If a new developer forgets to override fly() in a future subclass, the bug silently reappears in production.

Furthermore, subclasses that cannot fly still inherit the fly() method, creating misleading APIs and violating the Liskov Substitution Principle (LSP · Unit 6).

💡 Steps 8–11: The Architectural Breakthrough (Delegation over Inheritance)

CHANGE is the driving force here. When requirements change, standard class inheritance binds behavior at compile time and creates rigid, unbreakable coupling between parent and child.

The Solution: Take the behaviors that vary (flying and quacking) and pull them completely out of the Duck class. Encapsulate them inside dedicated interfaces (FlyBehavior and QuackBehavior). The Duck superclass holds references to these interfaces and delegates execution at runtime.

1.2

The Foundational Object-Oriented Principles

The two universal design principles derived from the SimUDuck analysis.

Principle 1: Program to an Interface

Clients must depend on abstract supertypes (interfaces or abstract base classes), not on concrete classes. This ensures client code is decoupled from the underlying algorithms, enabling transparent polymorphism.

Principle 2: Favor Composition Over Inheritance

A "HAS-A" relationship is vastly more flexible than an "IS-A" relationship. Composition lets you encapsulate a family of algorithms into separate objects and change an object's behavior dynamically at runtime via setter methods.

1.3

Formal Gang of Four (GoF) Pattern Specification

The formal academic blueprint from Gamma, Helm, Johnson, and Vlissides [GHJV95].

Pattern Name: Strategy (also known as Policy)
GoF Intent: “Define a family of algorithms, encapsulate each one, and make them interchangeable. Strategy lets the algorithm vary independently from clients that use it.”
Problem: You must cope with anticipated and unanticipated changes to algorithms—even dynamically at runtime—without modifying or breaking existing client classes.
Solution: Use object delegation instead of class inheritance. Encapsulate algorithms into separate strategy classes implementing a common interface. The client context holds an interface reference.

Exercise: What Are the Dependencies Created?

A core examination topic: mapping directional coupling between Context and Strategy.

Directional Coupling Analysis:

  • Context depends strictly on the Strategy Abstraction: The Context holds a reference to the interface Strategy. It has zero compile-time dependency on any concrete implementation (e.g. ConcreteStrategyA or ConcreteStrategyB). This satisfies the Dependency Inversion Principle (DIP · Unit 6).
  • Concrete Strategies depend on the Strategy Interface: Each concrete class implements the interface contract. Concrete strategies do not depend on the Context unless the context passes a reference to itself as an algorithm parameter.
  • Client Configures Context: The outside client instantiates a concrete strategy and passes it into the context's constructor or setter. Once injected, client and context interact solely through the stable context interface.
Architectural Links to Future Units (Prof. Schäfer Notes):
  • Open-Closed Principle (OCP · Unit 6): Context is closed for modification but open for extension by writing new strategy classes.
  • Liskov Substitution Principle (LSP · Unit 6): Any concrete strategy must seamlessly fulfill the interface contract without altering client correctness.
  • Template Method Pattern (Unit 2): Strategy alters an entire algorithm via delegation, whereas Template Method alters individual steps via class inheritance.

1. Hardware Drivers & OS Kernels

Operating system kernels treat storage, networking, and graphics cards via generic device driver interfaces. Swapping an NVMe SSD for an HDD requires zero changes to the file read/write client kernel logic.

2. UNIX qsort & Java Comparator

Exercise: Time to Code! (Flexible Sorter Engine)

Implementing a high-throughput, interchangeable list sorter following Prof. Schäfer's exercise specification.

Figure 1.2: Application of Strategy Pattern to Sorter
DatasetSorter.java Java 21 Generics 
@FunctionalInterface
public interface SortStrategy<T extends Comparable<T>> {
    void sort(List<T> items);
}

public final class QuickSortStrategy<T extends Comparable<T>> implements SortStrategy<T> {
    @Override
    public void sort(List<T> items) {
        if (items.size() <= 1) return;
        quickSort(items, 0, items.size() - 1);
    }
    private void quickSort(List<T> list, int low, int high) {
        if (low < high) {
            int p = partition(list, low, high);
            quickSort(list, low, p - 1);
            quickSort(list, p + 1, high);
        }
    }
    private int partition(List<T> list, int low, int high) {
        T pivot = list.get(high);
        int i = low - 1;
        for (int j = low; j < high; j++) {
            if (list.get(j).compareTo(pivot) <= 0) {
                i++;
                Collections.swap(list, i, j);
            }
        }
        Collections.swap(list, i + 1, high);
        return i + 1;
    }
}

public class DatasetSorter<T extends Comparable<T>> {
    private SortStrategy<T> strategy;

    public DatasetSorter(SortStrategy<T> strategy) {
        this.strategy = Objects.requireNonNull(strategy);
    }

    // Dynamic runtime hot-swap
    public void setStrategy(SortStrategy<T> strategy) {
        this.strategy = Objects.requireNonNull(strategy);
    }

    public void executeSort(List<T> dataset) {
        strategy.sort(dataset);
    }
}

Exercise: Questions for Self-Study (Official Exam Questions)

Verbatim self-study questions assigned by Prof. Dr. Jörg Schäfer with complete exam-grade solutions.

🎯 Self-Study Question 1: Strategy Object Explosion

"What happens when a system has an explosion of Strategy objects? Is there some way to better manage these strategies?"

The Architectural Problem:

If every single Context instance creates and retains its own independent Strategy object, a system managing millions of contexts will allocate millions of small algorithmic objects in heap memory. This causes memory bloat, high cache-miss rates, and severe Garbage Collection latency spikes.

The 3 Exam-Grade Architectural Solutions:

  1. Stateless Strategies via the Flyweight Pattern (Unit 5 & GoF): If a concrete Strategy does not maintain internal mutable state (meaning it only operates on data passed via method parameters), it can be implemented as a stateless singleton. A single Flyweight strategy instance in memory can be shared concurrently across millions of Context objects.
  2. First-Class Functions and Lambdas (Modern Languages): In modern Java (Java 8+) and Python, strategies can be represented as pure function references (e.g. Integer::compareTo or lambdas). Functional interfaces eliminate the need to instantiate heavy class metadata structures.
  3. Strategy Factory (Unit 8): Encapsulate strategy creation inside a centralized Factory. The factory pools or caches pre-created strategy instances, preventing uncontrolled object allocation.
🎯 Self-Study Question 2: Context Data Access Coupling Dilemma

"In the implementation section of the strategy pattern in [GHJV95], the authors describe two ways in which a strategy can get the information it needs: (A) data passed as arguments, or (B) context passed as a reference. But what happens if the data required by the strategy is NOT available from the context’s public interface? How could you remedy this potential problem?"

The Architectural Dilemma:

If the Strategy requires internal data that Context does not expose publicly, naively adding public getters to Context destroys Information Hiding (Encapsulation). Outside clients would now be able to see and depend on internal implementation details that should have remained private.

The 3 Architectural Remedies:

  1. Narrow Specialized Interface (Interface Segregation Principle · Unit 6): Define a narrow, private interface (e.g. ContextInspectable) declaring only the specific getter methods the Strategy requires. Context implements this interface. When delegating, Context passes this typed strictly as ContextInspectable. Outside clients remain blind to these internal methods because they hold a reference to Context, not the narrow interface.
  2. Data Transfer Object (DTO) / Parameter Object: Context extracts and bundles only the required data fields into an immutable parameter object or DTO, and passes it directly to strategy.execute(dataBundle). Context internals remain fully private.
  3. Package-Private Visibility (Language-Level Solution): In Java, declare the sensitive accessor methods with package-private (default) access, and place Context and concrete Strategies in the same internal package. In C++, designate the Strategy as a friend class of Context.
