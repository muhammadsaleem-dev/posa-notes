Strategy Pattern (Policy)

Master dynamic runtime algorithm selection, delegation over inheritance (has-a over is-a), request delegation, and functional comparators. Directly synthesized from Prof. Dr. Jörg Schäfer's lecture notes and authentic exam sheets.

1

Pattern Profile & Canonical UML Architecture

Core GoF Specification
Name: Strategy (also known as Policy Pattern)
Type: Behavioral pattern which focuses on how objects interact and communicate with each other. It specifically enables selecting an algorithm at runtime by encapsulating each algorithm within a separate class, allowing them to be interchangeable.
Policy: Define a family of algorithms, encapsulate each one, and make them interchangeable. Strategy lets the algorithm vary independently from clients that use it.
Problem: You want to be able to vary the behavior (algorithms) of objects — even at runtime! You must cope with anticipated and unanticipated changes to algorithms and new algorithms while avoiding changing code and/or breaking existing client code.
Solution: Use delegation instead of inheritance.
• Inheritance: Creates an rigid "is-a" relationship. In deep hierarchies, extending base class behavior causes tight coupling and code duplication.
• Delegation: Creates a flexible "has-a" relationship. An object handles a request by passing it to another object (the delegate) that knows how to perform the task.
Real-World Examples from Notes: Hardware drivers, TV decoder cards, getting to the airport (car, public transport, taxi), cooking recipes, and C UNIX qsort() function pointers.

Head First: The SimUDuck Evolution

Textbook Problem & Annotated Code
📖 Head First: Duck Simulator (Strategy Pattern) Head First Chapter 1
Collapse Expand

In “Head First Design Patterns,” Chapter 1 introduces the Strategy Pattern through the famous SimUDuck simulation game. The evolution illustrates why inheritance fails when behaviors vary across subtypes:

The 5-Step Architectural Dilemma
  1. The Innocent Superclass: The standard Duck superclass defined quack(), swim(), and an abstract display().
  2. The Feature Request: Management requested that ducks should also fly. Adding fly() to the Duck superclass immediately gave flight to all ducks.
  3. The Production Bug: In production, Rubber Ducks and Decoy Ducks started flying across the screen!
  4. The Failed Band-Aid (No-op Overrides): Overriding fly() in RubberDuck to do nothing ({}) violated the Liskov Substitution Principle (LSP), duplicated code across every non-flying duck, and made runtime changes impossible.
  5. The Strategy Solution: Pull flying and quacking completely out of the Duck class! Encapsulate them into families of interchangeable behavior interfaces (FlyBehavior and QuackBehavior) and delegate to them.

By delegating to interfaces, introducing new flying behaviors (such as a rocket-powered duck: FlyRocketPowered) requires zero changes to the existing Duck hierarchy!

💻 1. Minimal Strategy Implementation (from Prof. Schäfer's Notes) StrategyPatternDemo.java 
// 1. The Strategy Interface: declares common contract for all algorithms
interface Strategy {
    void executeAlgorithm();
}

// 2. Concrete Strategies: encapsulate specific algorithm variants
class ConcreteStrategyA implements Strategy {
    @Override
    public void executeAlgorithm() {
        System.out.println("Executing Algorithm A");
    }
}

class ConcreteStrategyB implements Strategy {
    @Override
    public void executeAlgorithm() {
        System.out.println("Executing Algorithm B");
    }
}

class ConcreteStrategyC implements Strategy {
    @Override
    public void executeAlgorithm() {
        System.out.println("Executing Algorithm C");
    }
}

// 3. The Context: maintains a reference to Strategy and delegates work to it
class Context {
    private Strategy strategy; // Delegation: has-a relationship

    public Context(Strategy strategy) {
        this.strategy = strategy;
    }

    // Dynamic runtime algorithm switching via setter injection!
    public void setStrategy(Strategy strategy) {
        this.strategy = strategy;
    }

    public void executeStrategy() {
        strategy.executeAlgorithm(); // Invokes delegated strategy
    }
}

// 4. Client Demo: demonstrates swapping algorithms dynamically at runtime
public class StrategyPatternDemo {
    public static void main(String[] args) {
        Context context = new Context(new ConcreteStrategyA());
        context.executeStrategy(); // Output: Executing Algorithm A

        // Change strategy to ConcreteStrategyB dynamically at runtime!
        context.setStrategy(new ConcreteStrategyB());
        context.executeStrategy(); // Output: Executing Algorithm B

        // Change strategy to ConcreteStrategyC
        context.setStrategy(new ConcreteStrategyC());
        context.executeStrategy(); // Output: Executing Algorithm C
    }
}
🦆 2. Head First SimUDuck Code (Encapsulated Behavior Interfaces) DuckSimulator.java 
// Behavior Interfaces encapsulate varying actions
public interface FlyBehavior {
    void fly();
}
public interface QuackBehavior {
    void quack();
}

// Concrete Fly Behaviors
public class FlyWithWings implements FlyBehavior {
    public void fly() { System.out.println("I'm flying with wings!"); }
}
public class FlyNoWay implements FlyBehavior {
    public void fly() { System.out.println("I can't fly."); }
}
public class FlyRocketPowered implements FlyBehavior { // Added later with ZERO modification to Duck!
    public void fly() { System.out.println("I'm flying with a rocket!"); }
}

// Concrete Quack Behaviors
public class Quack implements QuackBehavior {
    public void quack() { System.out.println("Quack!"); }
}
public class Squeak implements QuackBehavior {
    public void quack() { System.out.println("Squeak!"); }
}

// Abstract Duck Client uses delegation
public abstract class Duck {
    protected FlyBehavior flyBehavior;     // Delegated strategy
    protected QuackBehavior quackBehavior; // Delegated strategy

    public void performFly() {
        flyBehavior.fly(); // Delegate to strategy object
    }
    public void performQuack() {
        quackBehavior.quack(); // Delegate to strategy object
    }
    // Dynamic runtime behavior swapping:
    public void setFlyBehavior(FlyBehavior fb) {
        this.flyBehavior = fb;
    }
    public void swim() {
        System.out.println("All ducks float, even decoys!");
    }
    public abstract void display();
}

// Concrete Duck: ModelDuck starts unable to fly, then gets rocket powered at runtime
public class ModelDuck extends Duck {
    public ModelDuck() {
        flyBehavior = new FlyNoWay();
        quackBehavior = new Quack();
    }
    public void display() { System.out.println("I'm a model duck"); }
}

Prof. Dr. Jörg Schäfer's 5 Key Architectural Axioms

Directly from POS-exams-notes.pdf
Axiom 1 Recognize the Need for Strategy: Encapsulate What Varies

Identify the aspects of your application that vary and separate them from what stays the same. Hardcoding varying behaviors directly into subclasses causes rigid coupling and code duplication.

Axiom 2 Recognize the Pattern in Existing Code: Eliminate Conditionals

Look for messy if-else or switch blocks that select between different algorithm behaviors. Refactor these conditionals into polymorphic Strategy objects implementing a common interface.

Axiom 3 Understand Change as the Driving Force (OCP Compliance)

When new behaviors are introduced (e.g., FlyRocketPowered), you should not modify the existing Duck class or its subclasses. Simply create a new class implementing the interface — the Open-Closed Principle (OCP) in action.

Axiom 4 Delegation as an Alternative to Inheritance (Composition over Inheritance)

Inheritance creates rigid, compile-time bound "is-a" hierarchies. Delegation creates dynamic "has-a" relationships that allow behavior to be swapped on the fly at runtime.

Axiom 5 Not Only "Things" but Behavior Can Be Encapsulated in Classes

In classic OOP, novice programmers only model physical nouns (Car, Account) as classes. Strategy elevates verbs and algorithms (Flying, Quacking, Sorting) into first-class citizens in your architecture.

Functional Strategy: UNIX qsort() & Python map()

Exercise 01 from POS-exams-notes.pdf

Prof. Schäfer's Exam Question (Exercise 01):
“How does the C function pointer compar in qsort() or Python's map() function represent the Strategy Pattern?”

The Functional Equivalence:
  • C UNIX qsort(void *base, size_t nel, size_t width, int (*compar)(const void *, const void *)):
    The sorting algorithm itself (heapsort or quicksort) is completely decoupled from the comparison logic. Instead of hardcoding ordering rules, the algorithm accepts a function pointer (compar), allowing comparison behavior to be customized at runtime without modifying the sorting algorithm.
  • Python map(function, iterable):
    The map() function represents the Context. It allows dynamic selection of an algorithmic transformation function (f or g) to be applied to a list of values without modifying the map() engine itself.
  • Pattern Criticism Note from Notes (p. 2006):
    In languages with first-class functions and closures (C++, Python, modern Java lambdas), full Strategy class hierarchies are often replaced directly by function pointers or lambda expressions (`(d1, d2) -> Integer.compare(...)`), eliminating boilerplate class definitions.

Authentic Exam Sheet · Question 8 [5 Pts] How does the Strategy Pattern differ from the Template Method Pattern?

Official Model Answer & Grading Rubric (Prof. Dr. Jörg Schäfer Standard):

The difference centers around coupling mechanism, runtime mutability, and algorithm granularity:

  1. Coupling Mechanism:
    • Strategy: Utilizes object composition and delegation. Context holds an interface reference to a Strategy object (has-a relationship).
    • Template Method: Utilizes class inheritance. Subclasses extend an abstract base class (is-a relationship).
  2. Runtime Mutability:
    • Strategy: Entire algorithms can be swapped dynamically at runtime via setter injection (e.g. duck.setFlyBehavior(new FlyRocketPowered())).
    • Template Method: Algorithm variants are bound statically at compile-time via inheritance; changing behavior requires re-instantiating a different subclass.
  3. Algorithm Granularity:
    • Strategy: Encapsulates and swaps the entire algorithm as an atomic unit.
    • Template Method: Freezes the invariant algorithm skeleton in the superclass and allows subclasses to vary only individual steps.
Exam Notes · Exercise 01 [5 Pts] Why does the UNIX qsort() function pointer or Python's map() constitute an implementation of the Strategy Pattern?

Official Model Answer:

In qsort(), the overarching sorting algorithm (Context) is strictly decoupled from the element ordering criteria (Strategy).

  • Algorithmic Decoupling: The comparison logic is passed as a function pointer parameter (int (*compar)(const void *, const void *)) rather than being hardcoded into the sorting engine.
  • Runtime Interchangeability: Callers can switch sorting from ascending to descending, or compare completely different struct payloads, simply by supplying a different function pointer at runtime without recompiling or altering the qsort() implementation.
  • Open-Closed Principle: The sorting engine is closed for modification but open for extension.
