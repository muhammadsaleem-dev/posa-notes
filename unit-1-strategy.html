Universal Architectural Standard Pillar 01

Intent & Motivation Invariants

Every design pattern originates from a recurring production architectural failure. To master a pattern, you must define:

  • ✓ The GoF Intent Statement: Concise, memorizable specification of what behavior is abstracted.
  • ✓ The Failure Mode Eliminated: Identifies whether it kills inheritance bloat, state switchboards, or coupling.
  • ✕ Fatal Exam Error: Describing "what the code does" rather than "why the architectural problem exists".
Unit 1: Strategy Pattern Focus

GoF Intent & The Duck Simulator Failure

"Define a family of algorithms, encapsulate each one, and make them interchangeable. Strategy lets the algorithm vary independently from clients that use it."

DuckInheritanceFailure.java · Failure Mode vs. Solution 
// PROBLEM: Base class inheritance locks all subclasses into default behaviors
abstract class Duck {
    void fly() { System.out.println("Flying!"); } // RubberDuck & DecoyDuck break!
}

// STRATEGY FIX: Encapsulate volatile algorithms into interchangeable contracts
interface FlyBehavior { void fly(); }
class FlyWithWings implements FlyBehavior { public void fly() { /* Flapping wings */ } }
class FlyNoWay implements FlyBehavior { public void fly() { /* Do nothing */ } }
🎯 Prof. Schäfer Exam Criteria: You will be asked "Why can't we simply use class inheritance?" Answer: Inheritance creates compile-time locks, causes subclass explosion ($2^N$ combinations), and forces inappropriate default implementations onto subclasses.
Universal Architectural Standard Pillar 02

Structural Participants & Single Responsibility

Patterns divide responsibilities across distinct structural roles. You must isolate who holds state, who delegates, and who executes:

  • ✓ Context: Maintains the domain chassis and holds a reference to the abstract strategy interface.
  • ✓ Strategy Interface: Declares the pure signature contract common to all algorithmic variants.
  • ✓ Concrete Strategies: Implements the concrete algorithm variant without leaking details to Context.
  • ✓ Client: Selects and passes the desired Strategy instance into the Context.
Unit 1: Strategy Pattern Focus

Duck Simulator Participants

  • ✓ Context: Duck (abstract base chassis holding flyBehavior and quackBehavior).
  • ✓ Strategy Interface: FlyBehavior (declares void fly()).
  • ✓ Concrete Strategies: FlyWithWings, FlyNoWay, FlyRocketPowered.
  • ✓ Client: MiniDuckSimulator (wires initial strategy into Duck chassis).
🎯 Exam Trap: Never let a ConcreteStrategy inherit from the Context! The relationship is strictly composition: Context HAS-A Strategy.
Universal Architectural Standard Pillar 03

Formal UML 2.5 Diagram Syntax

Drawing diagrams accurately is where students routinely drop 5 to 10 points on the exam. UML connectors carry rigorous legal semantic meaning:

  • ✓ Directed Association / Aggregation (──>): Points from Context to Strategy interface with multiplicity 1.
  • ✓ Realization / Implementation (···▷): Dashed line with open hollow triangular head pointing to <<interface>> Strategy.
  • ✕ Fatal Exam Error: Using a solid inheritance triangle (──▷) for an interface! This is an immediate point deduction.

Universal Architectural Standard Pillar 04

Core Principles Enforced

Patterns are concrete expressions of foundational software engineering axioms:

  • ✓ Open/Closed Principle (OCP): The Context class is closed for modification when new algorithms are invented, but open for extension.
  • ✓ Dependency Inversion Principle (DIP): High-level domain logic does not depend on low-level detail; both depend on abstractions.
  • ✓ Favor Composition over Inheritance: Dynamic aggregation yields greater flexibility and less fragility than static class derivation.
Unit 1: Strategy Pattern Focus

OCP & DIP in Action

When we need to introduce a brand new flight algorithm (e.g., FlyRocketPowered), we do not touch Duck.java at all. We write a single new class implementing FlyBehavior.

🎯 Exam Question: "Which SOLID principles are directly realized by the Strategy Pattern?" Always cite OCP, DIP, and SRP, accompanied by the Head First axiom "Encapsulate what varies."
Universal Architectural Standard Pillar 05

Implementation Mechanics & Hot-Swapping

Code wiring must support dynamic mutation without re-instantiating the entire context:

  • ✓ Interface Reference: Field declared as the interface type, never concrete class.
  • ✓ Runtime Setter: setStrategy(Strategy s) allows swapping algorithms on live objects.
  • ✓ Pure Delegation: Context method simply forwards the request to this.strategy.algorithm().
Unit 1: Strategy Pattern Focus

Duck Dynamic Hot-Swapping

DuckHotSwap.java · Dynamic Mutation 
// 1. Context instantiated with initial baseline strategy
Duck modelDuck = new ModelDuck();
modelDuck.performFly(); // Output: << Silence >> (FlyNoWay)

// 2. Dynamic runtime hot-swap without re-instantiating the Context
modelDuck.setFlyBehavior(new FlyRocketPowered());
modelDuck.performFly(); // Output: "Screaming through the sky at Mach 3!"
🎯 Exam Trap: If your Context class does not provide a setter for the strategy, you lose runtime dynamicity, reducing the pattern to basic constructor dependency injection.
Universal Architectural Standard Pillar 06

Architectural Costs & Trade-offs

Senior software architects never declare a pattern "always good". Every abstraction introduces trade-offs:

  • ✓ Benefits: Eliminates conditional statements, isolates algorithmic bugs, enables independent mock testing.
  • ✕ Costs: Class Explosion (many small classes), Heap allocation overhead, increased mental indirection.
  • ✕ Client Awareness: The client application must understand the differences between strategies to select the right one.
Unit 1: Strategy Pattern Focus

Mitigating Strategy Costs in Java

In modern Java 8+, class explosion and heap allocation can be mitigated:

StrategyOptimization.java · Lambdas & Flyweights 
// Java 8+ Functional Interface: Pass lambda directly (zero new class files!)
duck.setFlyBehavior(() -> System.out.println("Jetpack gliding!"));

// High-throughput systems: Share stateless Flyweight singletons
duck.setFlyBehavior(FlyBehaviors.NO_WAY); // Reuses 1 shared instance, 0 GC allocations
🎯 Trade-off Summary: Strategy trading compile-time simplicity for runtime flexibility and clean OCP compliance.
Universal Architectural Standard Pillar 07

Rival Pattern Decision Matrix

In architecture reviews and exams, the most critical skill is choosing between rival patterns that look identical on UML diagrams:

  • ✓ Strategy vs. State: Identical UML structure! In Strategy, the client selects an algorithm. In State, state changes autonomously inside the object.
  • ✓ Strategy vs. Template Method: Strategy uses composition (whole algorithm). Template Method uses inheritance (skeleton base class, subclass overrides steps).
  • ✓ Strategy vs. Command: Strategy encapsulates an algorithm; Command encapsulates a request / action with undo capability.
Unit 1: Strategy Pattern Focus

Universal Architectural Standard Pillar 08

Real-World Enterprise Reference & Exam Traps

Real-world enterprise systems rely on Strategy everywhere. Knowing standard JDK citations proves deep industry mastery:

  • ✓ java.util.Comparator: Swapped inside Collections.sort(list, comparator).
  • ✓ java.awt.LayoutManager: Components delegate layout to BorderLayout, FlowLayout.
  • ✓ Spring ResourceLoader: Swapping file system, classpath, or cloud S3 loading strategies.
Unit 1: Strategy Pattern Focus

Top 3 Exam Traps to Avoid

  • ✕ Trap 1: Circular Context Passing. Passing Context to Strategy creates tight two-way coupling. Only pass raw data parameters!
  • ✕ Trap 2: Missing Setter. Forgetting setFlyBehavior() prevents runtime behavior changes.
  • ✕ Trap 3: LSP Violation. Throwing UnsupportedOperationException inside a ConcreteStrategy violates Liskov Substitution.
🎯 Exam Target: Scoring 15/15 points requires demonstrating awareness of all 3 traps.

Step 1: The Clean Starting Model (Textbook Inheritance)

Stable Baseline

We start with an abstract base class Duck providing shared behaviors like quack() and swim(). Subclasses like MallardDuck and RedheadDuck inherit these methods and provide their own display logic.

💡 Why it worked: Every duck in the system behaved identically. There was zero variance in flight or sound.

Step 2: The Innocent Feature Request (The Inheritance Trap)

Naive Engineering Move

The Requirement: Management demands that ducks in the simulator must fly.
The Junior Trap: "We have an inheritance hierarchy! Let's just add public void fly() to the base Duck class so all subclasses inherit it for free!"

Duck.java — Naive Superclass Mutation
git diff
public abstract class Duck { public void quack() { System.out.println("Quack"); } + public void fly() { System.out.println("Flying with wings!"); } // MISTAKE: FORCED ON ALL SUBCLASSES public abstract void display(); }
⚠️ The Hidden Flaw: In class inheritance, modifying a superclass automatically mutates the behavior of every single subclass, even those that should never have that capability.

Step 3: The Production Bug (Rubber Ducks Flying!)

CRITICAL REGRESSION BUG

During the release demo, disaster strikes: Bath toy RubberDuck instances suddenly sprout wings and fly across the display! Inanimate wooden DecoyDuck instances also fly!

💥 The Architectural Root Cause: Fragile Base Class

What was intended to be an isolated feature addition inadvertently broke subclasses across the entire system. In enterprise systems, this is how security privileges or tax calculation bugs silently leak across unrelated microservices.

Step 4: The Flawed Band-Aid (No-op Overrides & LSP Violation)

Antipattern: Empty Overrides

The developers attempt a quick hack: "We'll just override fly() in RubberDuck and DecoyDuck with an empty body to do nothing:"

RubberDuck.java — LSP Violation
empty override
public class RubberDuck extends Duck { + @Override public void fly() { /* Do nothing - rubber ducks cannot fly! */ } }
Maintenance Explosion:

When 50 duck types exist, developers must manually remember to override dozens of irrelevant methods.

LSP Violation (Unit 6):

Subclasses advertise an API contract they cannot fulfill, violating behavioral subtyping.

Step 5: The Architectural Epiphany (The Strategy Pattern)

The Masterclass Solution

The Solution: Take what varies and pull it completely out of Duck! Encapsulate flying inside a FlyBehavior interface. The Duck class holds an interface reference and delegates at runtime.

- quackBehavior: QuackBehavior

🎉 The Triumph: New flight algorithms can be created without changing a single line of Duck! Behavior can be swapped dynamically at runtime via setFlyBehavior()!
STAGE 1 KEY TAKEAWAYS · FOUNDATIONAL DESIGN PRINCIPLES

The 3 Architectural Axioms Derived from This Story

The failure of inheritance and the emergence of the Strategy pattern establish three universal object-oriented design principles. Memorize these for Prof. Schäfer's POSA exam:

Principle 1 · OCP

Encapsulate What Varies

Isolate volatile business algorithms into dedicated interfaces so they never contaminate or break stable client domains.

Principle 2 · GoF #1

Composition Over Inheritance

A flexible "HAS-A" relationship enables dynamic runtime behavior changes without touching rigid class inheritance trees.

Principle 3 · DIP

Program to Interfaces

High-level modules must depend strictly on abstract contracts, completely decoupling callers from concrete implementations.

Duck.java & Subclasses (Antipattern) 
// ❌ PROBLEM: Adding methods to base class forces inappropriate behavior
public abstract class Duck {
    public void quack() { System.out.println("Quack"); }
    public void swim() { System.out.println("Swimming"); }
    public void fly() { System.out.println("Flying high!"); } // INHERITED BY ALL

}

// ❌ RubberDuck must override with an empty body (LSP Violation!)
public class RubberDuck extends Duck {
    @Override
    public void fly() {
        // Do nothing... bath toys cannot fly!
        // PROBLEM: Callers still see fly() on RubberDuck and expect real flight!
    }
}
StrategyPattern.java (Clean Design) 
// ✅ SOLUTION: Encapsulate flying into an interface
@FunctionalInterface
public interface FlyBehavior {
    void fly();
}

public class FlyWithWings implements FlyBehavior {
    public void fly() { System.out.println("Flying with biological wings!"); }
}

public class FlyNoWay implements FlyBehavior {
    public void fly() { System.out.println("<< Silence >> Grounded peacefully."); }
}

// ✅ Context delegates to the interface and can hot-swap at runtime!
public abstract class Duck {
    protected FlyBehavior flyBehavior;

    public void performFly() {
        flyBehavior.fly(); // Dynamic delegation!
    }

    public void setFlyBehavior(FlyBehavior fb) {
        this.flyBehavior = Objects.requireNonNull(fb); // Runtime swap!
    }
}

🎯 Official Exam Gotcha 1: Strategy Object Explosion

"What happens when a system has an explosion of Strategy objects? How do we manage memory?"

The Problem: Allocating individual Strategy instances for 1,000,000 Context objects wastes heap memory and triggers heavy Garbage Collection pauses.

The 3 Exam-Grade Solutions:

  1. Stateless Flyweight Strategies (Unit 5 & GoF): If strategies maintain no mutable internal state, share a single singleton Strategy instance across all Contexts.
  2. First-Class Functions / Lambdas (Modern Java 8+): Pass pure method references (e.g. Integer::compareTo), eliminating heavy class metadata.
  3. Strategy Factory (Unit 8): Pool pre-allocated strategy instances.
🎯 Official Exam Gotcha 2: Context Private Data Access Dilemma

"If a Strategy needs private data from Context, how do we pass it without breaking encapsulation?"

  1. Segregated Read-Only Interface (ISP · Unit 6): Context implements a narrow interface exposing only necessary getters, and passes that interface to Strategy.
  2. Data Transfer Object (DTO): Context creates an immutable snapshot record and passes it as a method parameter: strategy.sort(context.toSnapshot()).
  3. Package-Private Visibility: In Java, keep Context and concrete strategies in the same package with default access.
