Unit 1 · Behavioral Architecture & Foundations

The Strategy Pattern & Dynamic Decoupling

How elite software engineers isolate volatile algorithmic business logic from stable domain contexts, eliminate brittle inheritance hierarchies, and achieve zero-downtime runtime extensibility.

The 3 Canonical Pillars of Object-Oriented Architecture GoF Category: Behavioral

The Golden Rule: “Identify the aspects of your application that vary and separate them from what stays the same.”

1. Program to Interfaces

Never program to concrete implementations. Depend on interface abstractions so concrete algorithms can be substituted transparently via polymorphism.

2. Favor Composition over Inheritance

Class inheritance fixes behavior statically at compile time. Object composition gives you dynamic, in-memory elasticity to alter behavior on the fly.

3. Open-Closed Principle (OCP)

Classes should be closed for direct modification but open for extension. Add 50 new algorithms without touching a single line of client context code.

1.2 The Architectural Journey: Anti-Pattern vs. Masterclass

Why 90% of legacy systems fail when using inheritance for shared behavioral logic.

❌ The Naive Inheritance Anti-Pattern Production Bug

Adding fly() directly to the Duck superclass forces all 50 subclasses to inherit it automatically: 

public class Duck {
    public void quack() { ... }
    public void swim() { ... }
    // 💥 DISASTER: Rubber ducks now fly!
    public void fly() { 
        System.out.println("Flying!"); 
    }
}
// RubberDuck is now forced to fly!
public class RubberDuck extends Duck { ... }
💥 Catastrophic Regression: Overriding with empty no-ops violates the DRY principle and breaks Liskov Substitution Principle (LSP).
✅ The Strategy Pattern Architecture Clean Architecture

Extract varying behaviors into separate interfaces. Duck holds a reference and delegates at runtime: 

public abstract class Duck {
    // Composition: "has-a" relationship
    protected FlyBehavior flyBehavior;
    
    public void performFly() {
        flyBehavior.fly(); // Runtime delegation
    }
    // Dynamic runtime hot-swap setter!
    public void setFlyBehavior(FlyBehavior fb) {
        this.flyBehavior = fb;
    }
}
🌟 Architectural Triumph: 100% Extensible. Add 20 new flight algorithms without modifying a single line of Duck client code.

DatasetSorter.java (Java 21) Generics & Functional Interfaces 
// 1. The Strategy Interface as a Functional Interface
@FunctionalInterface
public interface SortStrategy<T extends Comparable<T>> {
    void sort(List<T> items);
}

// 2. Concrete Strategy: In-place QuickSort
public final class QuickSortStrategy<T extends Comparable<T>> implements SortStrategy<T> {
    @Override
    public void sort(List<T> items) {
        if (items.size() <= 1) return;
        quickSort(items, 0, items.size() - 1);
    }
    private void quickSort(List<T> list, int low, int high) {
        if (low < high) {
            int p = partition(list, low, high);
            quickSort(list, low, p - 1);
            quickSort(list, p + 1, high);
        }
    }
    private int partition(List<T> list, int low, int high) {
        T pivot = list.get(high);
        int i = low - 1;
        for (int j = low; j < high; j++) {
            if (list.get(j).compareTo(pivot) <= 0) {
                i++;
                Collections.swap(list, i, j);
            }
        }
        Collections.swap(list, i + 1, high);
        return i + 1;
    }
}

// 3. The Context Class (Zero dependency on concrete strategies)
public class DatasetSorter<T extends Comparable<T>> {
    private SortStrategy<T> strategy;

    public DatasetSorter(SortStrategy<T> strategy) {
        this.strategy = Objects.requireNonNull(strategy, "Strategy cannot be null");
    }

    // Dynamic runtime hot-swap!
    public void setStrategy(SortStrategy<T> strategy) {
        this.strategy = Objects.requireNonNull(strategy);
    }

    public void executeSort(List<T> dataset) {
        long start = System.nanoTime();
        strategy.sort(dataset);
        long elapsed = System.nanoTime() - start;
        System.out.printf("Sorted %d elements in %.2f ms%n", dataset.size(), elapsed / 1e6);
    }
}

class DatasetProcessor:
    def __init__(self, strategy: SortStrategy[T]) -> None:
        self._strategy = strategy

    def set_strategy(self, strategy: SortStrategy[T]) -> None:
        self._strategy = strategy

    def process(self, data: List[T]) -> None:
        t0 = time.perf_counter()
        self._strategy.sort(data)
        elapsed = (time.perf_counter() - t0) * 1000
        print(f"Processed {len(data)} items via {self._strategy.__class__.__name__} in {elapsed:.3f}ms")

1.7 Exercise: Official Self-Study Questions (Prof. Dr. Jörg Schäfer)

🎯 Gotcha #1: Strategy Object Explosion & Memory Overhead

"What happens when a high-scale system has an explosion of Strategy objects? How can an architect prevent catastrophic memory exhaustion?"

The Architectural Problem: If 1,000,000 Duck or Sorter instances each instantiate a brand new FlyWithWings or QuickSortStrategy object, the JVM allocates millions of redundant objects, triggering severe Garbage Collector pauses and heap bloat.

The 3 Exam-Grade Solutions:

  1. Stateless Strategies via Flyweight Pattern: If a Strategy contains no mutable instance fields, it can be made a stateless Singleton / Flyweight. All 1,000,000 contexts share a single instance in memory.
  2. First-Class Lambdas & Method References: In modern Java (Integer::compareTo) or Python (lambda x: x.id), strategies are passed as pure function references without allocating heavyweight class instances.
  3. Strategy Factory (Unit 8): Cache and manage strategy lifecycles behind a centralized Factory to prevent ad-hoc allocation.
🎯 Gotcha #2: Context Data Access Coupling & Privacy Leaks

"GoF states a Strategy gets data by (A) parameter arguments or (B) Context reference passed to Strategy. What happens if the data required by Strategy is NOT public on Context? How do you solve this without violating Encapsulation?"

The Dilemma: If Context exposes its private fields via public getters just so a Strategy can read them, Information Hiding is broken for all other outside callers!

The 3 Architectural Remedies:

  1. Narrow Interface (Interface Segregation Principle): Define a restricted interface (e.g. ContextInspectable) exposing only the fields the Strategy needs. Context implements it and passes this typed strictly as ContextInspectable.
  2. Data Transfer Object (DTO): Context bundles only the required data slice into an immutable DTO and passes it into strategy.execute(dto).
  3. Package-Private Visibility (Java): Place Context and Strategies in the same package, keeping access package-private.
