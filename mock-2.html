Exam Notes Question 1 · Unit 2A 5 Points

How could you achieve the functionality of a Template Method using object composition? What would some of the tradeoffs be?

Model Answer & Rubric Model Solution & Rubric

Official Model Solution:

  1. Composition Alternative (Strategy Pattern): Instead of having an abstract class with primitive abstract methods that subclasses override via inheritance, the context class delegates variant step(s) to a strategy interface injected at runtime.
  2. The Canonical Head First Example (Ducks & Comparators):
    • Inheritance approach (Template Method): A Duck class implements Comparable<Duck> and overrides compareTo(). The sorting algorithm relies on inheritance and can only sort ducks in one fixed way.
    • Composition approach (Strategy): We pass a Comparator<Duck> into Arrays.sort(ducks, comparator). The sorting algorithm is parameterised via object composition.
  3. Tradeoffs Analysis:
    • Advantages of Composition: Dynamic runtime hot-swapping; sorts objects from external libraries whose source code or inheritance hierarchy cannot be altered; avoids subclass explosion.
    • Disadvantages of Composition: Requires creating additional objects and interfaces; extra indirection; the strategy object may need access to private context state, requiring wider accessor methods.
⚠️ Exam Pitfall: Always ground your answer in the Comparable (Template Method subclassing) vs Comparator (Strategy composition) example from the course notes.
Exam Notes Question 2 · Unit 2B 5 Points

How does the Command Object get access to the data it needs to perform its job? How does one guarantee that this does not create a strong coupling?

Model Answer & Rubric Model Solution & Rubric

Official Model Solution:

  1. Data Access Mechanism: The Command object receives its required target Receiver and parameter data via Constructor Dependency Injection when instantiated by the Client, OR parameters are passed into execute(Receiver target). The command encapsulates the receiver instance and state changes internally.
  2. Preventing Strong Coupling:
    • The Invoker (e.g. RemoteControl) knows only the abstract Command interface (execute(), undo()). It has zero knowledge of the concrete Receiver or the domain data.
    • The Command depends on an abstract Receiver interface where possible, shielding it from concrete receiver implementations.
    • The Client wires together the Receiver and Command, completely decoupling the Invoker from the Receiver.
⚠️ Exam Pitfall: Never state that the Invoker provides the data to the Command. The Invoker is pure trigger mechanism! Data is bound at construction time.
Exam Notes Question 3 · Unit 2B 5 Points

In a MacroCommand, in what order must child commands execute, and in what order must undo() be invoked? Why?

Model Answer & Rubric Model Solution & Rubric

Official Model Solution:

  • Execution Order: Strict forward FIFO (First-In, First-Out) order ($C_1 \to C_2 \to \dots \to C_n$). Commands execute sequentially in the exact logical order registered.
  • Undo Order: Strict reverse LIFO (Last-In, First-Out) order ($C_n \to C_{n-1} \to \dots \to C_1$) using a stack or reverse loop iteration.
  • Causal Reason (Non-Commutativity): State transformations in real systems are non-commutative. For example, if a MacroCommand (1) turns on a Stereo, and (2) sets volume to 10; undoing in forward order would set the volume of an off device, causing an exception or corrupted state. Reversing the sequence restores the exact invariant system state.
Exam Notes Question 4 · Unit 3 5 Points

How does the Composite pattern help to consolidate system-wide conditional logic?

Model Answer & Rubric Model Solution & Rubric

Official Model Solution:

  1. Elimination of Type Queries: Without Composite, clients must constantly query types: if (node instanceof Composite) { ... iterate children ... } else { ... process leaf ... }. This litters conditional logic throughout the client application.
  2. Uniform Polymorphism: Composite defines a uniform component interface for both simple leaves and complex composites. The client invokes component.operation() identically without branching.
  3. Recursive Delegation: Composite nodes automatically delegate operations to their children recursively. The branching logic is consolidated into polymorphism, preserving the Open-Closed Principle (OCP).
Exam Notes Question 5 · Unit 9 5 Points

Why is an Object Adapter generally preferred over a Class Adapter, and why is a Class Adapter impossible in Java when adapting two concrete classes?

Model Answer & Rubric Model Solution & Rubric

Official Model Solution:

  • Java Limitation: A Class Adapter requires multiple class inheritance: the adapter must subclass both the Target class and the Adaptee class (class Adapter extends Target, Adaptee). Since Java enforces single class inheritance, a Class Adapter is impossible when both Target and Adaptee are concrete classes.
  • Flexibility of Object Adapter: An Object Adapter uses object composition (holding an instance variable Adaptee adaptee;). This adheres to "Favor object composition over class inheritance".
  • Polymorphic Coverage: An Object Adapter can adapt not only the specified Adaptee class, but any of its subclasses dynamically at runtime. A Class Adapter can only adapt that single static class.

Exam Notes Question 6 · Unit 8 5 Points

In [GHJV95], an Abstract Factory is composed of Factory Methods, each with exactly one signature. Does this imply that the Factory Method can only create an object in one way? What do you do if you want to specify room color & size in MakeRoom()?

Model Answer & Rubric Model Solution & Rubric

Official Model Solution:

  1. No Restriction: It does NOT imply creation in only one way. A factory method can be parameterized (e.g. MakeRoom(RoomType type, Color color, int size)) or use default arguments.
  2. Alternative Solutions from GoF:
    • Prototype Pattern: The Abstract Factory holds prototypical instances of rooms and clones them, parameterizing only the variant attributes (color, size).
    • Builder Pattern: If object creation involves complex multi-step construction with many optional parameters, replace or pair the Abstract Factory with a Builder pattern.
⚠️ Exam Pitfall: Avoid suggesting adding dozens of overloaded methods to the Abstract Factory interface. That violates the Interface Segregation Principle (ISP) and creates brittle interfaces.

Exam Notes Question 8 · Unit 5 10 Points

Name and explain 4 architectural building patterns from Christopher Alexander's 1977 book. Can you implement a reusable binary "pattern library" for software? If not, why not?

Model Answer & Rubric Model Solution & Rubric

Part 1: 4 Alexander Architectural Patterns:

  1. Identifiable Neighborhood: Keep urban communities to 300–500 people so residents recognize faces and preserve mutual social responsibility.
  2. City-Country Fingers: Interlace bands of countryside into urban areas so nature is accessible within walking distance from any urban center.
  3. Light on Two Sides of Every Room: Design rooms with windows on at least two exterior walls to eliminate glare and provide balanced natural light.
  4. Alcoves: Create intimate, semi-enclosed nooks within larger social rooms so individuals can withdraw without being entirely isolated.

Part 2: Why a Reusable Binary Pattern Library is Impossible in Software:

  • Generative Blueprints vs Components: A design pattern is a description of a solution to a recurring design problem in a context, not a prefabricated piece of machine code or binary JAR/DLL.
  • Contextual Adaptation: Every pattern must be adapted to domain-specific types, inheritance trees, thread-safety models, and performance constraints. You cannot compile a generic "Observer" into a binary library that fits all business domains without loss of type safety or excessive boilerplate.

Exam Notes Question 9 · Unit 6 5 Points

Can you check for conformance to the Liskov Substitution Principle (LSP) automatically using static analysis tools? Why or why not?

Model Answer & Rubric Model Solution & Rubric

Official Model Solution:

  • General Answer: NO. Conformance to LSP is fundamentally undecidable in the general case (consequence of Rice's Theorem and the Halting Problem).
  • Syntactic vs Semantic Verification:
    • Static compilers/linters can easily verify syntactic conformance (method names, parameter contravariance, return type covariance, and declared exception subtyping).
    • Static tools cannot automatically verify behavioral semantics:
      1. Subclasses must not strengthen preconditions (inputs cannot be more restrictive).
      2. Subclasses must not weaken postconditions (guarantees cannot be broken).
      3. Invariants of the superclass must be preserved.
      4. History constraint (state mutations must obey superclass rules).
  • Verifying behavioral LSP requires formal verification, Design by Contract (e.g., Eiffel, JML), or runtime contract monitoring.
Exam Notes Question 10 · Unit 6 5 Points

Does the sentence: “This class adheres to the Open Closed Principle” make sense in software architecture?

Model Answer & Rubric Model Solution & Rubric

Official Model Solution:

No, the sentence is fundamentally incomplete and misleading.

  • No software module can ever be 100% closed against all possible kinds of changes. As Robert C. Martin notes: "Closure is always relative to anticipated axes of change."
  • A class may be closed against the addition of new payment algorithms (via Strategy), but completely open and vulnerable to changes in tax calculation regulations or multi-currency conversions.
  • The architect must explicitly specify: "This class is closed against [Axis of Change X] by means of [Abstraction Y]." Claiming absolute adherence is architectural nonsense.
Exam Notes Question 11 · Unit 6 5 Points

Why does the Single Responsibility Principle (SRP) make sense? Why does the Dependency Inversion Principle (DIP) make sense?

Model Answer & Rubric Model Solution & Rubric

Official Model Solution:

  • SRP Rationale: "A class should have only one reason to change" (i.e. one actor/stakeholder). When a single class mixes business logic, GUI formatting, and database queries, changes requested by the CFO risk breaking features used by the DBA. SRP isolates blast radiuses of requirement changes.
  • DIP Rationale: "High-level modules should not depend on low-level modules; both should depend on abstractions." High-level business rules are the core asset of an enterprise. DIP prevents volatile I/O devices, UI frameworks, or database drivers from dictating domain logic architecture.
Exam Notes Question 12 · Unit 7 (Main Sequence Calculation) 10 Points

Given a package $P$ with 2 abstract classes, 8 concrete classes, 15 incoming dependencies ($C_a$), and 5 outgoing dependencies ($C_e$): Calculate Instability ($I$), Abstractness ($A$), and Normalized Distance ($D$). Interpret whether $P$ is well-designed.

Model Answer & Rubric Model Solution & Rubric

Official Mathematical Derivation:

  1. Instability ($I$): $$I = \frac{C_e}{C_a + C_e} = \frac{5}{15 + 5} = \frac{5}{20} = 0.25$$ $P$ is highly stable (many incoming afferent couplings, few efferent couplings).
  2. Abstractness ($A$): $$A = \frac{N_a}{N_a + N_c} = \frac{2}{2 + 8} = \frac{2}{10} = 0.20$$ $P$ is predominantly concrete (80% concrete classes).
  3. Normalized Distance ($D$): $$D = |A + I - 1| = |0.20 + 0.25 - 1| = |-0.55| = 0.55$$

Architectural Interpretation:

  • The ideal Main Sequence line is $A + I = 1$ ($D = 0$). With $D = 0.55$, package $P$ is significantly off the sequence, dipping into the Zone of Pain $(A \to 0, I \to 0)$.
  • The Zone of Pain: Package $P$ is heavily relied upon by 15 outside modules, yet contains mostly concrete implementation code. This makes $P$ rigid and extremely painful to modify without breaking dependents.
  • Recommendation: Introduce interfaces or abstract classes to raise $A$ closer to $0.75$, balancing stability with abstract extensibility.

Exam Notes Question 13 · Unit 12 5 Points

Could you implement a compiler using Pipes & Filters? What features make the pipe architecture less suitable for a modern compiler?

Model Answer & Rubric Model Solution & Rubric

Official Model Solution:

  • Feasibility: YES. Historically, early UNIX compilers were implemented strictly as Pipes & Filters (e.g. preprocessor | parser | optimizer | code_generator | assembler) because physical RAM was measured in kilobytes.
  • Why It Is Less Suitable for Modern Compilers:
    1. Shared Global Context: Modern compilers require a unified, complex Symbol Table and rich Abstract Syntax Tree (AST) accessible by multiple optimization passes. Streaming text/bytes between disconnected pipe processes has enormous serialization overhead.
    2. Non-Linear Backtracking: Complex syntax and semantic analysis require non-linear navigation and lookahead across the AST, which cannot be done over one-way sequential pipes.
    3. Rich Error Diagnostics: Modern compilers need random access to original source files to print precise column/line error spans.
Exam Notes Question 14 · Unit 12 5 Points

In the Blackboard architecture, when should the application main loop stop? What are the liabilities of the Blackboard architecture?

Model Answer & Rubric Model Solution & Rubric

Official Model Solution:

Stopping Conditions (3 Pillars):

  1. Goal Achieved: A hypothesis on the blackboard meets or exceeds the required confidence threshold or complete solution specification.
  2. Quiescent State / Dead End: No Knowledge Source (KS) is able to inspect the blackboard and contribute further progress.
  3. Resource Bound Exceeded: Time budget or computation step limits are exhausted.

Liabilities:

  • Non-deterministic Execution: Opportunistic activation of KS makes testing, debugging, and reproducing failures exceptionally hard.
  • Centralized Bottleneck: The central blackboard is a major concurrency synchronization bottleneck under heavy parallel write loads.
Exam Notes Question 15 · Unit 13 5 Points

Define in your own words the difference between Analysis Patterns and Design Patterns.

Model Answer & Rubric Model Solution & Rubric

Official Model Solution:

  • Analysis Patterns (Martin Fowler): Model the business domain concepts, business rules, and real-world semantic structures (e.g., Party, Accountability, Observation, Account Posting). They are technology-agnostic and conceptual—independent of programming languages, databases, or GUI frameworks.
  • Design Patterns (Gang of Four): Model the technical software architecture and OOP implementation mechanics (e.g., Strategy, Composite, Decorator, Factory). They solve technical design problems like code reuse, interface decoupling, dynamic polymorphism, and memory management.
Exam Notes Question 16 · Unit 15 5 Points

What was Peter Norvig’s core critique regarding the 23 Gang of Four patterns in dynamic and functional programming languages?

Model Answer & Rubric Model Solution & Rubric

Official Model Solution:

In his 1996 analysis (Design Patterns in Dynamic Languages), Peter Norvig demonstrated that:

  1. 16 of the 23 GoF Patterns are Invisible or Native Idioms: In dynamic and functional languages with first-class functions, closures, dynamic typing, and multi-methods (e.g., Common Lisp, Python, Clojure), 16 of the GoF patterns disappear into simple elementary language syntax.
  2. Concrete Examples:
    • Strategy: Passing a first-class lambda function (e.g. Python's map() or qsort(..., compar)) eliminates the need for Strategy classes and context wrappers.
    • Command: Passing anonymous closures replaces the entire Command class hierarchy and execute() ceremony.
    • Iterator: Native language generator functions (yield) eliminate custom iterator classes.
  3. Conclusion: Many GoF patterns are not universal architectural truths, but rather compensating workarounds for the limitations of static OOP languages (C++ and Java 1.0).
Exam Notes Question 17 · Unit 10 5 Points

Is RSS really using the Observer Pattern in the technical sense?

Model Answer & Rubric Model Solution & Rubric

Official Model Solution:

Technically: NO.

  • Push vs Pull Architecture:
    • The GoF Observer pattern is a Push mechanism: The Subject maintains active references to subscribed observers and pushes notifications/state changes immediately when an event occurs via synchronous or asynchronous callbacks.
    • RSS is a Polling / Pull mechanism: The RSS server maintains zero state about subscribers. Client readers periodically send HTTP GET requests to poll the XML feed.
  • While both share the conceptual goal of notifying multiple interested parties of updates, their architectural mechanics are fundamentally opposite (Push event dispatch vs Pull polling over HTTP).
