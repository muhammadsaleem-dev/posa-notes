Testing Patterns: The 5 Test Doubles

Master Gerard Meszaros’ canonical xUnit Test Double taxonomy (Dummy, Stub, Spy, Mock, Fake) and the architectural debate between State Verification (Detroit) and Behavior Verification (London).

⚡ Executive Summary Testing Patterns: Test Doubles & Fixture Architecture
Collapse Expand

“Tests are first-class architectural artifacts. Repeatable, deterministic verification requires rigorous test double patterns.”

🎯 The Gerard Meszaros Test Double Taxonomy

Dummy (passed but never used); Stub (returns canned answers); Spy (records call interactions); Mock (pre-programmed with expectations to verify behavior); Fake (working in-memory implementation).

→ Knowing when to use a Stub vs. Mock is tested on every exam.
🕵️‍♂️ State Verification vs. Behavior Verification

State Verification (Stubs) asserts on data returned by the system under test. Behavior Verification (Mocks) asserts that specific method invocations occurred with precise arguments.

→ Overusing mocks leads to brittle tests coupled to implementation details.

The 5 Gerard Meszaros Test Doubles

xUnit Test Patterns Standard
1. Dummy: Objects passed around but never actually used. Primarily used to satisfy mandatory method signatures (e.g. non-null parameter).
2. Stub: Provides canned answers to calls made during test execution, responding only to specific test inputs. Does not record calls or verify behavior.
3. Spy: A Stub that also records information about how it was called (e.g. invocation count, recorded arguments) so test code can assert on them afterwards.
4. Mock: Objects pre-programmed with explicit expectations before execution. During or after the test, the mock verifies that expected method calls occurred with exact parameters.
5. Fake: Has a real, working implementation of the collaborator, but takes shortcuts that make it unsuitable for production (e.g. in-memory H2 database instead of PostgreSQL).

State vs. Behavior Verification

Detroit (Classical) vs. London (Mockist) Schools
TDD SCHOOLS Detroit (Classicist) vs. London (Mockist)
State Verification (Detroit / Chicago)

Executes the SUT (System Under Test) and asserts on the resulting final state: assertEquals(150.0, account.getBalance());. More resilient to internal refactoring because tests do not care about private collaborator interactions.

Behavior Verification (London / Mockist)

Asserts on interactions: verify(paymentGateway).charge(150.0);. Ensures that the SUT collaborates with dependencies exactly as specified. Can lead to brittle tests if private collaboration details change.

Direct Question → Answer Format
Question 1: Distinguish Between a Stub, a Spy, and a Mock 5 Points

Distinguish between a Stub, a Spy, and a Mock in Gerard Meszaros' test double taxonomy!

Model Answer:
  • Stub: Supplies canned answers to calls from the SUT to drive test execution, but does not record interactions or verify call counts.
  • Spy: Extends a stub by recording runtime telemetry (e.g., number of invocations, arguments passed) for subsequent assertion by the test method.
  • Mock: Configured with strict expectations upfront (expected invocations, exact arguments, order). It verifies the interactions automatically as part of the test verification.
