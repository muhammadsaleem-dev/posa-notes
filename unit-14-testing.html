Unit 14 · Quality Assurance & Verification

Testing Patterns & Test Doubles

“Now you really have done something.” — Christopher Alexander

Gerard Meszaros’s xUnit patterns for isolating the System Under Test (SUT): the 5 distinct varieties of Test Doubles and the difference between state and behavioral verification.

1

14.3 The 5 Test Doubles (Gerard Meszaros)

A "Test Double" is any pretend object used in place of a real collaborator during tests.

1. Dummy

Passed around but never actually used. Used solely to satisfy parameter lists (e.g. new User("test", null)).

2. Fake

Has a real working implementation, but takes shortcuts that make it unsuitable for production (e.g. an in-memory database).

3. Stub

Provides pre-programmed canned answers to calls made during tests, ignoring calls outside scenario expectations.

4. Spy

A stub that also records execution telemetry (e.g. records how many emails were sent and what arguments were passed).

5. Mock

Pre-programmed with strict expectations. Verifies that specific methods were invoked in a specific order (behavior verification).

2

State vs. Behavior Verification

State Verification (Stubs / Classical)

Executes the method and inspects the final state of the SUT or its collaborators: assertEquals(150.0, account.getBalance());

Behavior Verification (Mocks / Mockist)

Verifies that the SUT correctly collaborated with its peers: verify(paymentGateway, times(1)).charge(150.0);

14.4 Questions for Self-Study

Exam Drill What is the critical risk of over-relying on Mock objects for behavior verification?

Over-mocking creates brittle tests that are tightly coupled to implementation details.

If a developer refactors the internal method delegation of a class without altering its external output, state-verification tests continue to pass, but mock-verification tests break because the specific mocked invocations changed. Tests should verify what happens, not how it happens.
