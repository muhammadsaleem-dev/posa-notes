PILLAR 1 OF 8 · INTENT & MOTIVATION

Preventing Architectural Decay & Systemic Rot

Software architectures do not fail overnight; they degrade gradually due to the accumulation of 7 classic design smells (Rigidity, Fragility, Immobility, Viscosity, Needless Complexity, Needless Repetition, Opacity). The 5 SOLID principles provide formal laws to counteract these smells.

Primary Architectural Intent

Ensure systems remain maintainable, extensible without modification, safely substitutable across class hierarchies, decoupled from volatile details, and aligned with distinct business actors.

PILLAR 4 OF 8 · FORMAL LAWS & INVARIANTS

Barbara Liskov's Formal Subtype Invariance

Let \(\phi(x)\) be a property provable about objects \(x\) of type \(T\). Then \(\phi(y)\) should be true for objects \(y\) of type \(S\) where \(S\) is a subtype of \(T\).

1. Preconditions

Cannot be strengthened in a subtype (subtypes can accept more inputs, but never fewer).

2. Postconditions

Cannot be weakened in a subtype (subtypes must guarantee at least as much as the parent).

3. Invariants & History

All invariants of the supertype must be preserved. Subtypes cannot mutate immutable supertype state.

PILLAR 5 OF 8 · IMPLEMENTATION MECHANICS

Dependency Injection & Interface Segregation

OrderProcessor.java · DIP In Practice
// Clean DIP: High-level policy depends strictly on Abstractions
public class OrderProcessor {
    private final PaymentGateway gateway;
    private final InventoryRepository inventory;

    // Constructor Injection (Dependency Inversion)
    public OrderProcessor(PaymentGateway gateway, InventoryRepository inventory) {
        this.gateway = Objects.requireNonNull(gateway);
        this.inventory = Objects.requireNonNull(inventory);
    }

    public void process(Order order) {
        inventory.reserve(order.getItems());
        gateway.charge(order.getTotal());
    }
}

Architectural Trade-offs & Cognitive Cost

✅ SOLID Benefits
  • High testability: Mocks and stubs easily injected.
  • Eliminates cascading breaks when database or external APIs change.
  • Code reuse without coupling to environment-specific details.
⚠️ Potential Over-Engineering
  • Interface proliferation: Creating 1-to-1 interfaces for classes that will never have a second implementation.
  • Indirection: Navigating code requires jumping through interfaces.
  • Can violate YAGNI if speculative complexity is added too early.

● Stage 01 · Symptoms of Architectural Decay

The 7 Classic Architectural Smells (Robert C. Martin)

Before learning the principles, an architect must recognize the symptoms of systemic decay. Uncle Bob identified seven cardinal design smells that signal an application is rotting from within.

1. Rigidity

The tendency for software to be difficult to change because every single modification forces a cascade of changes in dependent modules.

2. Fragility

Changes cause the system to break in places that have no conceptual relationship to the part that was changed.

3. Immobility

The inability to reuse software parts in other applications because components are deeply entangled with local dependencies.

4. Viscosity

It is easier to do the "hacky wrong thing" than to preserve architectural integrity (design viscosity vs. environment viscosity).

5. Needless Complexity

The design contains infrastructure and speculative abstractions that have no direct business value today (YAGNI violation).

6. Needless Repetition

Copy-paste programming. Bug fixes in one module leave identical duplicate bugs alive across unmerged copies.

7. Opacity

The code is convoluted and expresses intent poorly, reading like an impenetrable riddle to new team members.

🧠 Key Takeaways: Rigidity vs Fragility
Rigidity (Cost of Change)

You want to change module A, but the compiler forces you to change B, C, D, and E. The architecture is rigid.

Fragility (Unpredictable Risk)

You modify user authentication, and suddenly the PDF report generator crashes. The architecture is fragile.

Viscosity (Friction)

Doing it right takes 3 hours of boilerplate; hacking it takes 3 minutes. Developers inevitably hack.

● Stage 02 · Foundational Laws

The 5 SOLID Principles Blueprint

Each letter of the SOLID acronym represents a fundamental design constraint that guarantees modularity, testability, and resilience against architectural decay.

S Single Responsibility Principle (SRP)

Rule: “A class should have one, and only one, reason to change.”

Each class should encapsulate a single business actor's requirements. If a class calculates employee salaries, connects to the SQL database, AND renders HTML, changing the database schema will force modifications to core financial payroll calculations.

O Open-Closed Principle (OCP)

Rule: “Software entities should be open for extension, but closed for modification.” (Bertrand Meyer)

You should be able to extend the behavior of a module without modifying its source code. Achieved via abstraction (interfaces, abstract base classes) and patterns like Strategy and Template Method.

L Liskov Substitution Principle (LSP)

Rule: “Subtypes must be substitutable for their base types without altering program correctness.” (Barbara Liskov)

A derived class must fulfill all behavioral promises made by its parent. It cannot throw unexpected runtime exceptions, weaken postconditions, or strengthen preconditions.

I Interface Segregation Principle (ISP)

Rule: “Clients should not be forced to depend upon interfaces that they do not use.”

Many client-specific interfaces are vastly superior to one bloated "fat" interface. Avoid "God Interfaces" that force a print-only client to implement scanner and fax methods.

D Dependency Inversion Principle (DIP)

Rule: “High-level modules should not depend on low-level modules. Both must depend on abstractions.”

Abstractions must not depend on details. Details (concrete implementations) must depend on abstractions.

Formal LSP: The Rectangle / Square Paradox

In high-school mathematics, a square is a special case of a rectangle. However, in object-oriented architecture, modeling class Square extends Rectangle violates the Liskov Substitution Principle! Run the interactive lab below to see the behavioral assertion crash in real time.

The Mathematical Root Cause (Design by Contract):
A Rectangle promises an independent postcondition: "Calling setWidth(w) leaves height unchanged."
A Square subclass cannot preserve this postcondition without violating its own invariant (\(width == height\)). Therefore, Square breaks client expectations and cannot be safely substituted for Rectangle.

Exam Drill 1 Why does "Square extends Rectangle" violate the Liskov Substitution Principle? (10 Exam Points)

Model Answer (Prof. Schäfer 1.0 Standard):

1. Rectangle establishes an independent postcondition: "Modifying width via setWidth(w) leaves height unchanged."

2. A client method written for Rectangle relies on this contract:

void test(Rectangle r) {
    r.setWidth(5);
    r.setHeight(4);
    assert(r.getArea() == 20); // Breaks if r is Square! (Square area would be 16)
}

3. Square cannot honor this postcondition without violating its own fundamental geometric invariant (\(width == height\)). Therefore, Square cannot be safely substituted for Rectangle without altering program correctness.

Exam Drill 2 What is the precise definition of a "responsibility" in the Single Responsibility Principle? (8 Exam Points)

Model Answer:

Robert C. Martin explicitly defines a responsibility as "a reason to change".

Furthermore, a reason to change is mapped directly to a single business stakeholder, user role, or actor within the organization. For example, financial auditors, DBA administrators, and UI designers represent distinct actors; a class should never mix requirements originating from multiple actors.

Exam Drill 3 Distinguish Dependency Inversion Principle (DIP) from Dependency Injection (DI). (7 Exam Points)

Model Answer:

  • Dependency Inversion Principle (DIP): A high-level architectural principle. It states that high-level policy modules should not depend on low-level detail modules; both must depend upon abstractions.
  • Dependency Injection (DI): A concrete design pattern / implementation technique. It provides dependencies to an object from the outside (via constructor, setter, or framework) rather than having the object construct them itself using new.

DI is the primary mechanism used to realize DIP.

Authentic Exam Question · LSP Conformance Can conformance to the Liskov Substitution Principle (LSP) be checked automatically? (7 Exam Points)

Official Model Answer & Grading Rubric (Prof. Dr. Jörg Schäfer):

No, not completely.

  • What can be checked automatically: Compilers and static linters easily verify syntactic subtyping (e.g. method signatures, return type covariance, parameter type contravariance, and visible access modifiers).
  • Why semantic LSP cannot be fully checked automatically: LSP is fundamentally a behavioral contract. It requires that:
    1. Subtypes must not strengthen preconditions (\(Pre(T) \implies Pre(S)\)).
    2. Subtypes must not weaken postconditions (\(Post(S) \implies Post(T)\)).
    3. Subtypes must preserve invariants (\(Inv(S) \implies Inv(T)\)) and respect history constraints (e.g. immutable objects remain immutable).

Statically verifying whether arbitrary runtime code fulfills behavioral postconditions and invariants is undecidable (equivalent to the Halting Problem). Therefore, software teams rely on Design by Contract (DbC), formal specifications, and extensive polymorphic contract test suites rather than pure compiler checks.
