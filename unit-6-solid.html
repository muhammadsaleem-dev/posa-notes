SOLID Principles & Architectural Decay

Master Robert C. Martin's 5 foundational design principles, the 4 classic symptoms of architectural rot (Rigidity, Fragility, Immobility, Viscosity), and the formal proof of why Square is NOT a Rectangle in object orientation.

1

The 5 SOLID Principles

Robert C. Martin Framework
S SRP — Single Responsibility Principle: "A class should have one, and only one, reason to change." In enterprise architecture, this translates to: A class should be responsible to one, and only one, actor or business stakeholder. Cohesive behavior belongs together; divergent responsibilities must be segregated.
O OCP — Open-Closed Principle: "Software entities should be open for extension, but closed for modification." You should be able to introduce new business features or algorithmic variations without altering existing, tested source code (achieved via polymorphism: Strategy, Template Method, Decorator).
L LSP — Liskov Substitution Principle: "Subtypes must be substitutable for their base types without altering the correctness of the program." Derived classes must fulfill all behavioral contracts guaranteed by the superclass (preconditions, postconditions, and class invariants).
I ISP — Interface Segregation Principle: "Clients should not be forced to depend on methods they do not use." Prefer many small, client-specific role interfaces over a single bloated "fat" general-purpose interface.
D DIP — Dependency Inversion Principle: "1. High-level modules should not depend on low-level modules; both should depend on abstractions.
2. Abstractions should not depend on details; details should depend on abstractions."
S · SRP DEEP DIVE The Multi-Actor Collision Anti-Pattern & Cohesive Separation

The Single Responsibility Principle is fundamentally about people and organizational actors. When multiple business stakeholders demand changes to the same source file, changes collide catastrophically: 

// VIOLATION: Employee class serves 3 different business stakeholders!
public class Employee {
    // 1. Actor: CFO / Accounting Department
    public Money calculatePay() {
        return regularHours() * hourlyRate + calculateOvertime();
    }

    // 2. Actor: COO / HR Operations Department
    public String reportHours() {
        return "Regular Hours: " + regularHours() + " | Overtime: " + reportOvertime();
    }

    // 3. Actor: CTO / Database Administrators
    public void save() {
        Database.getConnection().execute("INSERT INTO employees VALUES (" + this.id + ", ...)");
    }

    // SHARED PRIVATE METHOD: The fatal architectural coupling!
    private int regularHours() {
        return Math.min(this.loggedHours, 40);
    }
}
The Catastrophic Failure Scenario:

The HR department (COO) requests a policy change: non-overtime regular hours should be capped at 35 instead of 40. A developer updates regularHours() to return Math.min(this.loggedHours, 35). The change passes HR's acceptance tests and is deployed.

The Result: Payroll (CFO) now computes regular pay based on 35 hours instead of 40! Employees across the corporation receive incorrect paychecks because two separate business actors shared a single class.

The SRP Refactoring: Separate Classes Bound by Single Actor Cohesion: 

// Clean Architecture: Each class has exactly ONE actor and ONE reason to change
public class PayCalculator {
    public Money calculatePay(EmployeeData employee) { /* CFO logic */ }
}

public class HourReporter {
    public String reportHours(EmployeeData employee) { /* COO logic */ }
}

public class EmployeeRepository {
    public void save(EmployeeData employee) { /* CTO / DB logic */ }
}

// Lightweight shared data structure (pure entity record without behavior)
public record EmployeeData(String id, int loggedHours, Money hourlyRate) {}
O · OCP DEEP DIVE Polymorphic Abstraction vs. Fragile Type-Switching

The Open-Closed Principle states that software entities should be open for extension (can add new behavior) but closed for modification (without modifying already-tested, deployed source code). 

// VIOLATION: GraphicEditor must be modified every time a new shape is invented!
public class GraphicEditor {
    public void drawShape(Object shape) {
        if (shape instanceof Circle c) {
            drawCircle(c);
        } else if (shape instanceof Rectangle r) {
            drawRectangle(r);
        } else if (shape instanceof Triangle t) {
            drawTriangle(t); // Every new shape requires editing and re-testing GraphicEditor!
        }
    }
    private void drawCircle(Circle c) { /* Circle rendering */ }
    private void drawRectangle(Rectangle r) { /* Rectangle rendering */ }
    private void drawTriangle(Triangle t) { /* Triangle rendering */ }
}

The OCP Refactoring via Polymorphism: 

// 1. The Abstraction is closed for modification
public interface Shape {
    void draw();
}

// 2. Extensions are open: simply introduce new classes implementing the interface
public class Circle implements Shape {
    public void draw() { /* Render Circle */ }
}

public class Rectangle implements Shape {
    public void draw() { /* Render Rectangle */ }
}

public class Triangle implements Shape {
    public void draw() { /* Render Triangle */ }
}

// 3. Client is 100% closed against all future shape additions!
public class GraphicEditor {
    public void drawShape(Shape shape) {
        shape.draw(); // Polymorphic dynamic dispatch: zero modifications ever needed!
    }
}
Meyer's OCP (1988) vs. Martin's OCP (Uncle Bob):
  • Bertrand Meyer (Original): Advocated using implementation inheritance. A class can be closed once compiled, and extended by subclassing it and overriding methods. (Weakness: tight coupling to base class internals via the Fragile Base Class Problem).
  • Robert C. Martin (Modern): Advocates using polymorphic interfaces. Depend on stable interfaces; swap behavior using composition (Strategy, Decorator, Template Method). Zero inheritance coupling.
L · LSP DEEP DIVE Behavioral Subtyping & Contract Preservation

Formulated by Turing Award laureate Barbara Liskov (1987): "If for each object $o_1$ of type $S$ there is an object $o_2$ of type $T$ such that for all programs $P$ defined in terms of $T$, the behavior of $P$ is unchanged when $o_1$ is substituted for $o_2$, then $S$ is a subtype of $T$." 

// VIOLATION: Subclass breaks superclass contract by throwing unexpected exception
public class CustomReadOnlyList<E> extends ArrayList<E> {
    @Override
    public boolean add(E element) {
        // Contract of Collection.add() guarantees element is inserted!
        throw new UnsupportedOperationException("Read-only list!");
    }
}

// Client expecting base ArrayList contract:
void processData(List<String> list) {
    list.add("test"); // CRASHES at runtime if CustomReadOnlyList is passed!
}
The 3 Formal Rules of Barbara Liskov & Jeannette Wing (1994):
  1. Preconditions cannot be strengthened in a subtype: The subclass cannot demand stricter validation or narrower parameter ranges than the superclass.
  2. Postconditions cannot be weakened in a subtype: The subclass must guarantee at least as much outcome/state guarantee to callers as the superclass.
  3. Invariants of the supertype must be preserved: Any state constraint guaranteed by the superclass must hold before and after every public method of the subclass.

I · ISP DEEP DIVE Fat Interfaces vs. Role Interfaces

When an interface becomes "fat", it forces client classes to depend on operations they never invoke, triggering unnecessary re-compilation, bloated testing harnesses, and dummy exception throws: 

// VIOLATION: Fat Interface forcing bloated contracts
public interface MultiFunctionDevice {
    void print(Document doc);
    void scan(Document doc);
    void fax(Document doc);
    void staple(Document doc);
}

// Low-cost DeskJet Printer forced to implement irrelevant methods:
public class SimpleDeskJet implements MultiFunctionDevice {
    public void print(Document doc) { /* Print logic */ }
    public void scan(Document doc) { throw new UnsupportedOperationException("No scanner!"); }
    public void fax(Document doc) { throw new UnsupportedOperationException("No fax!"); }
    public void staple(Document doc) { throw new UnsupportedOperationException("No stapler!"); }
}

// REFACTORED: Segregated Role Interfaces
public interface Printer { void print(Document doc); }
public interface Scanner { void scan(Document doc); }
public interface FaxMachine { void fax(Document doc); }

// High-end enterprise device implements all roles:
public class EnterpriseCopier implements Printer, Scanner, FaxMachine {
    public void print(Document doc) { ... }
    public void scan(Document doc) { ... }
    public void fax(Document doc) { ... }
}

// Simple device implements only what it supports:
public class SimpleDeskJet implements Printer {
    public void print(Document doc) { /* Print logic only */ }
}
D · DIP DEEP DIVE Decoupling High-Level Business Policy from Low-Level I/O Details

Traditional software dependencies flow downwards: high-level business logic depends on mid-level algorithms, which depend on low-level database drivers and hardware I/O. DIP inverts this hierarchy: 

// VIOLATION: High-level business logic is directly coupled to low-level volatile mechanisms!
public class OrderProcessor {
    private MySQLDatabase database = new MySQLDatabase(); // Tight coupling to MySQL
    private StripePaymentGateway payment = new StripePaymentGateway(); // Tight coupling to Stripe

    public void checkout(Order order) {
        payment.charge(order.total());
        database.insertOrder(order);
    }
}

// REFACTORED: Both High-Level and Low-Level depend on Abstractions
public interface PaymentGateway {
    void processPayment(Money amount);
}

public interface OrderRepository {
    void save(Order order);
}

// High-level policy depends ONLY on stable interfaces (Constructor Injection)
public class OrderProcessor {
    private final PaymentGateway paymentGateway;
    private final OrderRepository orderRepository;

    public OrderProcessor(PaymentGateway paymentGateway, OrderRepository orderRepository) {
        this.paymentGateway = paymentGateway;
        this.orderRepository = orderRepository;
    }

    public void checkout(Order order) {
        paymentGateway.processPayment(order.total());
        orderRepository.save(order);
    }
}

The 4 Symptoms of Rotting Design

Architectural Decay
CODE SMELLS Why Good Software Degrades into Chaos
1. Rigidity

The tendency for software to be hard to change because every single change forces a cascade of subsequent changes in dependent modules. The engineer fears touching code because simple tasks explode into multi-module rewrites.

2. Fragility

The tendency for software to break in places that have no conceptual or logical relationship to the modified area. Fixes introduce new bugs elsewhere, destroying developer confidence.

3. Immobility

The inability to reuse software from other projects or parts of the same project because it cannot be disentangled from the current application context. It is easier to rewrite the code from scratch than to separate it.

4. Viscosity

Design Viscosity: When doing things the right architectural way is slow, tedious, or cumbersome, whereas applying a quick, dirty hack is instantaneous.
Environment Viscosity: When compilation, test runs, or deployment cycles take hours, encouraging engineers to make quick dirty patches rather than clean refactorings.

Formal LSP: Why Square is NOT a Rectangle

The Classic Exam Proof
CRITICAL EXAM PROOF Behavioral Subtyping vs. Mathematical Classification

In mathematics, every square is a rectangle ($is-a$). But in Object-Oriented Design, a Square cannot substitute for a Rectangle without violating LSP: 

public class Rectangle {
    protected int width, height;
    public void setWidth(int w) { this.width = w; }
    public void setHeight(int h) { this.height = h; }
    public int getArea() { return width * height; }
}

// Naive inheritance: Square maintains width == height invariant
public class Square extends Rectangle {
    @Override
    public void setWidth(int w) { this.width = w; this.height = w; }
    @Override
    public void setHeight(int h) { this.height = h; this.width = h; }
}

// Client method expecting Rectangle behavioral contract:
void verifyArea(Rectangle r) {
    r.setWidth(5);
    r.setHeight(4);
    // Rectangle Contract Postcondition: getArea() == width * height == 20
    assert r.getArea() == 20; // FAILS for Square (yields 16)!
}
The 3 Formal Rules of Barbara Liskov's Behavioral Subtyping (1987):
  1. Preconditions cannot be strengthened in a subtype: The subtype cannot demand more from callers than the supertype. If a base method accepts any integer $\ge 0$, a subclass cannot mandate integers $\ge 10$.
  2. Postconditions cannot be weakened in a subtype: The subtype must guarantee at least as much to callers as the supertype. Square weakens Rectangle's postcondition: setting height has the side effect of altering width!
  3. Invariants of the supertype must be preserved: Any condition guaranteed true before and after every public method call on the supertype must remain true for all subtypes.

Core Exam Practice & Model Solutions

Direct Question → Answer Format
Question 1: Open-Closed Principle (OCP) Sorter Refactoring 8 Points

A class DataSorter has a method sort(int[] data, SortAlgorithm algo) using a switch statement over an enum:
if (algo == BUBBLE) { ... } else if (algo == QUICK) { ... }.
Explain why this violates OCP and provide the refactored solution!

Model Answer:
  1. OCP Violation: Whenever a new sorting algorithm (e.g. MERGE_SORT) is introduced, the existing, tested DataSorter class must be modified to add a new else if branch. It is closed neither for modification nor resilient to regression.
  2. Refactoring via Strategy Pattern: 
    public interface Sorter {
    void sort(int[] data);
}

public class QuickSort implements Sorter {
    public void sort(int[] data) { /* Quicksort implementation */ }
}

public class DataSorter {
    public void sort(int[] data, Sorter sorter) {
        sorter.sort(data); // Closed for modification, open for extension!
    }
}
Question 2: Why Classic Singleton Violates SOLID Principles 6 Points

Identify and explain at least two SOLID principles that are violated by the classic Singleton pattern!

Model Answer:
  1. Single Responsibility Principle (SRP): The Singleton class is responsible for its actual domain business logic (e.g., logging, database queries) AND managing its own instantiation and lifecycle (ensuring exactly one instance). That represents two distinct reasons to change.
  2. Dependency Inversion Principle (DIP): Classes using the Singleton call Singleton.getInstance() directly, binding themselves to a concrete class rather than an abstract interface. High-level modules become tightly coupled to a low-level concrete implementation.
  3. Open-Closed Principle (OCP): A Singleton is sealed via private constructors. It cannot be extended with polymorphic alternatives (e.g., a test double or mock) without modifying all call sites throughout the application.
Question 3: Formal LSP Proof for Square and Rectangle 6 Points

Prove using postconditions why Square extending Rectangle violates the Liskov Substitution Principle!

Model Answer:

The contract of Rectangle.setWidth(w) guarantees the following postcondition: $$\text{postcondition}(Rectangle.setWidth(w)) \implies (width' = w) \land (height' = height)$$ Namely, setting the width must leave the existing height unchanged.

When Square overrides setWidth(w) to maintain its invariant ($width = height$), it sets both: $$\text{postcondition}(Square.setWidth(w)) \implies (width' = w) \land (height' = w)$$ If $w \neq height$, the postcondition guaranteed by Rectangle is broken. Any client assuming the supertype's postcondition fails, proving that Square is not a valid behavioral subtype of Rectangle.

Question 4: Can LSP Conformance Be Checked Automatically? 5 Points

Can a compiler or static analysis tool automatically verify whether a class adheres to the Liskov Substitution Principle (LSP)? Explain why or why not.

Model Answer:

NO, automated verification of LSP is theoretically impossible in the general case.

  1. Rice's Theorem / Halting Problem: Determining whether two arbitrary programs or methods produce equivalent behavioral semantics across all possible inputs is undecidable.
  2. Syntactic vs. Behavioral Subtyping: Compilers (like Java's javac) only check syntactic conformance (type signatures, parameter counts, return types). They have zero visibility into method semantics, preconditions, or side effects.
  3. Partial Runtime Mitigations: Design-by-Contract frameworks (e.g., Eiffel, JML) and runtime property-based test suites can detect individual contract violations at runtime, but no static tool can prove universal LSP adherence.
Question 5: Semantic Analysis: "This Class Adheres to the Open-Closed Principle" 5 Points

Does the statement: "This class adheres to the Open-Closed Principle" make sense as an absolute claim? Explain why or why not.

Model Answer:

NO, the statement is semantically incomplete.

  1. Closure is Never Absolute: No non-trivial class can be closed against all possible future changes. A class closed against sorting variations (e.g., via a Sorter interface) is still open to changes in logging, persistence, serialization, or multithreading.
  2. Closure is Relative to Specific Variations: Closure must always be qualified: "This class is closed against changes in the sorting algorithm, but open to new sorting implementations."
  3. Strategic Closure: Experienced architects choose which dimensions of change to close based on domain experience. Closing against every conceivable future variation produces catastrophic over-engineering.
Question 6: Enterprise Rationale: Why SRP and DIP Make Sense 5 Points

Why does the Single Responsibility Principle (SRP) make sense from an organizational perspective? Why does the Dependency Inversion Principle (DIP) make sense from an architectural perspective?

Model Answer:
  • SRP Organizational Rationale: Software changes because people request changes. Different business stakeholders (e.g., Accounting, HR, Operations, Security) have divergent, often conflicting goals. When code for multiple actors is housed in the same module, a change requested by one stakeholder risks breaking features relied upon by another. SRP aligns code boundaries with human organizational boundaries.
  • DIP Architectural Rationale: High-level business rules represent the core intellectual property and value of the enterprise. Low-level details (databases, network protocols, UI toolkits) are volatile mechanisms that change frequently. DIP prevents volatile external mechanisms from dictating the structure of precious domain rules.
