Unit 6 · Core Object-Oriented Principles

OO Principles I: SOLID & Design Smells

“The ‘bad’ patterns are unable to contain the forces which occur in them. In the end, the whole system must collapse.” — Christopher Alexander

Robert C. Martin’s (Uncle Bob) design smells that signal architectural rot, and the 5 foundational SOLID principles that counteract them.

1

6.4 The 7 Classic Design Smells

Symptoms of decaying, brittle software architectures.

1. Rigidity

The tendency for software to be difficult to change. A single simple change causes a cascade of downstream changes in dependent modules.

2. Fragility

The software breaks in unexpected places that have no conceptual relationship to the area that was modified.

3. Immobility

The inability to reuse software from other projects or parts of the same project because it is too entangled with its current context.

4. Viscosity

Doing things the right, architectural way is much harder than doing the quick-and-dirty hack or copy-pasting.

5. Needless Complexity

Contains speculative design elements that anticipate problems that never actually occur (violating YAGNI).

6. Needless Repetition

Copy-and-paste reuse, violating the DRY principle. Changes must be repeatedly applied across duplicated blocks.

7. Opacity

The tendency of a module to be difficult to read and understand. Convoluted logic and poor naming.

2

6.5 The SOLID Principles (Uncle Bob)

S SRP: Single Responsibility Principle

Rule: “A class should have one, and only one, reason to change.”

Each class should encapsulate a single actor's requirements. If a class handles business calculations, database persistence, AND GUI formatting, changes to database schema or UI layout will force modifications to the core business logic.

O OCP: Open Closed Principle

Rule: “Software entities (classes, modules, functions) should be open for extension, but closed for modification.” (Bertrand Meyer)

You should be able to extend the behavior of a module without modifying its source code. Achieved via abstraction (interfaces, abstract classes) and patterns like Strategy and Template Method.

L LSP: Liskov Substitution Principle

Rule: “Subtypes must be substitutable for their base types without altering program correctness.” (Barbara Liskov)

The Classic Counterexample: The Rectangle and Square Problem

In mathematics, a Square is a kind of Rectangle. But in object-oriented programming: 

void clientFunction(Rectangle r) {
    r.setWidth(5);
    r.setHeight(4);
    assert(r.getArea() == 20); // FAILS IF r IS A SQUARE!
}

If Square extends Rectangle, setWidth(5) sets both width and height to 5. Then setHeight(4) sets both to 4! The assertion fails. Subtypes must honor all behavioral guarantees of the parent.

I ISP: Interface Segregation Principle

Rule: “Clients should not be forced to depend upon interfaces that they do not use.”

Many client-specific interfaces are much better than one bloated "fat" interface. Avoid "God Interfaces" that bundle printer, scanner, fax, and staple operations together when a client only wants to print.

D DIP: Dependency Inversion Principle

Rule:

  1. High-level modules should not depend on low-level modules. Both should depend on abstractions.
  2. Abstractions should not depend on details. Details (concrete implementations) should depend on abstractions.

6.7 Questions for Self-Study (Exam Practice)

Self-Study Q1 Explain why "A Square is a Rectangle" fails under the Liskov Substitution Principle (LSP).

In mathematics, a square has an invariant that width equals height. But a Rectangle class in software asserts an independent postcondition: after setWidth(w), the height remains unchanged.

A Square subclass cannot preserve this postcondition without violating its own invariant. Because the Square subclass breaks the behavioral contract expected by clients of Rectangle, it violates LSP. IS-A relationship in real life does not equal IS-A in software behavior!
