PILLAR 01 · FOUNDATIONAL INTENT

Intent & Architectural Forces

Decorator Pattern (GoF Wrapper)

Intent: Attach additional responsibilities to an object dynamically at runtime. Decorators provide a flexible, composable alternative to subclassing for extending functionality.

The Core Dilemma: Subclass explosion. In the famous Starbuzz Coffee example, combining 4 beverages with 5 condiments statically requires $4 \times 2^5 = 128$ subclasses! Decorator eliminates this by turning condiments into transparent wrapping layers.

Adapter Pattern (GoF Wrapper / Translator)

Intent: Convert the interface of a class into another interface clients expect. Adapter lets classes work together that couldn't otherwise because of incompatible interfaces.

The Core Dilemma: Legacy integration drift. An enterprise billing system expects a modern PaymentProcessor interface, but a legacy mainframe vendor provides an obsolete OldCobolGateway with mismatched method names and argument types.

PILLAR 03 · DYNAMIC DELEGATION

Dynamic Call Onion & Delegation Chains

The Decorator "Call Onion"

When the client invokes beverage.cost() on a beverage wrapped in multiple decorators:

  1. Client calls outermost decorator: Whip.cost().
  2. Whip delegates to its inner wrapped reference: Mocha.cost().
  3. Mocha delegates to the core component: DarkRoast.cost() ($\$1.99$).
  4. Call returns back up the onion stack:
    • DarkRoast returns $\$1.99$.
    • Mocha adds $\$0.20 \to \$2.19$.
    • Whip adds $\$0.10 \to \$2.29$ total!

The Adapter Delegation Bridge

Adapter does not augment behavior; it performs translation:

  1. Client calls target standard: paymentGateway.pay(Money.euros(50)).
  2. StripeAdapter intercepts the call.
  3. Translates object domain types into legacy primitives: converts Money.euros(50) to cents = 5000, currency = "eur".
  4. Invokes adaptee.chargeStripeToken("tok_123", 5000, "eur").
  5. Maps response back into target domain response.

PILLAR 05 · STRUCTURAL ECOSYSTEM

Structural Pattern Distinctions: Decorator vs Adapter vs Proxy vs Strategy

Decorator vs. Strategy ("Skin vs. Guts")

As Erich Gamma famously stated: "Decorator changes the skin of an object; Strategy changes its guts." Decorator wraps the outside transparently; Strategy swaps the internal algorithmic engine from within.

Decorator vs. Proxy

Both wrap an object and implement the exact same interface! The critical difference lies in Intent: Decorator adds new functional responsibilities; Proxy controls access, manages lazy instantiation lifecycle, or adds security without altering business capabilities.

Decorator vs. Adapter

Adapter changes the interface so the client can talk to an alien class. Decorator retains the identical interface so the client never knows the object was wrapped.

Decorator vs. Composite (Unit 3)

A Decorator can be viewed as a degenerate 1-child Composite: both share the component interface, but a Composite holds $N$ children to represent part-whole hierarchies, while a Decorator wraps exactly $1$ child to add behavior.

PILLAR 06 · SMELLS & CLASS EXPLOSION

Architectural Smells & Production Red Flags

1. Subclass Explosion (The Combinatorial Trap)

Creating subclasses like `BufferedEncryptedCompressingOutputStream`. Each new orthogonal feature multiplies the class hierarchy exponentially.

Remedy: Decorator Pattern wraps single-responsibility layers dynamically.
2. Type-Checking Breakage (`instanceof` Trap)

Client code executing `if (beverage instanceof DarkRoast)` fails silently when `DarkRoast` is wrapped inside `MochaDecorator`.

Remedy: Program strictly to the interface, never to concrete types.
3. Verbose Instantiation Boilerplate

Constructing 7 nested decorators by hand in client controller code: `new A(new B(new C(new D())))`.

Remedy: Encapsulate onion construction inside a Factory or Fluent Builder.
4. Two-Way Interface Drift

When both client and server update independently and the adapter becomes a tangled mess of bidirectional if/else type checks.

Remedy: Explicit Two-Way Adapter or Anti-Corruption Layer (DDD).
PILLAR 07 · PRODUCTION CODE STANDARD

Modern Enterprise HTTP Client Decorator Pipeline

HttpClientPipeline.java · Decorator Architecture 
package de.frankfurt.uas.posa.flexibility;

public interface HttpClient {
    HttpResponse execute(HttpRequest request);
}

// Concrete Component: Pure network socket execution
public class CoreNetworkClient implements HttpClient {
    @Override
    public HttpResponse execute(HttpRequest request) {
        return SocketEngine.dispatch(request);
    }
}

// Abstract Decorator Base
public abstract class HttpClientDecorator implements HttpClient {
    protected final HttpClient inner;
    protected HttpClientDecorator(HttpClient inner) { this.inner = inner; }
    @Override
    public HttpResponse execute(HttpRequest request) {
        return inner.execute(request);
    }
}

// Concrete Decorator: Automated Retry on 5xx Errors
public class RetryDecorator extends HttpClientDecorator {
    private final int maxRetries;
    public RetryDecorator(HttpClient inner, int maxRetries) {
        super(inner); this.maxRetries = maxRetries;
    }
    @Override
    public HttpResponse execute(HttpRequest request) {
        for (int i = 0; i < maxRetries; i++) {
            HttpResponse res = super.execute(request);
            if (res.statusCode() < 500) return res;
        }
        throw new ServiceUnavailableException("Retries exhausted");
    }
}
PILLAR 08 · EXAM TRAPS & DEFENSE

Frankfurt UAS Examination Pitfalls (Prof. Dr. Jörg Schäfer)

Exam Trap 1: "Why can't Java use Class Adapters?"

Schäfer's Trap: "Implement a Class Adapter in Java by inheriting from both the Target class and the Adaptee class."
Correct UAS Defense: Java does not support multiple class inheritance! A class can extend only one superclass. Therefore, in Java, Class Adapters are only possible if Target is an interface, or you must use Object Adapter (composition), which also adheres to the core principle: "Favor object composition over class inheritance."

Exam Trap 2: Decorator vs Proxy Distinction

Schäfer's Trap: "Both Decorator and Proxy wrap an object and implement its interface. Are they identical?"
Correct UAS Defense: No! Patterns are defined by Intent, not class diagram topology. Decorator augments new dynamic responsibilities. Proxy manages access control, lazy initialization, or remote distribution without changing or augmenting the business behavior of the underlying component.

Adapter Topology: Object vs. Class Adapter

The Adapter pattern bridges the gap between what an enterprise client needs and what an existing component provides:

1. Object Adapter (Composition)

Implements the Target interface and references the Adaptee via an instance field.

  • Advantage: Can adapt an Adaptee and any of its subclasses polymorphically.
  • Advantage: 100% compliant with single-inheritance languages like Java and C#.

2. Class Adapter (Multiple Inheritance)

Inherits publicly from Target and privately/publicly from Adaptee.

  • Advantage: Can override Adaptee behavior directly without forwarding calls.
  • Disadvantage: Impossible in Java/C# unless Target is a pure interface; commits statically to one concrete Adaptee class.

STAGE 04 OF 05 · PRODUCTION ARCHITECTURE

Real-World Case Study: java.io Stream Pipeline

The Java standard library’s java.io package is the most prominent decorator architecture in software engineering history:

LowerCaseInputStream.java · Custom java.io Decorator 
package de.frankfurt.uas.posa.streams;

import java.io.*;

// Concrete Decorator extending FilterInputStream (Decorator Base)
public class LowerCaseInputStream extends FilterInputStream {

    public LowerCaseInputStream(InputStream in) {
        super(in); // wraps core component
    }

    @Override
    public int read() throws IOException {
        int c = super.read();
        return (c == -1 ? c : Character.toLowerCase((char) c));
    }

    @Override
    public int read(byte[] b, int offset, int len) throws IOException {
        int result = super.read(b, offset, len);
        for (int i = offset; i < offset + result; i++) {
            b[i] = (byte) Character.toLowerCase((char) b[i]);
        }
        return result;
    }
}

Frankfurt UAS Examination Drills (Prof. Dr. Jörg Schäfer)

Authentic Exam Paper · Question 6 [4 Pts] Which of the OOP principles does Decorator primarily follow: Inheritance or Composition, and briefly explain why?

Official Model Answer & Grading Rubric (Prof. Dr. Jörg Schäfer):

The Decorator pattern primarily follows Composition (delegation), not inheritance.

  1. Dynamic Behavioral Delegation (Composition): The decorator maintains a private reference to a wrapped Component instance and augments behavior before or after forwarding calls at runtime. This avoids the combinatorial explosion of subclasses required by pure inheritance.
  2. Type Conformance Only (Subtyping): Inheritance from the abstract Component type is employed strictly for interface conformance and type substitutability (so decorators can substitute transparently for components), NOT for behavioral code reuse.
Exam Drill 2 · Architectural Comparison Explain the famous quote: "Decorator changes the skin of an object; Strategy changes its guts."

Official Model Answer:

A Decorator wraps an object from the outside. Both the decorator and the component share the identical supertype, and client requests pass through the decorator before reaching the component (changing the "skin").

A Strategy modifies an object from the inside. The Context holds a reference to a Strategy interface and delegates algorithmic computations to it internally (changing the "guts").

Exam Drill 2 · Liabilities Name two critical disadvantages of the Decorator pattern.

Official Model Answer:

  1. Loss of Type Identity: Code relying on concrete types (e.g. beverage instanceof DarkRoast) will fail once wrapped by a decorator because the outermost reference is now of type MochaDecorator.
  2. Proliferation of Tiny Objects: As demonstrated in java.io, simple operations require instantiating numerous small wrapper objects, complicating initialization and producing long debugging stack traces.
Exam Drill 3 · Adapter Varieties Why is an Object Adapter generally preferred over a Class Adapter in modern software engineering?

Official Model Answer:

An Object Adapter utilizes composition: it references an instance of Adaptee. This adheres to the fundamental principle: "Favor object composition over class inheritance." It enables adapting not only the specific Adaptee class, but any of its subclasses dynamically at runtime. A Class Adapter relies on multiple inheritance, binding statically to one concrete class and failing in single-inheritance languages like Java.
