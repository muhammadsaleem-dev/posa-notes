Unit 9 · Structural Design Patterns · Wrappers

Flexibility Patterns: Decorator, Adapter & Facade

Master runtime responsibility augmentation (Decorator), interface translation (Adapter), and subsystem simplification (Facade). Solve the subclass explosion dilemma and eliminate rigid inheritance hierarchies.

⚡ Executive Summary Flexibility Patterns: Structural Wrappers & Decoupling
Collapse Expand

“Combine structural patterns to dynamically extend, adapt, and decouple classes without triggering subclass explosion.”

🎯 The Structural Wrapper Trinity (Intent Matters!)

Decorator, Adapter, and Proxy share identical wrapper structures, but their intents differ: Adapter converts interfaces; Decorator dynamically adds behavior; Proxy controls access to the subject.

→ Never classify a pattern by its UML diagram alone; classify by its intent.
🕵️‍♂️ Bridge: Decoupling Abstraction from Implementation

Bridge separates an abstraction hierarchy from its implementation hierarchy, allowing both to vary independently along orthogonal dimensions (e.g. Window GUI vs. OS Platform).

→ Prevents cartesian product subclass explosion (M × N).

Pattern Profiles & Architectural Intent

The Wrapper Family
1. Decorator Pattern: "Attach additional responsibilities to an object dynamically. Decorators provide a flexible alternative to subclassing for extending functionality."
Key Trait: Decorator wraps an object having the same supertype interface, maintaining transparent compatibility while intercepting calls.
2. Adapter Pattern: "Convert the interface of a class into another interface clients expect. Adapter lets classes work together that couldn't otherwise because of incompatible interfaces."
Key Trait: Adapter wraps an adaptee to change its interface into a target interface.
3. Facade Pattern: "Provide a unified interface to a set of interfaces in a subsystem. Facade defines a higher-level interface that makes the subsystem easier to use."
Key Trait: Simplifies a complex subsystem for casual clients (Principle of Least Knowledge / Law of Demeter).

Minimal Architecture & Clean Code

The Starbuzz Coffee Onion in < 30 Lines
☕ Clean Decorator Implementation
Head First Starbuzz 
// 1. Component
public abstract class Beverage {
    public abstract String getDescription();
    public abstract double cost();
}

// 2. Concrete Component
public class Espresso extends Beverage {
    public String getDescription() { return "Espresso"; }
    public double cost() { return 1.99; }
}

// 3. Decorator Base (is-a Beverage and has-a Beverage!)
public abstract class CondimentDecorator extends Beverage {
    protected final Beverage beverage;
    public CondimentDecorator(Beverage beverage) { this.beverage = beverage; }
}

// 4. Concrete Decorators
public class Mocha extends CondimentDecorator {
    public Mocha(Beverage beverage) { super(beverage); }
    public String getDescription() { return beverage.getDescription() + ", Mocha"; }
    public double cost() { return beverage.cost() + 0.20; } // Delegation chain!
}

public class Whip extends CondimentDecorator {
    public Whip(Beverage beverage) { super(beverage); }
    public String getDescription() { return beverage.getDescription() + ", Whip"; }
    public double cost() { return beverage.cost() + 0.10; }
}

// 5. Client Assembly: The "Call Onion"
// Cost: 1.99 (Espresso) + 0.20 (Mocha) + 0.10 (Whip) = $2.29
Beverage order = new Whip(new Mocha(new Espresso()));

Core Exam Practice & Model Solutions

Direct Question → Answer Format
Question 1: Why Prefer Decorator Over Class Inheritance? 3 Points

Why does object composition via the Decorator pattern provide superior flexibility compared to class inheritance when augmenting behavior?

Model Answer:
  1. Prevents Subclass Explosion: With inheritance, every combination of optional features requires a dedicated subclass ($2^N$ combinatorial classes, e.g. EspressoWithMochaAndWhip). Decorator requires only $N$ decorator classes composed dynamically at runtime.
  2. Dynamic Runtime Mutability: Inheritance binds behavior statically at compile-time. Decorators can be attached, combined in arbitrary orders, and removed dynamically during execution.
  3. Single Responsibility & OCP: Concrete components focus purely on their core functionality without being bloated with optional features; new decorators can be added without altering existing components (Open-Closed Principle).
Question 2: Object Adapter vs. Class Adapter 4 Points

Contrast an Object Adapter with a Class Adapter. Which is preferred in Java and why?

Model Answer:
  • Object Adapter (Composition): The adapter implements the target interface and holds a reference to the adaptee (has-a). It delegates requests to the adaptee object. Preferred because it adheres to "favor composition over inheritance" and can adapt not only the adaptee class, but any of its subclasses.
  • Class Adapter (Multiple Inheritance): The adapter inherits from both the target interface and the adaptee class (is-a). Requires multiple implementation inheritance, which is unsupported in Java (Java only permits single class inheritance).
