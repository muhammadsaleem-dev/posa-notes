Composite Pattern

Master part-whole object hierarchies, recursive aggregation, and the fundamental trade-off between Transparency and Safety. Essential for recursive UI menus, graphics hierarchies, and arithmetic expression trees.

⚡ Executive Summary Composite Pattern: Uniform Part-Whole Hierarchies
Collapse Expand

“Treat individual objects and compositions of objects uniformly. Clients interact with primitives and containers identically.”

🎯 Recursive Structural Uniformity

Both Leaf objects and Composite containers implement the same Component interface. A composite transparently forwards operations recursively across all child elements.

→ Eliminates instanceof checks and nested branching in client code.
🕵️‍♂️ Transparency vs. Safety Trade-off

Defining child management (add/remove) in Component provides transparency (uniform client treatment) but sacrifices compile-time safety (Leaf throws UnsupportedOperationException).

→ Core architectural trade-off tested on exams.
Composite Pattern Role Matrix
Concept / Pattern Architectural Mechanism Why It Matters in Practice & Exams
Component Interface Common abstraction Declares operations common to both leaves and composites.
Leaf Atomic node Implements primitive behavior; possesses no children.
Composite Container node Stores child components; recursively delegates operations to children.
1

Pattern Profile & Canonical UML Architecture

Core GoF Specification
Name: Composite Pattern
Type: Structural Pattern — focuses on how classes and objects are composed to form larger structures while keeping them flexible and efficient.
Policy: "Compose objects into tree structures to represent part-whole hierarchies. Composite lets clients treat individual objects and compositions of objects uniformly."
Problem: In recursive tree structures (like menus with submenus or expressions with sub-expressions), client code must constantly check whether a node is a leaf or a composite (e.g. via instanceof). This introduces conditional branching, tight coupling to concrete types, and fragile code whenever new elements are added.
Solution: Define a common Component abstraction implemented by both individual elements (Leaf) and container elements (Composite). The Composite holds a collection of Component references (recursive composition) and delegates operations down to all children.
📐 Canonical Architecture: Figure 3.1 Composite Structure
👥 The 3 Core Participants
Participant Role Key Characteristic
Component Abstract supertype declaring common interface for all nodes in the tree. Declares core business operation (e.g. print(), evaluate()) and child management.
Leaf Represents leaf objects in the composition. A leaf has no children. Defines behavior for primitive objects. Throws exception or ignores child management calls.
Composite Defines behavior for components having children and stores child components. Implements operation() by recursively iterating over its children collection.

Head First & Expression Tree Walkthroughs

Concrete Implementations
🍽️ Domain 1: Head First Diner Menus & Submenus
MenuComponent Hierarchy

A restaurant menu can contain both single MenuItem leaves (e.g. Pasta, Pancake) and full sub-Menu composites (e.g. Dessert Menu, Dinner Menu). The client (the Waitress) needs only one call: allMenus.print(). 

// 1. Abstract Component base class
public abstract class MenuComponent {
    public void add(MenuComponent c) { throw new UnsupportedOperationException(); }
    public void remove(MenuComponent c) { throw new UnsupportedOperationException(); }
    public MenuComponent getChild(int i) { throw new UnsupportedOperationException(); }
    public String getName() { throw new UnsupportedOperationException(); }
    public double getPrice() { throw new UnsupportedOperationException(); }
    public void print() { throw new UnsupportedOperationException(); }
}

// 2. Leaf (MenuItem)
public class MenuItem extends MenuComponent {
    private String name;
    private double price;
    public MenuItem(String name, double price) { this.name = name; this.price = price; }
    public String getName() { return name; }
    public double getPrice() { return price; }
    public void print() { System.out.println("  " + getName() + ", $" + getPrice()); }
}

// 3. Composite (Menu)
public class Menu extends MenuComponent {
    private List<MenuComponent> children = new ArrayList<>();
    private String name;
    public Menu(String name) { this.name = name; }
    public void add(MenuComponent c) { children.add(c); }
    public void print() {
        System.out.println("\n--- " + name + " ---");
        for (MenuComponent child : children) {
            child.print(); // Recursive delegation!
        }
    }
}
🧮 Domain 2: Arithmetic Expression Tree (Exam Topic)
Expression Evaluation

Evaluating mathematical expressions like $3 + 4 * (5 - 6 * z / (x + y))$ is the canonical exam use-case for the Composite pattern. Operands (constants and variables) are Leaves, while operators ($+$, $-$, $*$, $/$) are Composites. 

// 1. Component
public interface Expression {
    double evaluate(Map<String, Double> context);
}

// 2. Leaves (Operands)
public class Constant implements Expression {
    private final double value;
    public Constant(double value) { this.value = value; }
    public double evaluate(Map<String, Double> ctx) { return value; }
}

public class Variable implements Expression {
    private final String name;
    public Variable(String name) { this.name = name; }
    public double evaluate(Map<String, Double> ctx) { return ctx.get(name); }
}

// 3. Composite (Binary Operator)
public abstract class BinaryOperator implements Expression {
    protected final Expression left;
    protected final Expression right;
    public BinaryOperator(Expression left, Expression right) {
        this.left = left; this.right = right;
    }
}

public class Add extends BinaryOperator {
    public Add(Expression left, Expression right) { super(left, right); }
    public double evaluate(Map<String, Double> ctx) {
        return left.evaluate(ctx) + right.evaluate(ctx); // Recursive delegation
    }
}

public class Multiply extends BinaryOperator {
    public Multiply(Expression left, Expression right) { super(left, right); }
    public double evaluate(Map<String, Double> ctx) {
        return left.evaluate(ctx) * right.evaluate(ctx); // Recursive delegation
    }
}

Transparency vs. Safety Trade-off

The #1 Architectural Dilemma
CRITICAL EXAM AXIOM Transparency vs. Safety

In the Composite pattern, there is a fundamental conflict between the Single Responsibility Principle (SRP) / Interface Segregation Principle (ISP) and uniformity of treatment:

Transparency (GoF Preference)

  • Approach: Define child management methods (add, remove, getChild) in the abstract Component base class.
  • Advantage: Maximum uniformity. Clients treat Leaves and Composites completely identically; zero downcasting or instanceof checks required.
  • Disadvantage: Loss of compile-time safety. Leaf nodes inherit operations that are meaningless for them and must throw runtime exceptions (e.g. UnsupportedOperationException). Violates LSP and ISP.

Safety (Java API Preference)

  • Approach: Define child management methods only on the concrete Composite class. Component only declares business operations (operation()).
  • Advantage: Type-safe at compile-time. Impossible to call add() on a Leaf; compiler rejects it outright. Adheres to ISP.
  • Disadvantage: Loss of transparency. Clients cannot treat all nodes uniformly. To add children, client must downcast using ((Composite) node).add(child) or inspect types with instanceof.
💡 Exam Rule: Gang of Four emphasizes Transparency because treating leaf and composite identically is the primary purpose of the pattern, even if it trades away compile-time type safety.

Core Exam Practice & Model Solutions

Direct Question → Answer Format
Question 1: Expression Tree Construction 4 Points

Given the mathematical expression: $$3 + 4 * (5 - 6 * z / (x + y))$$ Draw the expression tree according to standard operator precedence and parentheses!

Model Answer:

Following standard precedence (parentheses first, then multiplication/division left-to-right, then addition/subtraction): 

                     (+)
                    /   \
                   3     (*)
                        /   \
                       4     (-)
                            /   \
                           5     (/)
                                /   \
                              (*)   (+)
                              / \   / \
                             6   z x   y

• Root: The outermost addition ($+$), combining $3$ and the right-hand multiplication subtree.
• Inner Division: Subtree $(6 * z) / (x + y)$.
• Leaves: Operands $3, 4, 5, 6, z, x, y$.

Question 2: UML Class Diagram for Expression Evaluation 4 Points

Complete the UML class diagram for the Composite pattern to represent and evaluate such expressions. Identify the abstract Component, the Leaf classes, and the Composite operator classes!

Model Answer:
  1. Abstract Component: abstract class Expression
    • Method: + evaluate(context: Map<String, Double>): double
  2. Leaves:
    • Constant: holds value: double; evaluate() returns value.
    • Variable: holds name: String; evaluate() looks up context.get(name).
  3. Composite (Operator):
    • abstract class BinaryOperator extends Expression: holds left: Expression, right: Expression (Aggregation association back to Expression).
    • Concrete subclasses: Add, Subtract, Multiply, Divide each implement evaluate() by recursively evaluating left and right child nodes.
Question 3: How Composite Enables Expression Evaluation 6 Points

Explain how the Composite pattern enables the evaluation of the expression in your own words using the (completed) UML diagram!

Model Answer:

The Composite pattern enables expression evaluation through polymorphic recursive delegation:

  1. Uniform Treatment: The client triggers evaluation by calling evaluate(context) on the root node (e.g. Add). The client does not need to know whether the node is an operator or a simple operand.
  2. Recursive Delegation: Each BinaryOperator composite implements evaluate() by recursively calling left.evaluate(context) and right.evaluate(context). It then applies its specific arithmetic operation (e.g., $+$, $*$) to the two returned scalar values.
  3. Base Case Termination: When recursion reaches a Constant or Variable (Leaf), no further delegation occurs:
    • Constant returns its stored numerical value directly.
    • Variable looks up its variable name in the provided context map.
  4. Extensibility: New operators (e.g., Power, Modulo, or unary functions like Sin, Cos) can be introduced without modifying existing leaf classes or client evaluation code, satisfying the Open-Closed Principle.
