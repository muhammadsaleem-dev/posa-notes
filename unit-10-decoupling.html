Decoupling Patterns: Observer & Mediator

Master one-to-many publish-subscribe communication, Push vs. Pull notification models, the Lapsed Listener memory leak hazard, and Mediator coordination hubs.

⚡ Executive Summary Decoupling Patterns: Observer & Mediator Topologies
Collapse Expand

“Decouple senders from receivers. Replace tangled M-to-N dependencies with clean event broadcasting or centralized coordination.”

🎯 Observer: 1-to-Many Publish/Subscribe

The Subject maintains an observer registry. When state changes, it notifies observers without knowing their concrete types. Observers can pull updated state or receive push event payloads.

→ Beware the Lapsed Listener problem: unregister observers to avoid memory leaks.
🕵️‍♂️ Mediator: Many-to-Many Hub Coordination

Mediator encapsulates complex interactions between colleagues. Instead of colleagues referencing each other directly (tangled mesh), all communication routes through the central mediator hub.

→ Centralizes control logic at the expense of a potentially complex mediator.
Decoupling Patterns Comparison Matrix
Concept / Pattern Architectural Mechanism Why It Matters in Practice & Exams
Observer 1-to-Many Broadcast Subject publishes state events; observers subscribe and react autonomously.
Mediator Many-to-Many Hub Colleagues communicate strictly through a central mediator; eliminates cyclic colleague meshes.
Exam Pitfall Memory Leaks & Cycles Unregistered observers prevent garbage collection; cascading mediator events can trigger infinite loops.

Pattern Profiles & Architectural Intent

Publish-Subscribe & Centralized Hubs
1. Observer Pattern (Publish-Subscribe): "Define a one-to-many dependency between objects so that when one object changes state, all its dependents are notified and updated automatically."
Core Forces: Decouples the state-holder (Subject) from observers. Subject knows only that observers implement the Observer interface.
2. Mediator Pattern: "Define an object that encapsulates how a set of objects interact. Mediator promotes loose coupling by keeping objects from referring to each other explicitly."
Core Forces: Transforms an unmaintainable $N \times N$ mesh network into a clean 1-to-N hub-and-spoke architecture.

Minimal Architecture & Clean Code

The Head First Weather Station
🌦️ Head First WeatherData Subject & Display
< 30 Lines 
public interface Subject {
    void registerObserver(Observer o);
    void removeObserver(Observer o);
    void notifyObservers();
}

public interface Observer {
    void update(float temp, float humidity, float pressure); // Push model
}

public class WeatherData implements Subject {
    private final List<Observer> observers = new ArrayList<>();
    private float temperature, humidity, pressure;

    public void registerObserver(Observer o) { observers.add(o); }
    public void removeObserver(Observer o) { observers.remove(o); }

    public void notifyObservers() {
        for (Observer o : observers) {
            o.update(temperature, humidity, pressure); // Broadcast state
        }
    }

    public void setMeasurements(float temp, float humidity, float pressure) {
        this.temperature = temp;
        this.humidity = humidity;
        this.pressure = pressure;
        notifyObservers();
    }
}

Push vs. Pull Models & The Lapsed Listener Leak

Key Architectural Considerations
DESIGN DECISION Push vs. Pull Notification Models
Push Model: update(state)

Subject pushes all altered data as arguments in the update(...) method call. Observers get data instantly, but interface is brittle: whenever new state fields are added, the update() signature must change.

Pull Model: update(Subject s)

Subject passes itself or notifies with zero arguments. Each observer queries (pulls) only the specific properties it cares about via getters (subject.getTemperature()). More resilient and loosely coupled.

CRITICAL MEMORY HAZARD The Lapsed Listener Problem

When an observer registers with a long-lived subject, the subject holds a strong reference to that observer. If the observer reaches the end of its lifecycle in the UI but fails to call removeObserver(), the Garbage Collector cannot reclaim it! The unreferenced observer lingers in memory, receives unneeded notifications, and causes memory exhaustion.
Solutions: Mandatory unregistration in lifecycle teardown, or using WeakReference<Observer> in the subject's observer list.

Core Exam Practice & Model Solutions

Direct Question → Answer Format
Question 1: Push vs. Pull in Observer Pattern 4 Points

Explain the difference between Push and Pull communication in the Observer pattern. Why is the Pull model often preferred in complex systems?

Model Answer:
  • Push: The subject sends all updated data as method arguments to update(...). This forces the subject to anticipate what every observer needs.
  • Pull: The subject only notifies observers that a change occurred (e.g. update(this)). Each observer then queries only the subset of state it requires via public getters.
  • Why Pull is Preferred: Pull decouples the notification interface from the data schema. If the subject gains new fields, observers that don't need those fields are unaffected, adhering to the Open-Closed and Interface Segregation principles.
Question 2: What is the "Lapsed Listener" Problem? 4 Points

Describe the Lapsed Listener problem in Java listener/observer architectures and explain how it leads to memory leaks.

Model Answer:

The Lapsed Listener problem occurs when an observer registers with a long-lived publisher/subject and is subsequently discarded by client code without explicitly unregistering. Because the subject maintains an internal list containing a strong reference to the listener, the Java Garbage Collector considers the listener reachable and cannot free its memory, producing a classic Java memory leak.
