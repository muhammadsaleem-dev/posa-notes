PILLAR 1 OF 8 · INTENT & MOTIVATION

Publish-Subscribe & Request Delegation

Hardcoding dependencies between event producers and consumers paralyzes codebases. Decoupling patterns allow systems to broadcast state changes to dynamic sets of listeners or route incoming requests through an extensible handler pipeline.

Observer Intent

Define a one-to-many dependency between objects so that when one object changes state, all its dependents are notified and updated automatically.

Chain of Responsibility Intent

Avoid coupling the sender of a request to its receiver by giving more than one object a chance to handle the request. Chain receiving objects and pass the request along the chain.

PILLAR 2 OF 8 · PARTICIPANTS & ROLES

Structural Roles & Responsibilities

Pattern Participant Architectural Responsibility
Observer Subject (Publisher) Maintains registry of observers; provides attach, detach, and notifyObservers.
Observer Observer (Subscriber) Declares update callback (Push: update(data), Pull: update(subject)).
Chain of Resp. Handler (Abstract) Defines an interface for handling requests; holds a reference to the successor.
Chain of Resp. ConcreteHandler Handles requests it is responsible for, or forwards them to its successor in the pipeline.
PILLAR 3 OF 8 · FORMAL UML ANATOMY

Vector SVG UML: Observer & Subject Topology

PILLAR 4 OF 8 · DESIGN PRINCIPLES

Loose Coupling & The Hollywood Principle

Loose Coupling Principle

Strive for loosely coupled designs between objects that interact. Subject knows only that observers implement the Observer interface.

The Hollywood Principle

“Don’t call us, we’ll call you.” Low-level observers never poll high-level subjects; subjects invoke observers asynchronously.

Single Responsibility in Pipelines

Chain of Responsibility isolates individual validation, authentication, or logging tasks into separate handlers.

PILLAR 5 OF 8 · IMPLEMENTATION MECHANICS

Push vs Pull & WeakReference Cleanup

WeakObserverList.java · Preventing Leaks
// Solution to Lapsed Listener Problem: Weak References
public class SafeSubject {
    // WeakHashMap or List> prevents GC retention!
    private final List<WeakReference<Observer>> observers = new ArrayList<>();

    public void register(Observer o) {
        observers.add(new WeakReference<>(o));
    }

    public void notifyObservers() {
        observers.removeIf(ref -> ref.get() == null); // Purge collected listeners
        for (WeakReference<Observer> ref : observers) {
            Observer o = ref.get();
            if (o != null) o.update(this); // Clean Pull Model!
        }
    }
}
PILLAR 6 OF 8 · COSTS & TRADE-OFFS

Architectural Trade-offs

✅ Decoupling Benefits
  • Add/remove subscribers dynamically at runtime without restarting servers.
  • Open/Closed Principle: Add new displays or processors with zero changes to Subject.
  • Chain of Responsibility permits dynamic pipeline re-ordering.
⚠️ Architectural Liabilities
  • Lapsed Listener memory leaks: Discarded listeners remain in memory forever.
  • Unpredictable update orders: Observers cannot rely on execution sequencing.
  • Cascading update storms if an observer modifies subject state inside update().

PILLAR 8 OF 8 · EXAM TRAPS & BENCHMARKS

Prof. Schäfer Exam Traps: The Lapsed Listener Leak

🚨 Frankfurt UAS Exam Trap #1: The Lapsed Listener Problem

Question: "Why does an application running the Observer pattern eventually crash with an OutOfMemoryError if listeners are not explicitly deregistered?"
Model Answer: The Subject holds strong references to all registered Observers in its internal collection. Even if client code discards its own references to an observer, the Subject’s strong reference keeps the observer alive as a GC root, preventing garbage collection. Over time, millions of dead listeners accumulate, exhausting heap memory.

JDK Benchmark: java.util.concurrent.Flow, javax.servlet.Filter, java.awt.event.ActionListener.

● Stage 01 · Problem Space & Event Coupling

The Weather-O-Rama Disaster

Weather-O-Rama contracts you to build their next-generation weather monitoring station. Whenever new sensor measurements (temperature, humidity, pressure) arrive, multiple visual displays (Current Conditions, Statistics, Forecast) must be updated.

BrittleWeatherData.java · The Anti-Pattern
// ANTI-PATTERN: Direct hardcoded coupling to concrete display classes!
public class WeatherData {
    private CurrentConditionsDisplay currentDisplay = new CurrentConditionsDisplay();
    private StatisticsDisplay statsDisplay = new StatisticsDisplay();
    private ForecastDisplay forecastDisplay = new ForecastDisplay();

    public void measurementsChanged() {
        float temp = getTemperature();
        float humidity = getHumidity();
        float pressure = getPressure();

        // Rigid, closed for extension:
        currentDisplay.update(temp, humidity, pressure);
        statsDisplay.update(temp, humidity, pressure);
        forecastDisplay.update(temp, humidity, pressure);
        // Adding a 4th display requires modifying WeatherData source code!
    }
}
🧠 Key Takeaways: Broadcast Decoupling Axioms
Subject Independence

The Subject holds only an interface reference. It has zero knowledge of concrete display classes or how many listeners exist.

Push vs Pull Trade-off

Push sends all data attributes to everyone. Pull passes the Subject reference, allowing subscribers to query only needed state.

Lifecycle Discipline

Always deregister listeners upon teardown, or use weak references to eliminate the Lapsed Listener memory leak.

● Stage 04 · Enterprise Production Code

Production Code: Clean Observer & Pipelines

Here is the production implementation of the Observer pattern using the Pull Model, giving subscribers full autonomy over data extraction.

WeatherData.java · Clean Pull Model
package de.frankfurt.posa.decoupling;

import java.util.List;
import java.util.concurrent.CopyOnWriteArrayList;

public class WeatherData implements Subject {
    // CopyOnWriteArrayList allows safe concurrent registration/removal during notification
    private final List<Observer> observers = new CopyOnWriteArrayList<>();
    private float temperature;
    private float humidity;
    private float pressure;

    @Override
    public void registerObserver(Observer o) {
        observers.add(o);
    }

    @Override
    public void removeObserver(Observer o) {
        observers.remove(o);
    }

    @Override
    public void notifyObservers() {
        // Clean Pull Model: Passes 'this' so observers query only what they need!
        for (Observer observer : observers) {
            observer.update(this);
        }
    }

    public void setMeasurements(float temperature, float humidity, float pressure) {
        this.temperature = temperature;
        this.humidity = humidity;
        this.pressure = pressure;
        notifyObservers();
    }

    // Getters for Pull Model
    public float getTemperature() { return temperature; }
    public float getHumidity() { return humidity; }
    public float getPressure() { return pressure; }
}

Exam Drill 1 Explain the "Lapsed Listener Problem". How does it cause memory leaks in managed runtimes (Java/C#)? (10 Exam Points)

Model Answer (Prof. Schäfer 1.0 Standard):

In the Observer pattern, a Subject maintains a list of registered Observers. This list holds strong references to each observer instance.

When an observer's active lifecycle ends (e.g., a GUI window is closed by the user), the client application discards its reference to the window. However, because the long-lived Subject still holds a reference in its listener collection, the Garbage Collector sees the observer as reachable from a GC root and cannot reclaim its memory.

Architectural Solutions:

  1. Explicit lifecycle deregulation: Ensure removeObserver(this) is invoked on window close / component unmount.
  2. Weak References: Maintain listener lists using WeakReference<Observer> so listeners can be collected when no other strong references exist.
Exam Drill 2 Compare the "Push" and "Pull" models of Observer notification across Extensibility, Coupling, and Performance. (6 Exam Points)

Comparison Table:

  • Push Model: update(temp, humidity, pressure) sends all data fields in the method signature.
    Coupling: Tightly couples observers to the exact data signature. Adding a new measurement (wind speed) breaks all existing observers.
    Performance: Immediate access in a single call, but wastes bandwidth if observers only need one field.
  • Pull Model: update(Subject s) passes the Subject reference, and observers call getters (e.g. s.getTemperature()).
    Coupling: Highly extensible. Adding new getters does not alter the update() method signature.
    Performance: Slight overhead of multiple getter method invocations.
Exam Drill 3 Distinguish Chain of Responsibility from the Decorator Pattern. (4 Exam Points)

Model Answer:

Decorator: Focuses on additive composition. Every decorator in the chain executes its logic and unconditionally delegates to the wrapped component. The entire chain always executes.

Chain of Responsibility: Focuses on handling or delegating. A handler in the chain may service the request and short-circuit/terminate the chain (e.g., an AuthenticationFilter returning HTTP 401 without calling the servlet). Senders do not know which concrete node (if any) will handle the request.
