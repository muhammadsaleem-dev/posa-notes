Unit 3 · Structural Patterns

Iterator & Composite Pattern

“Evidently, then, a larger part of the ‘structure’ of a building or town consists of patterns of relationships.” — Christopher Alexander

Building robust tree hierarchies and separating traversal mechanics from underlying collection data structures.

1

3.3 The Iterator Pattern

Sequential access without exposing internal memory representations.

GoF Intent: Provide a way to access the elements of an aggregate object sequentially without exposing its underlying representation.

Problem: Lou’s Diner stores menu items in an ArrayList, while Mel’s Diner stores menu items in a fixed-size MenuItem[] array. The client waitress has to write two completely different, tightly-coupled loops to print the menus!

Solution: Encapsulate traversal inside an Iterator interface (hasNext(), next()). The aggregate implements createIterator(). Client code only iterates through the abstraction.

Single Responsibility Principle (SRP) Connection:

A collection should only have one responsibility: storing and managing elements. Managing traversal state (current index, filtering) is an orthogonal responsibility delegated to the Iterator.

2

3.4 The Composite Pattern

Treating individual leaf objects and nested composite structures uniformly.

GoF Intent: Compose objects into tree structures to represent part-whole hierarchies. Composite lets clients treat individual objects and compositions of objects uniformly.

Problem: What if a Menu contains Sub-Menus (e.g. Dessert Menu inside Dinner Menu)? Treating leaves and branches with separate classes forces clients to write recursive type-checking checks (instanceof).

How Composite Eliminates Conditionals

In naive code, traversing a tree structure requires ugly type checks:

BadCode.java (Anti-pattern)Without Composite
for (Object item : items) {
    if (item instanceof MenuItem) {
        ((MenuItem) item).printDetails();
    } else if (item instanceof SubMenu) {
        ((SubMenu) item).displaySubMenu(); // UGLY CONDITIONALS!
    }
}

With the Composite Pattern, polymorphism handles the recursion natively:

GoodCode.java (Clean Architecture)With Composite
// The client simply calls print() on the root component!
menuComponent.print();

// Inside Menu (Composite):
public void print() {
    System.out.println(getName() + " -- " + getDescription());
    for (MenuComponent component : menuComponents) {
        component.print(); // Recursive polymorphic dispatch!
    }
}

3.6 Exercise: Questions for Self-Study (Exam Practice)

Self-Study Q1 What are the trade-offs between "Transparency" and "Safety" in the Composite Pattern?

The Core Tension:

  • Transparency (GoF Default): Define child-management methods (add(), remove(), getChild()) in the root Component interface.
    Advantage: 100% uniformity. Clients treat Leaf and Composite identically without casting.
    Disadvantage (Loss of Type Safety): Calling add() on a Leaf is semantically invalid at runtime (throws UnsupportedOperationException).
  • Safety: Declare add() and remove() ONLY in the Composite class.
    Advantage: Compile-time type safety; impossible to call add() on a Leaf.
    Disadvantage (Loss of Transparency): Clients must check types and cast before managing children, reintroducing conditionals.
