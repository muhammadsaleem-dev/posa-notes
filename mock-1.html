Exam Sheet Question 6 · 5 pts Which of the OOP principles does decorator primarily follow: Inheritance or composition and briefly explain why?

Primary Principle: Composition (Object Composition over Class Inheritance)

Official Model Explanation (Prof. Dr. Jörg Schäfer Standard):

  1. Dynamic Behavioral Delegation (Composition): The Decorator pattern primarily follows object composition. The decorator maintains an instance variable referencing the wrapped component (protected Component component;) and delegates client requests to it dynamically at runtime. This prevents the exponential subclass explosion problem (e.g. Starbuzz coffee with 64 static subclasses) by allowing responsibilities to be attached and detached at runtime.
  2. Type Conformance Only (Inheritance): While the abstract Decorator class extends or implements the Component supertype, it does so strictly for interface conformance and type substitutability (so the decorator can stand in transparently wherever a Component is expected), NOT for inheriting behavior or reusing implementation code.
⚠️ Common Exam Trap: Stating that Decorator is an example of inheritance because Decorator extends Component loses the majority of points. The professor specifically tests whether you recognize that inheritance is only used for subtyping, while all functionality is delivered via composition.
Exam Sheet Question 7 · 5 pts What is the main task/role of the model in MVC?

Official Model Answer:

The Model represents the core computational and business logic of the Model-View-Controller architecture:

  1. Encapsulates Domain State & Invariants: It holds the application's domain data, business logic, calculations, and data consistency invariants. It acts as the single source of truth for the entire system.
  2. Subject in Observer Pattern: The Model manages registered observers (the views). Whenever its state changes, it broadcasts notifications via notifyObservers() without knowing the concrete GUI types of the observers.
  3. Complete Presentation Independence: The Model possesses zero knowledge of, and zero references to, user interface widgets, event listeners, or controllers. This enables headless automated testing and allows multiple disparate views (e.g., graphical chart, tabular grid, mobile app) to observe the same model simultaneously.
Exam Sheet Question 8 · 5 pts How does the Strategy Pattern differ from the Template Method Pattern?

Official Model Answer:

The fundamental distinction lies in coupling mechanism, runtime mutability, and algorithm granularity:

  1. Mechanism & Coupling:
    • Strategy utilizes object composition and delegation. The Context holds a reference to a Strategy interface and delegates computations to it.
    • Template Method utilizes class inheritance. Subclasses extend an abstract base class and override specific primitive/hook steps.
  2. Runtime Mutability:
    • Strategy allows swapping the entire algorithm dynamically at runtime via a setter method (e.g., duck.setFlyBehavior(new FlyRocketPowered())).
    • Template Method binds the algorithm variant statically at compile-time through class inheritance; altering behavior requires creating a different class instance.
  3. Granularity of Variation:
    • Strategy encapsulates and swaps the entire algorithm as an atomic unit.
    • Template Method preserves an invariant algorithm skeleton in the superclass and allows subclasses to alter only individual steps.

Exam Notes Case Study JUnit · 5 pts From looking at the JUnit pattern and UML diagram, where are the extension points used when using JUnit in a regular way vs extending JUnit with new framework capabilities?

Official Model Answer:

  • Regular Use Extension Points (Application Developers):
    1. Subclassing TestCase to define concrete test fixtures.
    2. Adding public test*() methods containing assertions.
    3. Overriding the Template Method hooks setUp() and tearDown() to initialize and clean up fixtures before/after each test execution.
  • Framework Extension Points (Tool & Plugin Developers):
    1. Overriding runTest(): Customize how test methods are dispatched (e.g. running tests in separate threads, parameterized data-driven runners).
    2. Extending TestSuite: Subclassing the Composite to dynamically assemble test suites from databases or file directories.
    3. Custom TestResult & TestListener: Implementing TestListener to capture start/end/failure events for custom GUIs, CI/CD XML reporting, or HTML dashboards.
Exam Notes Christopher Alexander & Epistemology · 5 pts Name 4 architectural building patterns from Christopher Alexander's 1977 book. Can we implement a reusable binary "pattern library" for software? Explain why or why not.

Part 1: 4 Physical Building Patterns from Alexander:

  1. Ring Roads: High-speed bypass roads preserving pedestrian city centers.
  2. Four-Storey Limit: Limiting buildings to four floors to maintain human scale and psychological connectivity.
  3. Window Place: Built-in alcoves providing natural lighting for quiet reflection.
  4. South Facing Outdoors: Locating open-air terraces to maximize natural sunlight and thermal comfort.

Part 2: Why We Cannot Implement a Reusable Binary Pattern Library:

Software patterns are abstract architectural templates and collaboration relationships, not concrete binary components. Unlike a math library or UI widget jar, a pattern must balance conflicting forces that vary depending on the problem domain, threading model, and language paradigm. Implementing a pattern requires structural integration into the application's domain type hierarchy.

Exam Notes Architectural Styles · 5 pts Could you implement a compiler using Pipes & Filters? What features make it less suitable for a modern compiler? In the Blackboard architecture, when should the application main loop stop?

Part 1: Pipes & Filters for Modern Compilers:

  • Yes: Classic early compilers were structured as pure linear pipelines: Lexer $\to$ Parser $\to$ Semantic Analyzer $\to$ Code Generator.
  • Why it is less suitable today: Modern optimizing compilers rely heavily on global symbol tables, multi-pass Abstract Syntax Tree (AST) optimizations, inline function expansions, and rich bidirectional error diagnostics. These require non-linear random access and feedback loops that strict unidirectional stream pipes cannot support.

Part 2: Blackboard Main Loop Termination Criteria:

The control loop stops when any of the following 3 conditions occur:

  1. Hypothesis Confidence Threshold: A Knowledge Source produces an acceptable solution reaching the target confidence score.
  2. Quiescence / Deadlock: No Knowledge Source is able to trigger or make further progress given the current state of the blackboard.
  3. Resource Bound Exhaustion: The allocated compute budget, memory ceiling, or time deadline is reached.

SOLID Principles & Package Architecture Metrics 15 Points

Rigorous mathematical package derivations and object-oriented architectural formalisms.

Exam Notes Liskov Substitution Principle · 5 pts Can you check for conformance to the Liskov Substitution Principle (LSP) automatically using static analysis tools? Why or why not?

Official Model Answer: No, not completely.

  • What static tools can check: Compilers and static checkers can automatically verify syntactic subtyping (method names, parameter type contravariance, return type covariance, and exception throwing rules).
  • Why semantic LSP cannot be automatically checked: LSP is fundamentally a behavioral contract. It dictates that:
    1. Preconditions cannot be strengthened ($Pre(T) \implies Pre(S)$).
    2. Postconditions cannot be weakened ($Post(S) \implies Post(T)$).
    3. Class invariants must be preserved ($Inv(S) \implies Inv(T)$).
    4. Historical constraints must be respected (e.g. an immutable object must not become mutable in a subtype).

Statically checking whether arbitrary runtime code fulfills behavioral postconditions and invariants across all execution paths is undecidable (equivalent to the Halting Problem). Conformance verification requires Design by Contract (DbC) and extensive polymorphic test suites.

Exam Notes SRP & OCP Formalisms · 5 pts What is the precise definition of a "responsibility" in SRP? Does the sentence "This class adheres to the Open-Closed Principle" make sense in software architecture?

1. Definition of Responsibility in SRP:

Robert C. Martin explicitly defines a responsibility as "a reason to change". In clean architecture, a reason to change is tied to a specific business actor or stakeholder group (e.g., Accounting vs Operations). A class should be responsible to one, and only one, actor.

2. Does "This class adheres to OCP" make sense?

No, not unconditionally. A class cannot be open for extension and closed for modification against all possible future changes. Closure is never complete; it is always tactical. An architect must anticipate the specific axes of variation that are likely to change and protect against those specific forces. Claiming universal OCP adherence is meaningless.

Exam Notes Package Metrics Calculation · 5 pts Given a package $P$ with 2 abstract classes, 8 concrete classes ($N_c = 10$), 15 incoming dependencies ($C_a = 15$), and 5 outgoing dependencies ($C_e = 5$). Calculate $I$, $A$, and $D$. Interpret whether $P$ is well-designed.

Step-by-Step Mathematical Derivation:

  1. Instability Metric ($I$): $$I = \frac{C_e}{C_a + C_e} = \frac{5}{15 + 5} = \frac{5}{20} = 0.25$$ Interpretation: The package is highly stable ($I \to 0$); many external packages depend on it.
  2. Abstractness Metric ($A$): $$A = \frac{N_a}{N_c} = \frac{2}{10} = 0.20$$ Interpretation: The package is predominantly concrete ($A = 0.20$), with only 20% interfaces/abstract classes.
  3. Normalized Distance from Main Sequence ($D$): $$D = |A + I - 1| = |0.20 + 0.25 - 1| = |-0.55| = 0.55$$
  4. Architectural Diagnosis: Because $D = 0.55 > 0.5$, the package deviates substantially from the Main Sequence line ($A + I = 1$). It falls deep into the Zone of Pain: it is heavily relied upon ($I = 0.25$), yet highly concrete ($A = 0.20$), making it rigid and difficult to modify without breaking external dependents.

Epistemology, Idioms & Norvig's Criticism 15 Points

Academic pattern critiques, programming idioms, and creational mechanics from the course syllabus.

Exam Notes Norvig's 16/23 Critique · 5 pts What was Peter Norvig's core critique regarding the 23 Gang of Four patterns in dynamic and functional programming languages?

Official Model Answer:

In his 1996 analysis, Peter Norvig demonstrated that 16 of the 23 GoF design patterns are invisible or drastically simplified in languages with first-class functions, macros, or dynamic typing:

  • Strategy: Reduced to passing a first-class lambda or function pointer directly, eliminating the need for an interface and concrete strategy classes.
  • Command: Simply a closure or zero-argument lambda holding captured lexical state.
  • Template Method: Parameterizing a higher-order function with customized callback functions rather than class inheritance.
  • Composite / Iterator: Handled natively by built-in generators, list comprehensions, and uniform sequence protocols.

Norvig argued that many GoF patterns are symptoms of missing language features in static languages like C++ and Java 1.0 rather than fundamental universal design constructs.

Exam Notes Idioms vs Patterns · 5 pts Explain how the C function pointer compar in qsort() or Python's map() function represents the Strategy Pattern. Differentiate between an Idiom and a Design Pattern.

1. Strategy in C and Python:

  • In C qsort(base, nmemb, size, compar): The sorting algorithm skeleton is invariant, while the comparison algorithm (Strategy) is passed as a function pointer compar and executed via delegation.
  • In Python map(function, iterable): The iteration loop is invariant, while the element transformation algorithm is passed dynamically as a callable strategy object.

2. Idiom vs Design Pattern:

  • Programming Idiom: A low-level, language-specific pattern that directly exploits the features and syntax of a particular programming language (e.g., RAII in C++, list comprehensions in Python).
  • Design Pattern: A medium-scale, language-independent structural configuration of collaborating roles that balances forces regardless of implementation technology.
Exam Notes Creational Constraints · 5 pts In [GHJV95], an Abstract Factory is composed of Factory Methods, each with exactly one signature. Does this imply that the Factory Method can only create an object in one way? What do you do if you want to specify room color & size in MakeRoom()?

Official Model Answer:

No, it does not imply only one way:

  1. Subclass Customization: Concrete factory subclasses can override the factory method to return specialized subtypes or pre-configured instances without changing the method signature.
  2. Handling Additional Attributes (Color & Size):
    • Parameterization: Introduce parameters to the factory method signature: makeRoom(Color c, int size).
    • Factory Method Overloading: Provide overloaded variants in the factory interface.
    • Prototype / Parameter Object: Pass a configuration specification object or use the Prototype pattern to clone and customize templates without exploding the factory interface.
