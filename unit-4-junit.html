PILLAR 01 · FOUNDATIONAL INTENT

Intent & Cook’s Tour Design Objectives

The Challenge: Building a Test Framework

In 1997, on a flight from Zurich to Atlanta for OOPSLA, Erich Gamma and Kent Beck pair-programmed JUnit. Their goal was to create a framework that solved three conflicting constraints:

  • Low Writing Friction: Writing a test must be as simple as defining a method; zero ceremonial configuration files.
  • Preservation of Value: Tests must remain repeatable and self-verifying across years of refactoring without manual supervision.
  • Recursive Composability: Running a single test method, an entire test class, or a multi-module enterprise regression suite must appear completely uniform to the execution harness.

The Architectural Solution: Compounded Patterns

Rather than invent bespoke framework mechanics, Gamma and Beck demonstrated Christopher Alexander's principle: "Patterns collaborate in harmony to generate living structures."

JUnit combines Command, Composite, Template Method, Collecting Parameter, and Observer into a seamless, micro-architectural gem of fewer than 1,000 lines of code that revolutionized the global software industry.

PILLAR 03 · DYNAMIC EXECUTION TRACE

Dynamic Lifecycle Sequence: runBare() & Fixture Sandboxing

The Template Method runBare() guarantees that even if a test throws an assertion error, tearDown() runs in the finally block, ensuring zero resource leakage:

TestCase.java · runBare() Template Method Execution Sequence 
public void runBare() throws Throwable {
    Throwable exception = null;
    setUp(); // 1. Hook Method: Fresh fixture per test
    try {
        runTest(); // 2. Dynamic Adapter / Test execution
    } catch (Throwable running) {
        exception = running;
    } finally {
        try {
            tearDown(); // 3. Invariant cleanup in finally
        } catch (Throwable tearingDown) {
            if (exception == null) exception = tearingDown;
        }
    }
    if (exception != null) throw exception;
}

PILLAR 05 · COMPOUNDED PATTERNS MATRIX

The 5 Compounded Patterns in Cook’s Tour

1. Command Pattern (TestCase)

Encapsulates a test execution request as an object. Decouples the invoker (TestRunner GUI/CLI) from the receiver (test business assertions).

2. Composite Pattern (TestSuite)

Enables treating individual test cases and collections of tests uniformly through the shared Test interface.

3. Template Method (runBare)

Defines the invariant skeleton algorithm setUp() -> runTest() -> tearDown(), deferring specific fixture setup to subclasses.

4. Collecting Parameter (TestResult)

Accumulates test failures, errors, and run counts across the entire composite tree without requiring exceptions to propagate upward.

5. Observer Pattern (TestListener)

TestResult notifies registered TestListener observers (progress bars, text loggers) whenever a test starts, fails, or completes.

6. Adapter Pattern (Reflection)

Adapts arbitrarily named public methods (e.g. testMoneyEquals()) to the fixed runTest() interface dynamically.

PILLAR 06 · FRAMEWORK ANTI-PATTERNS

Test Framework Anti-Patterns & Architectural Smells

1. Monolithic Runner Lock-In (JUnit 4)

In JUnit 4, a test class could only declare a single `@RunWith` runner (e.g. `@RunWith(SpringRunner.class)` OR `@RunWith(MockitoJUnitRunner.class)`). You could not combine them.

Remedy: JUnit 5's `@ExtendWith` supports multiple composable extensions.
2. Leaky Shared Fixture

Reusing a mutable instance field across multiple tests instead of reinstantiating fresh instances per test method execution.

Remedy: Fresh instance per method (JUnit's default PER_METHOD lifecycle).
PILLAR 07 · PRODUCTION CODE STANDARD

Modern JUnit 5 Jupiter Extension Architecture

TimingExtension.java · JUnit 5 Composable Extension 
package de.frankfurt.uas.posa.extensions;

import org.junit.jupiter.api.extension.*;
import java.lang.reflect.Method;

// JUnit 5 composable interceptor replacing monolithic @RunWith
public class TimingExtension implements BeforeTestExecutionCallback, AfterTestExecutionCallback {

    private static final ExtensionContext.Namespace NAMESPACE =
        ExtensionContext.Namespace.create(TimingExtension.class);

    @Override
    public void beforeTestExecution(ExtensionContext context) {
        context.getStore(NAMESPACE).put(context.getRequiredTestMethod(), System.currentTimeMillis());
    }

    @Override
    public void afterTestExecution(ExtensionContext context) {
        Method method = context.getRequiredTestMethod();
        long start = context.getStore(NAMESPACE).remove(method, long.class);
        long duration = System.currentTimeMillis() - start;
        System.out.printf("Method [%s] executed in %d ms%n", method.getName(), duration);
    }
}
PILLAR 08 · EXAM TRAPS & DEFENSE

Frankfurt UAS Examination Pitfalls (Prof. Dr. Jörg Schäfer)

Exam Trap 1: "Why does TestResult exist?"

Schäfer's Trap: "Why didn't Gamma and Beck just have `TestCase.run()` throw an exception or return an error code integer?"
Correct UAS Defense: If a test threw an exception out of run(), the composite TestSuite iteration would immediately halt, preventing subsequent tests from running. Returning an integer would pollute method signatures. The Collecting Parameter pattern accumulates results across the entire composite hierarchy while decoupling test execution from GUI presentation.

Exam Trap 2: Difference between Failure and Error

Schäfer's Trap: "What is the structural difference between `addFailure` and `addError` in TestResult?"
Correct UAS Defense: A Failure is expected and handled: an AssertionFailedError was thrown by an assertion method. An Error is unexpected: an unhandled runtime exception (e.g. NullPointerException, ArrayIndexOutOfBoundsException) escaped during execution.

STAGE 02 OF 05 · ARCHITECTURAL HARMONY

Patterns Working in Harmony

Command & Composite Synergies

TestCase is a Command object encapsulating the execution of a test method. TestSuite is a Composite that aggregates multiple Test instances.

Because both implement the Test interface, a TestSuite can contain other TestSuite instances recursively. The runner calls test.run(result) without knowing whether it is executing a leaf or an entire module hierarchy.

Template Method & Collecting Parameter

TestCase.runBare() uses Template Method to bracket test execution with setUp() and tearDown().

Errors are passed to TestResult via Collecting Parameter. Furthermore, TestResult is an Observer Subject: whenever a test finishes, it notifies GUI/CLI observers without coupling test code to UI libraries.

STAGE 04 OF 05 · PRODUCTION ARCHITECTURE

Handcrafted Mini-JUnit Cook’s Tour Engine

MiniJUnitEngine.java · Complete Cook's Tour Core 
package de.frankfurt.uas.posa.minijunit;

import java.util.*;

// 1. COMPOSITE INTERFACE
public interface Test {
    void run(TestResult result);
    int countTestCases();
}

// 2. COMMAND & TEMPLATE METHOD LEAF
public abstract class TestCase implements Test {
    private final String name;
    public TestCase(String name) { this.name = name; }

    @Override
    public void run(TestResult result) {
        result.startTest(this);
        try {
            runBare();
        } catch (AssertionError f) {
            result.addFailure(this, f);
        } catch (Throwable e) {
            result.addError(this, e);
        } finally {
            result.endTest(this);
        }
    }

    // Template Method
    public void runBare() throws Throwable {
        setUp();
        try {
            runTest();
        } finally {
            tearDown();
        }
    }

    protected void setUp() throws Exception {}
    protected void tearDown() throws Exception {}
    protected abstract void runTest() throws Throwable;

    @Override
    public int countTestCases() { return 1; }
}

// 3. COMPOSITE SUITE
public class TestSuite implements Test {
    private final List<Test> tests = new ArrayList<>();
    public void addTest(Test t) { tests.add(t); }

    @Override
    public void run(TestResult result) {
        for (Test t : tests) {
            if (result.shouldStop()) break;
            t.run(result);
        }
    }

    @Override
    public int countTestCases() {
        return tests.stream().mapToInt(Test::countTestCases).sum();
    }
}

// 4. COLLECTING PARAMETER & OBSERVER SUBJECT
public class TestResult {
    private int runTests = 0;
    private final List<String> failures = new ArrayList<>();
    private final List<String> errors = new ArrayList<>();

    public synchronized void startTest(Test t) { runTests++; }
    public synchronized void endTest(Test t) {}
    public synchronized void addFailure(Test t, AssertionError f) { failures.add(t.toString() + ": " + f.getMessage()); }
    public synchronized void addError(Test t, Throwable e) { errors.add(t.toString() + ": " + e.getMessage()); }
    public boolean wasSuccessful() { return failures.isEmpty() && errors.isEmpty(); }
    public boolean shouldStop() { return false; }
}

STAGE 05 OF 05 · ACADEMIC VERIFICATION

Frankfurt UAS Examination Drills (Prof. Dr. Jörg Schäfer)

Exam Drill 1 · Pattern Collaboration Name the four primary patterns in Gamma and Beck’s Cook’s Tour and describe how they interact.

Official Model Answer:

  1. Command (TestCase): Wraps test method executions as standalone command objects that can be collected and invoked polymorphically.
  2. Composite (TestSuite): Composes individual TestCase commands and nested TestSuite containers under the unified Test interface.
  3. Template Method (runBare): Defines the execution algorithm invariant: setUp() $\to$ runTest() $\to$ tearDown(), where tearDown() is protected inside a finally block.
  4. Collecting Parameter (TestResult): Thread-safe object passed across the composite hierarchy to record passed counts, failure stacks, and unhandled errors without stopping test execution.
Exam Drill 2 · Decoupling How does JUnit keep its core engine decoupled from graphical user interfaces (e.g. Swing, Eclipse, IntelliJ)?

Official Model Answer:

Via the Observer Pattern. TestResult acts as the Subject. GUI and CLI runners implement the TestListener interface and register themselves with testResult.addListener(this). When tests start, fail, or end, TestResult notifies the listener, updating progress bars and counters without the core JUnit classes ever importing a UI framework.

Exam Drill 3 · JUnit 5 Migration Why was the monolithic `@RunWith` and `@Rule` model of JUnit 4 replaced with `@ExtendWith` in JUnit 5?

Official Model Answer:

JUnit 4 suffered from the Single Runner Limitation: a test class could only specify one `@RunWith` runner. This prevented developers from simultaneously using Spring's test runner, Mockito's runner, and parameterization. JUnit 5 solved this with the Jupiter Extension Model (`@ExtendWith`), which uses composable, multi-stage lifecycle interceptors that can be stacked arbitrarily on any test class or method.
