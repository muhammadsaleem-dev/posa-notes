Unit 7 · Macro Architecture & Modularity

OO Principles II: Packaging Patterns & Metrics

Scaling beyond individual classes into packages, JARs, and microservice modules. Uncle Bob’s 6 package principles and the mathematical metrics for stability and abstractness.

1

7.3.2 Principles of Package Cohesion

Which classes belong inside the same package?

1. REP: Reuse-Release Equivalence Principle

“The granule of reuse is the granule of release.” You cannot effectively reuse a library without tracking version numbers and changelogs. Everything inside a package must be released together under a shared version tag.

2. CRP: Common-Reuse Principle

“Classes that aren’t reused together should not be packaged together.” Prevents clients from depending on classes they don’t actually need. (The package-level equivalent of the Interface Segregation Principle).

3. CCP: Common-Closure Principle

“The classes in a package should be closed together against the same kinds of changes.” If requirements change, all affected classes should reside in a single package. (The package-level equivalent of the Single Responsibility Principle).

7.3.6 Principles of Package Coupling

How packages should depend on one another.

1. ADP: Acyclic-Dependencies Principle

“The dependency structure between packages must form a Directed Acyclic Graph (DAG).” No cyclic dependencies! Cycles create a “morning-after syndrome” where changes anywhere break builds everywhere.
How to break cycles: (A) Apply Dependency Inversion (DIP) with an interface; or (B) extract shared dependencies into a new third package.

2. SDP: Stable-Dependencies Principle

“Depend in the direction of stability.” A package should only depend on packages that are more stable than itself. Volatile packages should sit at the top of the dependency graph; stable packages at the bottom.

3. SAP: Stable-Abstractions Principle

“A package should be as abstract as it is stable.” A stable package that is heavily depended upon must be abstract (composed of interfaces) so it can be extended without requiring source code modifications.

7.3.8 Mathematical Package Metrics

Quantifying stability, abstractness, and architectural health.

1. Instability Metric ($I$)

Coupling count: $C_a$ (Afferent coupling: incoming dependencies), $C_e$ (Efferent coupling: outgoing dependencies).

Instability: I = C_e / (C_a + C_e)
  • $I = 0$ (Maximally Stable): $C_e = 0$, $C_a > 0$. Depended upon by many packages, depends on none. Hard to change.
  • $I = 1$ (Maximally Unstable): $C_e > 0$, $C_a = 0$. Depends on many packages, depended upon by none. Easy to change.

2. Abstractness Metric ($A$)

Ratio of abstract classes & interfaces ($N_a$) to total classes ($N_c$).

Abstractness: A = N_a / N_c
  • $A = 0$: Completely concrete package (no interfaces).
  • $A = 1$: Pure abstraction (only interfaces and abstract classes).

3. Normalized Distance from the Main Sequence ($D$)

Normalized Distance: D = |A + I - 1|

On the ideal Main Sequence, $A + I = 1$. The further a package drifts ($D \to 1$), the more architecturally troubled it is:

A (Abstractness) ▲ 1.0 ┌──────────────────────────────────────┐ │ Zone of Uselessness │ │ (A=1, I=1: Abstract, but unreferenced) │ \ │ │ \ THE MAIN SEQUENCE │ │ \ (Ideal Balance: A+I=1) │ │ \ │ │ \ │ │ Zone of Pain │ │ (A=0, I=0: Concrete & unchangeable) │ 0.0 └──────────────────────────────────────┴──► I (Instability) 0.0 1.0
⚠️ Zone of Pain ($A=0, I=0$)

Completely concrete, but heavily depended upon. Highly rigid and painful to change (e.g. core database entities without interfaces).

👻 Zone of Uselessness ($A=1, I=1$)

Pure abstract classes that nobody depends on. Waste of design effort; dead abstractions.

7.5 Questions for Self-Study (Exam Practice)

Exam Calculation A package has 3 incoming package dependencies ($C_a = 3$) and depends on 1 external package ($C_e = 1$). It contains 2 interfaces and 8 concrete classes ($N_c = 10$). Compute Instability ($I$), Abstractness ($A$), and Distance ($D$). Is this package in good architectural health?

Step-by-Step Calculation:

  1. $I = \frac{C_e}{C_a + C_e} = \frac{1}{3 + 1} = \frac{1}{4} = \mathbf{0.25}$
  2. $A = \frac{N_a}{N_c} = \frac{2}{10} = \mathbf{0.20}$
  3. $D = |A + I - 1| = |0.20 + 0.25 - 1| = |-0.55| = \mathbf{0.55}$

Architectural Diagnosis:

$D = 0.55$ indicates noticeable drift toward the Zone of Pain ($A + I = 0.45 < 1$). Because the package is relatively stable ($I = 0.25$), it is depended upon by 3 external packages, but it is $80\%$ concrete ($A = 0.20$). To restore balance closer to the Main Sequence, the developers should extract interfaces for the exported classes to increase $A$.
