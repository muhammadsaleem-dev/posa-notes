Unit 7 · Macro Architecture & Package Design

Package Principles & Main Sequence Metrics

Master Robert C. Martin's 6 package principles (cohesion & coupling), the Cohesion Tension Triangle, cycle breaking via DIP, and quantitative package metrics: Instability ($I$), Abstractness ($A$), and Distance from the Main Sequence ($D$).

⚡ Executive Summary Packaging Principles & Metrics: Enterprise Modularity
Collapse Expand

“Packages are the unit of release and deployment. Clean architecture balances package cohesion, coupling, and stability metrics.”

🎯 Package Cohesion vs. Package Coupling

Cohesion rules (REP, CCP, CRP) govern which classes belong together. Coupling rules (ADP, SDP, SAP) govern package dependencies: eliminate dependency cycles and depend toward stability.

→ Acyclic Dependencies Principle (ADP) is non-negotiable.
🕵️‍♂️ The Main Sequence & Normalized Distance (D)

Instability I = Ce/(Ca+Ce) and Abstractness A = Na/Nc. The Main Sequence balances A + I = 1. Distance D = |A+I-1| measures design health. Avoid the Zone of Pain (I=0, A=0) and Zone of Uselessness (I=1, A=1).

→ D near 0 represents optimal enterprise package architecture.
Package Architecture Health Matrix
Concept / Pattern Architectural Mechanism Why It Matters in Practice & Exams
The Main Sequence A + I = 1 (D ≈ 0) Ideal balance between abstractness and package stability.
Zone of Pain I = 0, A = 0 (Rigid Concrete) Highly depended-upon, completely concrete. Very painful to modify (e.g. legacy DB schema).
Zone of Uselessness I = 1, A = 1 (Unused Abstraction) Completely abstract, but no packages depend on it. Pure dead speculative design.

The 6 Packaging Principles

Granularity & Coupling Boundaries
Part 1: Package Cohesion Principles (What belongs inside a package): • REP (Reuse/Release Equivalence Principle): "The granule of reuse is the granule of release." Reusable packages must be tracked with official release numbers, changelogs, and documentation so consumers know when to upgrade.
• CCP (Common Closure Principle): "Classes that change together are packaged together." (The package-level SRP). Gathers classes subject to the same business forces into a single package to minimize the number of packages affected when requirements change.
• CRP (Common Reuse Principle): "Classes that are not used together should not be packaged together." (The package-level ISP). Prevents package consumers from being forced to re-compile or re-test when classes they don't even use are updated.
Part 2: Package Coupling Principles (How packages interact): • ADP (Acyclic Dependencies Principle): "Allow no cycles in the package dependency graph." The dependency graph between packages must form a Directed Acyclic Graph (DAG).
• SDP (Stable Dependencies Principle): "Depend in the direction of stability." A package should only depend on packages that are more stable than itself ($I_{\text{target}} \le I_{\text{source}}$).
• SAP (Stable Abstractions Principle): "A package should be as abstract as it is stable." Stable packages must be abstract ($A \approx 1$) so they can be extended via polymorphism; unstable packages should be concrete ($A \approx 0$).
COHESION TRIANGLE Figure 7.1: The Dynamic Tension Between REP, CCP, and CRP

The three package cohesion principles are mutually antagonistic. You cannot maximize all three simultaneously. Architecture is the art of balancing this tension based on project lifecycle:

CRITICAL EXAM DRILL Two Strategies to Break Dependency Cycles (ADP)

When two packages depend on each other (e.g. Orders depends on Billing, and Billing depends on Orders), the build system breaks down into the "Morning After Syndrome". Independent releases become impossible. Two canonical strategies eliminate the cycle:

Strategy 1: Invert Dependency via DIP

If Billing needs an OrderRecord class in Orders, extract an interface BillableOrder into Billing. Have the class in Orders implement that interface.

The Result: The dependency arrow from Billing → Orders is completely reversed into Orders → Billing. The cycle is eliminated!

Strategy 2: Extract a Shared Package

Identify the mutual data structures or entities causing the cycle and move them into a brand-new third package: OrderBillingCore.

The Result: Both Orders and Billing depend downward on OrderBillingCore. Neither package depends on the other, creating a clean Directed Acyclic Graph (DAG).

Robert C. Martin's Package Metrics

Quantitative Stability & Abstractness
FORMULAS & DEFINITIONS Computing $Ca$, $Ce$, $I$, $A$, and $D$

Instability Metric ($I$)

$$I = \frac{Ce}{Ca + Ce} \quad (0 \le I \le 1)$$ • $Ca$ (Afferent Coupling): Number of external classes that depend on classes inside this package (incoming arrows). High $Ca$ makes a package responsible and stable.
• $Ce$ (Efferent Coupling): Number of classes inside this package that depend on external classes (outgoing arrows). High $Ce$ makes a package dependent and volatile.
• $I = 0$: Maximally stable package (relied upon by many, depends on none).
• $I = 1$: Maximally unstable package (relies on many, no incoming dependents).

Abstractness Metric ($A$)

$$A = \frac{Na}{Nc} \quad (0 \le A \le 1)$$ • $Na$: Number of abstract classes and interfaces in the package.
• $Nc$: Total number of classes (concrete + abstract + interfaces) in the package.
• $A = 0$: Purely concrete package ($Na = 0$).
• $A = 1$: Purely abstract package (only interfaces/abstract classes).

Normalized Distance from Main Sequence ($D$)

$$D = |A + I - 1| \quad (0 \le D \le 1)$$ • The Main Sequence line satisfies: $A + I = 1$.
• Packages close to $D = 0$ are architecturally well-balanced between stability and abstractness.
• Packages with $D \to 1$ suffer from pathological design flaws (Zone of Pain or Zone of Uselessness).

The Zone of Pain vs. The Zone of Uselessness

Main Sequence Vector Chart
📐 Canonical Architecture: Figure 7.2 The Main Sequence Diagram ($A$ vs $I$)
Zone of Pain ($A \approx 0, I \approx 0$)

Packages here are maximally stable ($I=0$) and maximally concrete ($A=0$). Many external packages depend on them, yet they contain no abstractions. Modifying them causes massive ripple effects.

Permissible Exception: Non-volatile utility foundations (e.g. java.lang.String, basic math libraries). Because they never change, their concreteness causes no pain.

Zone of Uselessness ($A \approx 1, I \approx 1$)

Packages here are maximally abstract ($A=1$) and maximally unstable ($I=1$). They contain pure abstract interfaces, but zero external packages depend on them.

Architectural Pathology: Represents dead code, abandoned design attempts, or premature over-engineering ("speculative generality").

Core Exam Practice & Model Solutions

Direct Question → Answer Format
Question 1: Explain the Acyclic Dependencies Principle (ADP) 3 Points

Explain the Acyclic Dependencies Principle (ADP). Why are dependency cycles problematic, and what are two strategies to break them?

Model Answer:
  1. Principle: The dependency graph of packages must contain no cycles; it must be a Directed Acyclic Graph (DAG).
  2. Problem: Cycles create the "Morning After Syndrome". If Package A depends on Package B, and B depends on A, any change in A forces a re-build and re-test of B, which in turn triggers a re-build of A. The packages merge into one monolithic build unit, making independent testing and releasing impossible.
  3. Two Cycle-Breaking Strategies:
    • Dependency Inversion Principle (DIP): Introduce an interface in the caller's package and invert the dependency arrow.
    • Extract Shared Package: Move the classes both packages depend upon into a new shared third package.
Question 2: Complete Main Sequence Calculation for Package $P$ 10 Points

Given a package $P$ with 2 abstract classes, 8 concrete classes, 15 incoming dependencies ($Ca = 15$), and 5 outgoing dependencies ($Ce = 5$):
1. Calculate Instability ($I$).
2. Calculate Abstractness ($A$).
3. Calculate Normalized Distance ($D$) from the Main Sequence.
4. Interpret whether package $P$ is well-designed!

Model Answer:
  1. Instability ($I$): $$I = \frac{Ce}{Ca + Ce} = \frac{5}{15 + 5} = \frac{5}{20} = 0.25$$ Interpretation: The package is highly stable ($I = 0.25$). 75% of all connections are incoming dependencies from external modules.
  2. Abstractness ($A$): $$Nc = 2 + 8 = 10 \quad (\text{Total classes})$$ $$A = \frac{Na}{Nc} = \frac{2}{10} = 0.20$$ Interpretation: The package is largely concrete ($A = 0.20$); only 20% of its types are abstract.
  3. Normalized Distance from Main Sequence ($D$): $$D = |A + I - 1| = |0.20 + 0.25 - 1| = |0.45 - 1| = |-0.55| = 0.55$$
  4. Architectural Interpretation (Evaluation):

    Package $P$ is NOT well-designed. With $D = 0.55$, it deviates significantly from the Main Sequence line ($D = 0$) and drifts into the dangerous Zone of Pain.

    Because package $P$ is heavily relied upon by 15 external classes ($I = 0.25$), the Stable Abstractions Principle (SAP) demands that it should be highly abstract ($A \approx 1 - I = 0.75$). Since it is mostly concrete ($A = 0.20$), any change or bug fix inside its 8 concrete classes threatens to break the 15 dependent client classes.

    Remediation: Extract public interfaces for the concrete classes to push $A$ closer to $0.75$, bringing $D \to 0$.

Question 3: Inverting Dependencies vs. Extracting Packages 4 Points

Package GUI depends on Package Core. A new feature requires Core to notify GUI when data changes. How do you prevent a cyclic dependency?

Model Answer:

Do NOT allow Core to import GUI classes directly! Instead, apply the Dependency Inversion Principle (DIP):

  1. Define an Observer or ProgressListener interface inside Package Core.
  2. In Package GUI, implement this interface on the window/dialog class.
  3. At runtime, the GUI registers itself with Core.

Result: Compile-time dependency remains strictly one-way (GUI → Core), while runtime execution flows in reverse from Core to GUI. Zero cycle exists.

Question 4: Permissibility in the Zone of Pain 4 Points

Under what specific condition is a package permitted to reside deep in the Zone of Pain ($A=0, I=0$)? Give a real-world software example.

Model Answer:

A package is permitted in the Zone of Pain if and only if it is completely non-volatile (it will never, or virtually never, undergo changes).

  • Real-world Example: java.lang.String or the standard C runtime math library.
  • Reasoning: Millions of programs depend directly on java.lang.String ($Ca \to \infty \implies I=0$). It is completely concrete and final ($A=0$). However, because String has maintained an immutable, backwards-compatible API for 30 years, its concreteness causes zero pain. Pain only occurs when a stable, concrete package is volatile.
Question 5: Stable Dependencies Principle (SDP) Detection 5 Points

Package $X$ has $I = 0.2$. Package $Y$ has $I = 0.7$. If a developer adds an import from Package $X$ to a class in Package $Y$, does this violate SDP? Explain the architectural consequences.

Model Answer:

YES, this directly violates the Stable Dependencies Principle (SDP).

  1. Rule: SDP mandates that dependencies must flow in the direction of stability: $I_{\text{target}} \le I_{\text{source}}$.
  2. Violation: Here, Package $X$ (very stable, $I = 0.2$) is depending on Package $Y$ (very unstable/volatile, $I = 0.7$).
  3. Consequences: Package $X$ is depended upon by many other packages. By depending on the volatile Package $Y$, Package $X$ now inherits all of $Y$'s instability. Whenever $Y$ changes, $X$ must change, which in turn cascades changes throughout all of $X$'s dependents. The architecture becomes rigid and fragile.
