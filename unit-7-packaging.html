PILLAR 1 OF 8 · INTENT & MOTIVATION

Macro Architecture: Packaging Granularity

When an application grows past dozens of classes, organizing code at the class level alone is insufficient. Packaging principles determine how classes are grouped into deployable modules (JARs, DLLs, npm packages) and how dependencies flow between them without cycles.

Architectural Goal

Prevent the "Morning-After Syndrome" (where independent team commits break unrelated modules) by establishing Directed Acyclic Graphs (DAG) and quantifying stability metrics.

PILLAR 2 OF 8 · PARTICIPANTS & ROLES

The 6 Packaging Principles Breakdown

Category Acronym Principle Name Architectural Mandate
Cohesion REP Reuse-Release Equivalence The granule of reuse is the granule of release. Track versions jointly.
Cohesion CCP Common-Closure Principle Package classes together that change for the same reasons (Package SRP).
Cohesion CRP Common-Reuse Principle Don't force clients to depend on classes they don't use (Package ISP).
Coupling ADP Acyclic-Dependencies No cyclic dependencies allowed in package dependency topology.
Coupling SDP Stable-Dependencies Depend in the direction of stability ($I_{dependee} \le I_{dependent}$).
Coupling SAP Stable-Abstractions A package should be as abstract as it is stable ($A \approx 1 - I$).
PILLAR 3 OF 8 · FORMAL UML ANATOMY

Breaking Dependency Cycles with DIP

When Package A depends on Package B, and Package B introduces a back-dependency on Package A, a toxic cycle forms. Applying DIP breaks the cycle into a DAG.

PILLAR 4 OF 8 · CORE FORMULAS & METRICS

The Quantitative Metrics (I, A, D)

Instability Metric: \(I = \frac{C_e}{C_a + C_e}\)

\(C_a\) = Afferent coupling (incoming). \(C_e\) = Efferent coupling (outgoing). \(I=0\) is maximally stable; \(I=1\) is maximally volatile.

Abstractness Metric: \(A = \frac{N_a}{N_c}\)

\(N_a\) = Abstract classes & interfaces. \(N_c\) = Total classes. \(A=0\) is pure concrete; \(A=1\) is pure abstraction.

Main Sequence Distance: \(D = |A + I - 1|\)

On the Main Sequence, \(A + I = 1\). Drift towards 1 indicates severe design flaws (Zone of Pain or Zone of Uselessness).

PILLAR 6 OF 8 · COSTS & TRADE-OFFS

The Cohesion Tension Triangle

An architect cannot maximize all three cohesion principles simultaneously. You must balance the tension:

REP + CCP (Group Together)

Favors package maintainers and frequent releases. Results in larger packages that require fewer cross-package edits.

CRP (Split Apart)

Favors external package consumers. Results in smaller packages so clients don't download unneeded code.

🚨 Frankfurt UAS Exam Trap #1: The Zone of Pain

Question: "Why is a package with A=0 and I=0 located in the Zone of Pain?"
Model Answer: Because \(I=0\) means it has high afferent coupling (\(C_a > 0, C_e = 0\))—many packages depend on it, making it extremely stable and painful to change. Simultaneously, \(A=0\) means it is 100% concrete with zero interfaces. It cannot be extended polymorphically, freezing the entire architecture into rigidity.

● Stage 01 · Package Cohesion Principles

Package Cohesion: REP, CCP, and CRP

Which classes belong together in the same package? Uncle Bob formulated three cohesion principles that govern package boundaries.

1. REP: Reuse-Release Equivalence Principle

“The granule of reuse is the granule of release.” You cannot effectively reuse software without tracking versions, release notes, and deprecation schedules. Everything grouped inside a package must be released together under a shared semantic version tag.

2. CCP: Common-Closure Principle

“The classes in a package should be closed together against the same kinds of changes.” If requirements change, all affected classes should reside in a single package. CCP is the package-level equivalent of the Single Responsibility Principle (SRP).

3. CRP: Common-Reuse Principle

“Classes that aren’t reused together should not be packaged together.” Prevents clients from depending on classes they don’t actually need. CRP is the package-level equivalent of the Interface Segregation Principle (ISP).

🧠 Key Takeaways: The Cohesion Tension Triangle
REP + CCP

Make packages larger so all related changes stay contained within one package release.

CRP

Splits packages smaller so external consumers don't download unneeded transitive dependencies.

Architect's Duty

Balance this dynamic tension as the codebase matures from early development to stable public library.

● Stage 02 · Package Coupling Principles

Package Coupling: ADP, SDP, and SAP

How should packages depend on one another? Uncle Bob formulated three coupling principles to prevent the dreaded "morning-after syndrome".

1. ADP: Acyclic-Dependencies Principle

“The dependency structure between packages must form a Directed Acyclic Graph (DAG).” No cyclic dependencies! Cycles force entire systems into single indivisible monolithic deployment units.
How to break cycles: (1) Apply DIP by inverting dependencies with an interface; or (2) Extract shared dependencies into a new third package.

2. SDP: Stable-Dependencies Principle

“Depend in the direction of stability.” A package should only depend on packages that are more stable than itself. Packages that are expected to change frequently (volatile UI or presentation) should depend on rock-solid core business domains.

3. SAP: Stable-Abstractions Principle

“A package should be as abstract as it is stable.” A stable package that is heavily depended upon must be abstract (composed of interfaces) so it can be extended without modifying its source code.

● Stage 04 · Architecture as Code

Automating Architecture Governance with ArchUnit

Modern engineering organizations do not rely on manual code review to enforce package coupling rules. They use automated architecture testing frameworks like ArchUnit in CI/CD pipelines.

PackageArchitectureTest.java · ArchUnit
package de.frankfurt.posa.packaging;

import com.tngtech.archunit.junit.AnalyzeClasses;
import com.tngtech.archunit.junit.ArchTest;
import com.tngtech.archunit.lang.ArchRule;
import static com.tngtech.archunit.library.dependencies.SlicesRuleDefinition.slices;
import static com.tngtech.archunit.library.Architectures.layeredArchitecture;

@AnalyzeClasses(packages = "de.frankfurt.posa")
public class PackageArchitectureTest {

    // 1. ADP Enforcement: Strictly forbid cyclic dependencies across all packages!
    @ArchTest
    public static final ArchRule NO_PACKAGE_CYCLES =
        slices().matching("de.frankfurt.posa.(*)..")
            .should().beFreeOfCycles();

    // 2. SDP Enforcement: Presentation cannot be accessed by Domain
    @ArchTest
    public static final ArchRule LAYER_DEPENDENCY_RULE =
        layeredArchitecture()
            .consideringAllDependencies()
            .layer("Presentation").definedBy("..presentation..")
            .layer("Domain").definedBy("..domain..")
            .layer("Infrastructure").definedBy("..infrastructure..")
            .whereLayer("Presentation").mayNotBeAccessedByAnyLayer()
            .whereLayer("Domain").mayOnlyBeAccessedByLayers("Presentation", "Infrastructure");
}

Exam Calculation Drill 1 A package has 3 incoming package dependencies ($C_a = 3$) and depends on 1 external package ($C_e = 1$). It contains 2 interfaces and 8 concrete classes ($N_c = 10$). Compute I, A, and D. Diagnose architectural health. (10 Exam Points)

Step-by-Step Calculation:

  1. \(I = \frac{C_e}{C_a + C_e} = \frac{1}{3 + 1} = \frac{1}{4} = \mathbf{0.25}\)
  2. \(A = \frac{N_a}{N_c} = \frac{2}{10} = \mathbf{0.20}\)
  3. \(D = |A + I - 1| = |0.20 + 0.25 - 1| = |-0.55| = \mathbf{0.55}\)

Architectural Diagnosis:

\(D = 0.55\) indicates significant drift toward the Zone of Pain (\(A + I = 0.45 < 1\)). Because the package is relatively stable (\(I = 0.25\)), it is depended upon by 3 external packages, but it is \(80\%\) concrete (\(A = 0.20\)). To restore balance closer to the Main Sequence, developers must extract interfaces for public classes to raise \(A\) closer to \(0.75\).

Exam Drill 2 Explain the two distinct strategies to break a cyclic dependency between Package A and Package B. (6 Exam Points)

Strategy 1: Dependency Inversion (DIP)

Create an interface in Package A that defines the operations Package B needs to call. Package B then realizes this interface. The dependency arrow inverts, transforming the cycle into a single-direction graph.

Strategy 2: Extract a Shared Third Package (Package C)

Extract the shared classes or data entities that both A and B need into a new independent package C. Both A and B depend on C, completely breaking the cycle between A and B.

Exam Drill 3 Why does the Common-Reuse Principle (CRP) cause packages to become smaller, while the Common-Closure Principle (CCP) causes them to become larger? (4 Exam Points)

Model Answer:

CCP (Group Together): Dictates that classes changing for the same reason should be packaged together. To reduce the blast radius of changes and the number of packages needing re-release, CCP groups classes, making packages larger.

CRP (Split Apart): Dictates that classes not reused together must be split. To prevent consumers from being forced to re-compile or re-deploy due to changes in classes they don't care about, CRP breaks packages into smaller units.
